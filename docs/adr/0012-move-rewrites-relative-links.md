# ADR-0012：跨目录移动时改写被移动笔记自身正文里的相对路径链接

- 状态：已采纳
- 日期：M3

## 背景

M3 交付了"拖拽整理文件"（`note_move`）：按字符 span 精确改写**全库指向被移动笔记**的链接，
保留别名/锚点、跳过代码块与行内代码、BOM/换行保真，并复用索引的解析规则
（`crates/mn-index/src/rename.rs` 的 `relocate_note`）。

但**被移动文件自身正文里**的相对链接没有跟着改写：`项目/设计文档.md` 里的
`![](../附件/图.png)` 一旦被移到别的目录，参照点就换了 —— 图片退化为占位元素，`[文字](子/篇.md)`
同理。这条限制写在 `docs/architecture.md` §8 与 `README.md` 的「已知限制」里。

当初没做的理由是"判断这个相对目标是不是 Vault 里的某个文件，需要完整条目表"，
而索引只收录 Markdown 笔记（图片/PDF 的全集在索引里根本不存在）。本轮要回答的是两个问题：

1. 改写的**判据**是什么 —— 要不要查文件系统？
2. 哪些形态**不能**碰 —— 碰了就是把用户写好的地址改坏。

## 决策

### 1. 纯路径算术，不做任何存在性检查

把"相对旧目录的路径"解析成"Vault 根相对路径"（`old_dir + 目标`），再用新目录重新表达：
`项目/设计文档.md` 里的 `../附件/图.png` → `附件/图.png`；移到 `日记/2026/` 后写成
`../../附件/图.png`。全程只有字符串运算（`links::join_relative` + `relative_posix`）。

为什么不做存在性检查：

- **拿不到全集**：索引只收录 Markdown。要判断 `../附件/图.png` 是否存在，就得扫盘（或维护第二份
  文件表）—— 而 1 万笔记场景的纪律是"绝不全库读文件"，改名/移动只碰候选集；
- **不会指错**：算术保证"改写前后指向同一个 Vault 根路径"，不做同名兜底，因此不会把链接改成
  指向别处的同名文件；
- **目标不存在时改写依然正确**：一条本来就悬空的相对链接，改写后依然悬空，但"相对于这篇笔记"
  的原意被完整保住 —— 那正是作者写下相对路径时的心智模型（阅读视图本来就按 URL 语义相对当前
  笔记解析）。ADR-0002 的口径也一致：Markdown 源码是唯一真相，我们只维护**相对关系**，
  不替用户判断文件在不在。

### 2. 只改"相对路径"链接，其余形态一律放行

判据落在 `mn_core::links::is_position_relative_target`：**它的含义是否随这篇笔记的位置变化**。

| 放行的形态 | 理由 |
| --- | --- |
| 带 scheme（`http:`/`https:`/`mailto:`/`data:`/`asset:`/`vscode:` …，大小写不敏感） | 不随位置变化，按路径改写是纯破坏。按 `scheme:` 语法判定，不用白名单 —— 白名单漏一个（例如 `asset:`）就会改坏一条本来正常的地址 |
| 协议相对 `//example.com/x`、Vault 根绝对 `/附件/图.png` | 参照点是根（或以 `/` 开头即绝对），与笔记位置无关 |
| 纯锚点 `#小节`、`^块标识` | 指向文内 |
| 裸名 wikilink `[[乙]]`、`![[图.png]]` | 由索引按"文件名主干 + 同目录优先"解析，写的不是路径（漂移风险见代价表） |
| 代码块、行内代码、反斜杠转义 | 沿用既有抽取器（`extract_links_with_spans`）的上下文判定，不另写一套 Markdown 解析器 |

刻意**不**复用 `links::is_external`：那个函数回答"索引要不要把这条链接算进链接图"（口径可以保守，
少收几条不算错），这里回答"改写时能不能按路径去动它"（口径必须更严）。两个问题不同，
口径也就必须分开写，否则收紧 `is_external` 会顺手改变索引的收录范围。

**含 `/` 的 wikilink 是例外**：`[[子/篇]]`、`![[附件/图.png]]` 写的就是路径 —— 索引对含 `/` 的目标
按"相对当前目录 → 相对根 → 路径后缀"三级解析，位置一换含义就变，所以它按路径改写。但这里多一道
**一致性校验**：索引当前解析到的目标若与路径算术不一致，就放行不动 —— 那种链接本来靠"相对根/后缀"
这一级兜着，按算术改写反而会把它弄悬空（Markdown 形式没有这个问题：阅读视图按 URL 语义相对当前
笔记解析，算术就是它的口径）。

### 3. Markdown 链接与图片全覆盖，复用既有的 span 改写

`[文字](目标)`、`[文字](<带 空格的目标>)`、`![alt](目标)`、`![alt](<目标> "title")` 都走
`extract_links_with_spans` + `replace_link_target`：

- 只替换**目标区**，因此别名、锚点、`<>` 包裹、`"title"` 原样留着；尖括号里的目标换完仍在括号里；
- 新目标含空格而原文没写 `<>` 时，由既有的"回读校验"（`replace_verified`）自动补上，
  补不上就跳过并记日志（宁可少改也不写出一个必然悬空的链接）；
- 具体支持到哪一层由 `mn-core/src/links.rs` 的能力决定，**没有为此引入任何新依赖**。

### 4. 只改"移动后路径确实变了"的链接，其余一个字符都不动

换目录后换算结果与原文一字不差（同级目录互换位置、同目录改名后的自链接）时**不写盘**：
无意义的 diff 会污染 git 历史，还会让 mtime 版本令牌无谓地跳一次，前端会误判成"文件被外部改过"。

同一条纪律统一了正文改写的坐标系：**正文改写后落在新目录，所有新目标都按新目录表达**
（`RewriteFrame::new_dir`）。被移动笔记的自链接也按新位置写 —— 若按旧目录写，写出来的路径从新位置
解析时会错位，深目录里甚至直接跑出 Vault 根。目录没变（同目录改名）时这条链路整段不参与。

### 5. 索引与全文搜索复用既有链路增量同步

被移动笔记自身在计划阶段就并入候选集（`referrers_of` 之外显式加它 —— 它正文里的图片、
同级笔记在索引里根本查不到归属），写回时照旧 `LinkIndex::upsert` + `SearchIndex::upsert_note`。
不新开第二条同步路径：链接文本变了，索引里的出链目标必须立刻跟着变（反链面板不必等重扫）。

## 代价与已知限制

| 项 | 说明 |
| --- | --- |
| 引用式定义的 URL 行（`[id]: ../附件/图.png`）不改写 | 既有抽取器不认这种形态（索引里也不算链接）。为它单写一份"围栏/缩进/转义"判定等于再养一套 Markdown 解析器，与本项目"规则只有一份"的纪律冲突。**用户仍会看到失效链接**：用引用式定义写图片地址的笔记，跨目录移动后图片依旧断掉 |
| 裸名 wikilink 的漂移不修 | `[[乙]]` 按名字解析；移动后若新目录（或全库）存在同名笔记，"同目录优先"可能把它指到**另一篇**上。修它要按索引模拟"搬家之后"的解析结果，属另一件事。**用户仍会看到失效/指错链接**：同名笔记多、又靠裸名链接时 |
| 反斜杠分隔的相对目标不改写 | Markdown 里 `\` 是转义字符（`\.` 与 `\附` 语义不同），而本层路径算术只认 POSIX `/`；`..\附件\图.png` 会被跳过 |
| 越出 Vault 根的目标不改写 | `../../外面/图.png` 无法用"Vault 根相对路径"表达——它本来就在 Vault 之外 |
| 目标不存在时也会被改写 | 纯路径算术的直接代价（见决策 1）：悬空的相对链接改写后依然悬空，只是被搬到新位置的相对关系上 |
| 只对 Markdown 笔记的正文改写 | 非笔记文件（`.txt`/`.json`/图片）里长得像链接的文本一律不碰 —— 只能靠扩展名判断，因为 UTF-8 的 `.txt` 能读成功 |
| 目录重命名 / 目录移动仍未做 | 与既有边界一致：要连同整棵子树的正文一起改写 |
| 被移动笔记自身的正文现在会变 | 前端必须重新读取它。既有契约已覆盖：`updated_links` 里被移动笔记按**旧路径**上报，`app/actions.ts` 命中它就 close + reopen，不需要新协议 |
| 单篇改写仍有体积上限 | 只读候选集（指向它的笔记 + 它自己），单文件上限 64 MiB（`DEFAULT_MAX_READ_BYTES`）；超限的文件跳过并记日志 |

## 影响

- 宿主与前端**零改动**：命令仍是 `note_move` / `note_rename`，DTO 不变，索引/搜索增量同步复用既有链路。
- `docs/architecture.md` §8 与 `README.md` 里"被移动文件自身正文里的相对链接不会跟着改写"那条限制
  已经不成立，待统一更新。
- `crates/mn-core/src/links.rs` 新增一个**只读**判定 `is_position_relative_target`（"这个目标随笔记
  位置变化吗"），与 `is_external` 并列；`crates/mn-index/src/rename.rs` 的模块文档与本文档一起，
  是"哪些形态会改、哪些放行"的唯一说明处。
- 正文改写的坐标系收敛到 `RewriteFrame`（`旧目录 → 新目录`），顺带修掉一处潜在缺陷：深目录里的
  自链接此前会按旧目录写成 `../../../归档/甲` 这种从新位置解析时**跑出 Vault 根**的路径。
