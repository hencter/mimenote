# ADR-0016：文件监听（Vault 外部改动的自动同步）

- 状态：已采纳
- 日期：M5

## 背景

"磁盘上的文件是唯一事实来源"（ADR-0002），但在此之前应用**从不主动看磁盘**：外部改动只有三条
被发现的路 —— 打开笔记时读盘、保存时的 mtime 冲突检测（ADR-0004）、用户手动 `Ctrl+Alt+R` 重扫。
对**单个文件**来说这够用（打开就看见了）；对"同步盘把别的设备的改动落下来"这种**批量、后台、
用户不在场**的改动则完全不够：文件树、链接、标签、搜索、图谱全都停在旧状态，直到用户想起来按重扫。

真实用法（用户的 Vault 在坚果云同步目录里）决定了这不是边角需求，而 M5 的清单里也一直挂着
"文件监听（`notify`）触发的增量"。

要回答四个问题：

1. 监听到的事件**怎么变成界面与索引的更新**？（重扫整库，还是按文件精细增量？）
2. **自己写的文件**怎么排除？（不然每保存一次就重扫一次，这是本块最容易做错的地方。）
3. 同步盘一次落几百个文件时怎么**不变成几百次重扫**？
4. 换 Vault / 关 Vault / Vault 被删掉时，监听怎么收场？

## 决策

### 1. 监听在**宿主**，不在 `mn-core` / `mn-index`

新增 `apps/desktop/src-tauri/src/watcher.rs`。`notify` 只加在宿主 crate（`[workspace.dependencies]`
登记、`src-tauri` 引用）。

理由：监听是**会话级的"外部世界信号"**，不是索引算法。索引是**可重建的纯派生数据**（ADR-0002/0008/0014），
它的输入应当是"条目表 + 文件内容"，而不是"操作系统事件"——把 `notify` 塞进 `mn-index` 会让那两层的
测试与可移植性都被一个平台相关的 IO 机制绑住，也让"换个监听实现"变成一件要动索引层的事。

### 2. 外部改动 = **去抖后整库重扫**，不做按文件精细增量

事件流 → 去抖合并（见决策 5）→ 推给前端一个 `mn://vault-changed` → 前端调用**既有的**
`vault_snapshot`（重扫条目表）→ 既有的 `indexer::spawn_build`（后台、可取消、增量复用）。

**为什么不在监听层里按文件增量更新索引**：

| | 按文件精细增量 | 整库去抖重扫（本 ADR） |
| --- | --- | --- |
| 新文件的路径解析（同名消歧、裸名链接、后缀解析） | 每条事件都要按索引规则重算一遍候选集 —— 就是 `mn-index` 里最容易出错的那部分 | 复用重扫后的条目表，解析口径与"打开 Vault"完全同一份 |
| 删除/改名 | 要区分"删了"还是"改了名"，而 `ReadDirectoryChangesW` 给的 rename 是两个独立事件（`From`/`To`），配不配对还要靠推测 | 重扫一次就对上了（条目表是权威） |
| 一次风暴 | N 个文件 N 次索引更新（N 次 FTS 事务） | 一次构建，且**没变的文件不读**（复用缓存库的 `(path, mtime, size)` 判定键） |
| 与其它路径的一致性 | 多出第二条"往索引里写东西"的路，越久越容易和全量构建漂移 | 只有一条路（`build_indexes`），不存在口径分叉 |

代价是**每次外部改动都要付一次重扫**。这笔账实测如下（1 万笔记 + 100 目录，本机 SSD，
release 构建，`cargo test -p mimenote --release -- --ignored --nocapture bench_watch_latency`）：

| 阶段 | 实测 |
| --- | --- |
| 落盘 → 事件推给前端（宿主侧判定） | **502 / 510 / 510 ms**（三轮；其中 500 ms 是去抖静默期，判定本身 2–10 ms） |
| → 条目表重扫（`scanner::scan`，页缓存热） | **107 ms** |
| → 索引重建完成（**复用**缓存库，1 万篇里只重读那 1 篇） | **105 ms**（复用 9999 篇） |
| **宿主侧端到端合计** | **≈ 714 ms** |
| → 前端重建条目表与树（`buildTree(10000)`，jsdom） | **11.7 ms** |
| 小 Vault（十几篇） | **≈ 0.51 s**（几乎全是静默期） |

作为对照：缓存库为空时的**首轮整库建索引**是 **5506 ms** —— 差 26 倍，正是 ADR-0008/0014
的复用判定键在这里兑付的价值。也就是说：**一次外部改动的成本 ≈ 0.5 s 静默期 + 0.2 s 后台 CPU**，
而且那 0.2 s 在 `spawn_blocking` 线程上发生，输入路径完全不受影响（构建可取消）。

监听自身的**常驻开销**（同一台机器，四个阶段各采样 18 次取平均；`idle → vault → watching → stopped`
是为了把"1 万条目的条目表"与"监听"分开）：

| 阶段 | 句柄 | 工作集 | 线程 |
| --- | --- | --- | --- |
| `idle` | 162.9 | 13.0 MB | 2 |
| `vault`（1 万条目的条目表，**无监听**） | 163.0 | 17.0 MB | 2 |
| `watching`（+ 监听） | **167.0** | 17.5 MB | **4** |
| `stopped`（停掉监听后） | 163.6 | 15.3 MB | 2 |

**监听本身的增量：4 个句柄、2 个线程、约 0.5 MB 工作集**（`ReadDirectoryChangesW` 的目录句柄
与其事件句柄 + `notify` 的读取线程 + 去抖线程）；`RecursiveMode::Recursive` 一次覆盖整棵树，
因此**不随文件数增长**。停掉之后句柄与线程都回到基线（工作集回落慢一点是分配器不还给系统的常态）——
这就是"副作用可逆"的实测形态。

### 3. "自己写的文件"用**条目表对账**排除，而不是靠时间窗或路径白名单

每一条事件都被问一句：**磁盘上的状态与条目表是否一致？**

- 一致（文件存在、`(mtime, size)` 与条目表相同；目录都是目录）→ 不是新闻，丢掉；
- 条目表里有、磁盘上没有 → 外部删除，是新闻；
- 条目表里没有、磁盘上有 → 外部新增，是新闻；
- 两边都没有 → 不是新闻（例如我们自己刚搬走/删掉的路径留下的 `From` 事件）。

为什么这一条同时解决了"自己写的文件不算外部改动"：**宿主每一次成功写入都会立刻更新条目表**
（`note_write` / `note_set_tags` / `note_create` / `note_rename` / `note_move` / `dir_*` /
`attachment_save` / `note_delete` 一律走 `VaultCtx::upsert` / `remove`），于是我们自己引起的事件到达时
（事件总在写入**之后**到达，而判定又在去抖窗口结束之后做），磁盘状态与条目表对得上 → 直接丢掉。

这条判据的三个好处：

1. **零额外记账**：不需要在每条写路径上加"我刚写了 X"的钩子（那些路径分散在 `commands.rs`、
   `attachments.rs`、`mn-index` 内部，加钩子既容易漏又容易腐化）；
2. **精确**：时间窗会连"用户刚保存完、别的设备立刻改同一个文件"一起吞掉；`(mtime, size)` 对账
   只吞掉"同毫秒 + 同字节数"的那种（与 ADR-0004 的令牌同一取舍，见代价表）；
3. **方向安全**：条目表是**宿主对磁盘的认知**，认知与磁盘不一致时宁可多扫一次，也不漏。

**判定放在去抖结束时做**（不是事件到达的瞬间）：宿主的写入是"先落盘、再更新条目表"，
若在事件到达那一刻判定，就可能与那次 `upsert` 撞在一起，把一次保存误判成外部改动。

### 4. 三类噪声在进队列前就被丢掉

| 噪声 | 为什么必须丢 |
| --- | --- |
| `.mimenote/` 之下的一切（缓存库、回收站、片段） | 缓存库**每轮构建都在写**（FTS5 落盘 + 链接/标签写穿透）。不丢它，重扫自己就会触发下一次重扫 |
| 原子写的临时文件（`mn_core::atomic::TEMP_PREFIX` = `.mimenote-`） | 每一次保存/新建/附件落盘都会在同目录先写 `.mimenote-xxxx.tmp` 再 rename —— 它是实现细节，`.mimenote-*.tmp` 一律不是新闻 |
| 扫描器本来就跳过的路径（`.git`、`node_modules`、隐藏项、`Thumbs.db`……） | 它们永远进不了条目表，重扫也看不见它们。**不挡掉的话，一次 `git fetch` / `pnpm install` 就会换来一堆重扫**（口径直接复用 `ScanOptions`，不另立一份忽略名单） |

另外：`EventKind::Access(_)` 一律忽略。**读文件不是改动** —— 少了这一条，重扫自己（读全库文件）
就会触发下一轮重扫，形成死循环。

### 5. 去抖 + 合并：静默期 500 ms，硬上限 2 s

`Debouncer`（纯逻辑，时钟由调用方注入 → 可以确定性地单测）：

- **静默期 500 ms**：最后一次事件之后安静 500 ms 才刷新。小改动因此有 0.5 s 的可感延迟，
  而同步盘一次落几百个文件只会产生**一次**刷新；
- **硬上限 2 s**：从第一条事件算起最多等 2 s —— 否则"另一个程序正在慢慢写一个大文件"
  会让刷新永远推迟下去；
- **路径去重**：同一路径重复出现只留一条；报文里最多带 **256** 条路径
  （`truncated` 标记是否截断），条数如实放在 `changes` 里。

**前端为什么不需要那张路径表**：判断"当前笔记要不要重载"用的是**重扫回来的 mtime**与文档的
版本令牌比对（`entries[i].mtimeMs === doc.baseMtimeMs` → 没变）。mtime 比对在任何规模下都成立，
也不会因为路径表截断而漏判。

### 6. 生命周期挂在 Vault 上下文上：`set_vault` / `clear_vault`

`AppState::set_vault` 是"当前 Vault 换了一个"的唯一入口（打开新 Vault 与重扫都会走到它），
因此监听的启停就放在那里：

- **换根** → 停旧监听（置停止标记 → 放开 OS 句柄 → join 去抖线程）+ 起新监听；
- **同一个根**（重扫：`vault_snapshot` 也会 `set_vault`）→ **原样保留**。重启会留下一个
  "事件无人接收"的窗口，重扫越频繁丢的事件越多；
- **`clear_vault`（关闭 Vault）** → 停监听。`WatcherHandle` 还实现了 `Drop`，句柄被丢掉时
  监听一定跟着停（架构 §2 规则 6：副作用可逆）。

去抖线程持有会话状态靠的是**启动时登记的 `Weak<AppState>`**（`lib.rs` 的 setup 里接线）：
`set_vault` 只有 `&self`，拿不到 `Arc`；用 `Weak` 而不是 `Arc`，监听线程也不会让会话状态永远活着。
事件出口抽成 `EventSink` trait —— 生产环境是 `TauriSink`（`AppHandle::emit`），测试里是一个
把载荷塞进 channel 的回调，**watcher 本身不知道 Tauri 的存在**，因此它的行为可以在真实临时目录上测。

### 7. 契约：一个事件，载荷里没有"必须做什么"

事件名 `mn://vault-changed`（与 `mn://index-status` 同一风格），载荷：

```jsonc
{
  "paths": ["笔记/甲.md"],   // 被判为外部改动的相对路径（字典序，最多 256 条）
  "truncated": false,        // 路径表是否被上限截断
  "changes": 1,              // 去抖窗口里收到多少条事件路径（含重复）
  "detectedAtMs": 1736300000000
}
```

**不新增 IPC 命令**：重扫走既有的 `vault_snapshot`，"当前笔记怎么办"由前端现有状态机决定。
事件只回答"磁盘上有新闻"，不指挥接收方做什么 —— 这是"事件 vs 命令"的边界，也让
"手动重扫"和"自动重扫"共用同一条链路。

前端侧（`state/vault-store.ts` 的 `subscribeVaultChanges` / `applyExternalChange`）：
静默重扫（不弹"已重扫"提示：同步盘可能每分钟都在落文件，那是噪音）→ 然后把决策交给
`note-store.applyExternalChange`：

| 当前笔记 | 行为 |
| --- | --- |
| 磁盘没变（mtime 与令牌一致） | 什么都不做（连 `revision` 都不动） |
| 变了，且**没有**未保存修改 | 从磁盘重新加载（`revision` 自增 → 编辑器整篇替换），提示"已在磁盘上更新，已重新加载" |
| 变了，且**有**未保存修改 | 进入**既有的冲突态**（顶部横幅 + 由用户选"覆盖 / 重新加载"）——绝不自动覆盖，也绝不静默丢弃 |
| 磁盘上已经不在了 | 只提示"已被删除或移动"，不假装重新加载成功 |

### 8. 浏览器预览模式优雅缺席

`pnpm dev` 下没有 Tauri 事件系统：订阅失败只记一条 `console.debug`，功能整体缺席
（与 `subscribeIndexStatus` 同一姿态）。守卫在宿主侧：没有事件出口时 `set_vault` 干脆不启动监听。

## 代价与已知限制

| 项 | 说明 |
| --- | --- |
| 每次外部改动付一次重扫 | 1 万文件约 **0.4–0.5 s** 后台 CPU（扫描 143 ms + 索引复用构建 0.26–0.31 s）。这是"不做按文件精细增量"的直接代价，见决策 2 |
| 判定键只有 `(mtime, size)` | **同一毫秒内且字节数相同**的外部改动会被漏判（与 ADR-0004 的版本令牌、ADR-0014 的索引复用同一取舍；要兜住得引入内容哈希，属 M5） |
| 条目表被截断时（`max_entries`，默认 20 万条）超出的路径 | 它们不在条目表里，因此每次事件都算"新闻" → 每次事件一次重扫。超大 Vault 下这是"能看见变化"与"重扫成本"之间的取舍 |
| **应用自己改名/搬迁时的链接改写**会多触发一次重扫 | `note_rename` / `dir_*` 改写了**别的文件**（`updated_links`），而条目表只更新被改名的那一条，被改写文件的 mtime 在条目表里是旧的 → 看起来像外部改动 → 一次多余的重扫（不弹提示，用户无感，成本同上一行）。根因在 `commands.rs` 的收尾只换一条，修它超出本轮的改动范围（见"影响"） |
| 同步盘中转文件 | 坚果云/OneDrive 的临时文件（`.goutputstream-*`、`*.tmp`、冲突副本 `xxx (冲突副本).md`）大多以 `.` 开头或本身就是要同步过来的正常文件：前者被"隐藏项"规则挡掉，后者**会**被当成新增（这正是用户期待的"同步下来了"）。真正的中转文件若既不隐藏也不在忽略名单里，会换来一次（去抖合并后的）重扫 |
| 网络盘 / UNC 路径 | `ReadDirectoryChangesW` 在 SMB 上语义与本地不同（对端不保证事件完整性，部分 NAS 干脆不发通知）；此时行为退化为"可能要等下一次手工重扫"，**不会**报错。`notify` 对这类场景的兜底选项（`PollWatcher`）本轮没有启用 |
| 监听句柄上限 | 每打开一个 Vault 只占**一个**目录句柄（`RecursiveMode::Recursive` 一次覆盖整棵树），因此不随文件数增长。系统句柄耗尽/监视器数量上限（Windows 上的 paging pool 约束）在 1 万文件量级不是问题；多个 Vault 同时打开的场景本轮不存在（一次只开一个） |
| `notify` 在 Windows 上的已知怪癖 | ① 改名是**两个独立事件**（`From` / `To`），本 ADR 的判定不依赖它们配对；② 目录被整个删掉/搬走时回调可能收到 `Err`，一律记日志忽略，**绝不上抛**；③ 事件可能重复投递（同一路径多次 `Modify(Data)`），去重与合并都在 `Debouncer` 里做；④ 缓冲区溢出时事件会丢（`notify` 记 warn），丢的那一次靠下一次重扫补齐 —— 而"下一次"可能是用户按重扫，因此**监听不是唯一的真相来源**，只是加速器 |
| 链接面板/标签面板不会立刻刷新 | 索引在后台重建（图谱与搜索是索引驱动的，会自己跟上），但"当前笔记的反链面板"仍要等它自己的刷新时机（切笔记 / 保存 / 图谱刷新）。本轮没有为它加一条"索引就绪 → 刷新面板"的订阅 |
| 监听失败 = 静默降级 | 起不来只记一条 warn，打开 Vault 照常成功，手动重扫（`Ctrl+Alt+R`）仍然是兜底 |

## 影响

- 新增 `apps/desktop/src-tauri/src/watcher.rs`（事件判定、去抖、句柄、生命周期）与
  `src-tauri/src/state.rs` 的接线（`set_vault` / `clear_vault` / `attach_runtime` /
  `is_watching`）、`lib.rs` 的 setup（接上 `TauriSink` 与 `Weak<AppState>`）；
- 新依赖 `notify 8`（**只给宿主 crate**；理由与替代方案见 `docs/dependencies.md`），
  `docs/architecture.md` §3.1 的事件行、§6 性能表、§8 已知限制同步更新；
- 前端：`state/vault-store.ts` 新增 `VAULT_CHANGED_EVENT` / `VaultChanged` /
  `applyExternalChange` / `subscribeVaultChanges`，`state/note-store.ts` 新增
  `applyExternalChange`（并让 `reload` 支持 `silent`），`App.tsx` 挂一次订阅；
- **没有**新增 IPC 命令、**没有**新增错误码、**没有**动 `mn-core` / `mn-index`
  （监听层把它们当作被使用的库，一点都不知道自己被人监听）；
- 测试：`watcher.rs` 内的纯逻辑单测（路径换算/过滤/去抖合并）+ **真实临时目录 + 真实 watcher**
  的宿主测试（外部新增与改写被上报、**自己的原子写不触发**、`.mimenote/` 与临时文件不触发、
  换 Vault 停旧监听、重扫不重启监听、闭库停监听、**Vault 目录被删掉时线程不 panic**）、
  前端 store 集成测试（事件 → 条目表刷新、无脏自动重载、有脏进冲突）、应用层 E2E 追加两条
  （外部新建出现在文件树、当前笔记被外部改写后自动重载且磁盘不被覆盖）。

### 后续（本轮刻意不做）

- **按文件精细增量**（决策 2 的另一条路）：它需要把"新文件的路径解析"从全量构建里抽出来，
  是一个独立的设计题（等于给索引加一条"单文件入口"，而消歧规则必须与全量构建逐字一致）；
- 条目表收尾对"被改写文件"的补齐（代价表中的那一行）—— 修它要动 `commands.rs` 的
  `apply_renamed_entry` / `apply_renamed_dir`，本轮改动范围不允许；
- 内容哈希作为二级令牌（ADR-0004 的既有待办，兑付后本 ADR 的"同毫秒漏判"一并消失）；
