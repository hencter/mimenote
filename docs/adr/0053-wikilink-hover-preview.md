# ADR-0053：`[[链接]]` 的悬停预览

- 状态：已采纳（已交付）
- 日期：v0.3.0 之后（用户诉求："编辑器里 `[[链接]]` 的 Obsidian 式悬停预览"）
- 相关：ADR-0009（所见即所得 / 装饰层）、ADR-0030（显示名不带 `.md`）、
  ADR-0035（容器切割树）、ADR-0049（一格一个编辑器）、ADR-0046（图谱浮窗那套"浮层"纪律）

> 编号说明：本任务原本指定 `0052`，但 `docs/adr/0052-tapered-edges-and-bundles.md`
> 已被同一批的另一项工作占用（图谱连线那一轮），因此顺延到 **0053**。

## 背景

`[[设计]]` 在编辑器里只是四个字。读的时候想知道"那篇里写了什么"再决定要不要跳过去，
而点一下的代价是**丢掉当前位置**（跳走之后还得找回来，滚动位置与光标都变了）。
Obsidian 的解法是：鼠标停在链接上短暂停留，弹一张只读小卡片。

这件事一直挂在"用户早前提过、仍未做"的清单上（`docs/handoff.md`）。它能被做出来的前提
是仓库里已经有三件现成的东西：

1. 装饰层（Live Preview）已经在每个 `[[…]]` 上写了 `data-mn-wikilink`
   （值就是 `splitWikilink` 解析出来的目标），并且已经算过"这个目标解析到哪一篇"；
2. `StaticNotePreview` 提供了**只读渲染任意一篇笔记**的唯一那条链路
   （图谱浮窗与非当前分栏的叶子都在用它）；
3. `links-store` 里有宿主索引给出的出链（`ResolvedLink`，含 `resolvedRelPath` 与
   `ambiguous`）。

## 决策

### 1. 命中判据只有一份：读装饰 + 读出链，不在悬停层重新解析 Markdown

卡片只弹在"鼠标底下有 `[data-mn-wikilink]`"的地方 —— 这一条把
`[[别名|目标]]`、`![[嵌入]]`、代码块/frontmatter 里的假链接、被表格 widget 接管的单元格
**全部**天然对齐编辑器（那些地方根本没有这条属性）。

"目标是谁"读 `links-store` 的出链，用 `normalizeLinkTarget` 匹配
（`domain/links.ts`，与阅读视图、与点击处理器同一套口径）。
刻意**不读**装饰上的 `data-mn-resolved`：装饰是"算的那一刻"的快照，
而 store 里的可能刚被索引刷新过。悬停预览不弹卡片没有后果，宁可等索引，
也不弹一篇指错笔记的正文。（点击处理器两个都看，是因为那里"点了没反应"有后果。）

### 2. 悬空链接**不弹**

`resolvedRelPath === null` 时根本不进入延迟。弹一张空卡片比不弹更糟：
用户会以为那篇笔记是空的，而链接的语义恰恰相反（"点击即创建"）。
这条也让 `![[图.png]]` 一类附件目标自动被挡掉（`isMarkdown` 再兜一道）。

### 3. 延迟 220ms、宽限 120ms

- **延迟不是 0**：鼠标扫过一行时会连续命中好几个链接，0 延迟的表现是"卡片跟着指针一路闪"，
  比不弹更烦。220ms 落在"看起来是停留、而不是路过"的那一段里；
- **宽限是为"从链接走到卡片"留的**：两者之间隔着几像素，指针一定会经过一段不在链接上的
  空隙。若命不中链接就立刻收起，卡片会在这段空隙里被关掉 —— 用户永远滚不动它。
  真正的判据是 `mouseleave` 的 `relatedTarget`：指向卡片就留住（卡片是 `.cm-editor`
  的孩子，指针进卡片之后内容区再也收不到 `mousemove`，这条路只能靠 `relatedTarget` 兜）。

### 4. 卡片复用 `StaticNotePreview`，只读、不写盘、不进标签页

卡片是"浮在正文上的一小块界面"，正文走唯一那条渲染链路（`ipc.noteRead` →
`renderMarkdown(frontmatterBody(text))` → DOMPurify 净化 → 出链表补 wikilink 标注）。
显示名走 `domain/paths.ts` 的 `displayName`（不带 `.md`），全路径退到 `title` 提示里
（ADR-0030 的口径）。它**不能**打开笔记、不能写盘、不进标签页 ——
与图谱浮窗同一条纪律；卡片里真正的"活"只有正文里的链接可点（那是 `StaticNotePreview`
现成的行为，走完整的打开流程）。

### 5. 位置夹在编辑器面板内，翻到另一侧而不是被裁掉

默认贴链接**下方**（不挡光标所在那一行 —— 那一行正是用户正在读的）；下方放不下且上方更宽裕
就翻到上方；右边放不下就贴右缘；面板比卡片还窄时贴左缘（左上角永远可见）。
高度取"面板里剩多少就多少"，卡片自己滚动，绝不把面板撑出一条滚动条。

### 6. 滚动 / 文档变更 / 失焦 / `Esc` / 点击别处都收起

- **滚动（`geometryChanged`）收起，不跟着挪**：卡片锚在一个随文档滚动的位置上，
  跟着挪意味着每一帧重新夹取（贴着面板边缘时会左右横跳），而"滚动时还留着浮层"
  本来就会挡住用户正在找的地方。代价：做不到"边滚边看预览"，那件事该用分栏；
- **文档变更之后重新判定**用的是**视图把新状态画进 DOM 之后**的钩子（`docViewUpdate`），
  不是 `update`：`update` 跑在 DOM 更新之前，那一刻旧装饰还在原地，走它会得出
  "卡片还好好的"这种假结论（真实踩过：删掉 `[[` 之后卡片留在屏幕上）。
  判据是"那个 `<span data-mn-wikilink>` 还在不在、目标属性还是不是原来那个"。

### 7. 事件全部挂在编辑器自己的 DOM 上

监听走 `ViewPlugin` 的 `eventHandlers`（CodeMirror 自己挂在**内容区**上、随插件销毁摘掉），
**没有一处 `document` / `window` 级监听**。于是同屏多个编辑器（ADR-0049 之后是常态）时，
只有指针真正所在的那个实例会收到 `mousemove` —— "卡片弹在别的格子里"在结构上不可能发生。
处理器一律返回 `void`（不吃事件）：选词、拖放、点击跳转的字面行为一个都没改。

## 代价与已知边界

1. **卡片是多出来的一棵 React 树**：每次弹出/收起各一次 `createRoot` / `unmount`
   （用 `flushSync` 同步落地，否则第一帧定位没有尺寸可夹）。悬停不是按键路径，代价可接受；
   但**不要**把它改成"常驻挂载 + 切换显隐"以外的东西之前先读这一段；
2. **卡片里的文字拖不进编辑器**：卡片的 mousedown 在卡片自己被截住（否则点卡片正文会
   让编辑器失焦、光标跳走、`[[` 露原文的观感当场变化）。这是刻意的取舍；
3. **"快速扫过"的判据在 jsdom 里只能靠假定时器**：真定时器下只能用"猜一个比延迟短的等待"
   表达，机器一忙就假红。因此那两条用例显式 `vi.useFakeTimers()`，并且**在假定时器窗口里
   只让出微任务**（等被假掉的 `setTimeout` 会死锁 —— 真实踩过一次 20s 超时）；
4. **卡片宽度与最大高度是"JS 一份、CSS 一份"**：夹取必须提前知道尺寸，而 `offsetWidth`
   在卡片刚挂上去的那一帧不可靠。两份数字里只有**高度下限**能与 CSS 成对钉住
   （`tests/wiki-hover.test.tsx` 的样式契约用例），宽度只由 JS 写进行内样式；
5. **多个编辑器同屏时卡片各自独立**：鼠标在哪一个编辑器上就由哪一个弹，同一时刻不会只有
   一张（用户把鼠标从 A 格移到 B 格，A 会先收到 `mouseleave` 收起，B 再延迟弹出）；
6. **卡片不跟随主题之外的任何设置**：它的字号跟阅读视图那一档
   （`--mn-font-size-reading`，没设置时回落到编辑器字号），刻意不做单独的设置项 ——
   悬停预览是"瞥一眼"，多一个可调项只是多一个要维护的东西。
