# ADR-0041：内容哈希二级令牌（M5 起步）

- 状态：已采纳（第一批已交付）
- 日期：M4/M5 并行开工（v0.2.0 之后）
- 相关：ADR-0002（索引可重建）、ADR-0004（mtime 版本令牌）、ADR-0008「后续修订」
  （跨会话增量复用）、ADR-0014（落盘索引）、ADR-0016（文件监听）

## 背景

跨会话增量复用的判定键是 `(path, mtime_ms, size)`：打开时对得上就一个文件都不读
（整轮打开 9.8s → 0.3s，约 30×）。代价是漏检窗口 —— **同一毫秒内、字节数又完全相同**
的内容改动会被判成"没变"（ADR-0008 已如实记录，`persisted_index.rs` 里甚至有一条
测试专门证明"复用路径一个文件都没读"）。M5 的任务就是收窄这个窗口，但不能把 30×
加速交回去。

## 决策

### 1. 哈希算法：FNV-1a 64（`mn-core::content_hash`）

- **零新依赖**、值跨版本稳定（`std` 的 `DefaultHasher` 明确不保证稳定性，不能落盘）；
- 只是**缓存用途**的二级令牌（索引可重建，碰撞最坏是"这次没发现"，下次 mtime 变化仍会重建），
  不做安全边界；
- 写入时免费：构建与保存路径手上本来就有全文，一次 O(文本) 内存遍历相对分词/落盘可忽略。

### 2. 落盘：`notes_meta` 加 `content_hash` 列（schema v3 → v4）

- `add_note_with_meta` 在写行**同一个事务**里记下正文哈希（ADR-0008 的不变量：
  落盘数据与判定键同一事务，不存在"内容新、键旧"的中间态）；
- 版本不符直接重建（缓存而已）：老用户升级后付出**一次**全量重建；
- 对账（`plan_incremental`）的复用判决**仍然只看 `(mtime, size)`** —— 把哈希放进判决
  等于每次打开全量读文件，30× 加速直接作废。哈希只在"手上已经有文本"的地方用。

### 3. 顺手修复：`note_read` 打开时校验（`commands/notes.rs`）

读笔记的路径本来就要读全文：读完后算一次哈希，与库里比对，对不上就地
`indexer::update_note`（内存链接索引 + 全文搜索整篇重写）。正常打开只多一次
SELECT；只在真正漏检时才多一次单篇重写。于是"外部同毫秒改动"的存活期从"下一次
mtime 变化"缩短到"下一次打开这篇笔记"。

### 4. 写穿透路径本来就是安全的

`upsert_note` / `IndexStore::replace_note` 在不知道新 mtime/size 时**删掉判定键行**
（"不知道"只能表达成"下一篇必须重读"），哈希列跟着一起删，无需额外处理。

## 代价与剩余窗口

1. **打开时的复用快路径仍然信任元数据**：从不打开的笔记若被外部同毫秒改写，
   索引里仍是旧内容，直到它被打开（本批修好）或 mtime 变化。彻底关闭需要"复用前全量读文件
   验哈希"（= 放弃 30×）或后台采样校验 —— 留待 M5 后续，后者不阻塞输入才能做；
2. `note_read` 修复只管**搜索 + 链接内存索引**（`update_note` 同步的两半），
   图谱是它们的只读投影，自动跟上；
3. 新增测试：哈希向量与稳定性（`mn-core` 4 条）、落盘与同字节检出
  （`search.rs` 1 条）；既有"快路径不读文件"证明测试保持原样（它现在刻画的是
   "打开那一刻"的行为，修复发生在"打开笔记"那一刻）。
