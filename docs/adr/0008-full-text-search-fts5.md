# ADR-0008：全文搜索用 SQLite FTS5，中文逐字分词、external content 换行号

- 状态：已采纳
- 日期：M2

## 背景

M2 要给 1 万笔记量级的 Vault 加全文搜索。要求：**离线**（运行时无出站请求）、**不要求用户额外安装东西**、
索引是**可重建的派生数据**（ADR-0002）、中文必须能搜（这是主要使用场景）。

自然语言全文检索要同时解决分词、倒排索引、相关性排序、增量更新四件事 —— 自己写等于把半个数据库塞进应用。

## 决策

### 1. SQLite FTS5，静态编进二进制（`rusqlite` + `bundled`）

理由与许可证见 `docs/dependencies.md`：`bundled` 把 SQLite 源码编进可执行文件，因此**不依赖系统 `sqlite3.dll`**、
也保证 FTS5 一定可用（系统库是否编译了 FTS5 不可控）。

### 2. 行表 + FTS5 external content：为了"排名之后还能拿到行号"

```sql
lines(id, rel_path, line, text, indexed_text)                     -- 行表（含原文与"分词后"文本）
lines_fts USING fts5(indexed_text, content='lines', content_rowid='id', tokenize='unicode61 remove_diacritics 2')
```

`content='lines'` 让 FTS 表不重复存原文，而 `bm25()` 排完序可以 `JOIN lines` 拿回 **`rel_path` 与 `line`**——
这正是 IPC 契约里 `SearchHit { relPath, line, snippet, score }` 需要的。若只用 FTS5 自带的 `snippet()`，
拿到的是带标记的片段而不是"第几行"，前端就没法展示行号。

### 3. 中文**逐字**分词（`space_cjk`），索引与查询两侧同口径

FTS5 的 `unicode61` 把一整串汉字当作**一个 token**：那样"今天天气很好"里永远搜不到"天气"。
因此入库与查询两侧都用同一个函数把 CJK 逐字切开（`今天天气` → `今 天 天 气`），中文查询于是变成
**相邻字短语匹配**（`天气` → `"天 气"`），语义上等价于子串检索，`今好` 不会命中。

- 代价：token 数与索引体积成正比（实测中文库索引约为被索引文本的 **2.7 倍**，1 万笔记 / 29.1 万行 ≈ 114.7 MB）；
- 如果将来 vault 的中文正文到几百 MB，索引会到 GB 量级，届时需要考虑词典分词或双字词粒度 ——
  这属于 M5 的规模问题，README/architecture 已记为已知限制。

### 4. 用户输入按**自然文本**处理，绝不让它变成 FTS 语法

每个词包进双引号（内部 `"` → `""`）、词尾加前缀 `*`，按空白切词、丢掉不含字母数字的词，最多 16 词 / 每词 64 字符。
`a"b(c)`、`-x`、`OR`、`NEAR`、`*`、`(`、`)`、`^`、`:`、`""`、500 字长串都有测试，**一律不报错**（`OR` 当普通词）。
前端另有 150ms 防抖 + 请求序号竞态丢弃、空查询不发 IPC。

### 5. 构建期间放宽持久化，用**自愈**兜底

批量写几十万行时，默认的 `journal_mode=DELETE` + `synchronous=FULL` 要多花好几秒。
构建期间用 `journal_mode=MEMORY` + `synchronous=OFF` + 32MB 页缓存，构建末尾 `optimize` 合并段。

**代价**：构建中途断电可能留下**坏库**。处理方式是 `SearchIndex::open` **自愈** —— 库**真的损坏**时
删掉重建（ADR-0002：索引是派生数据，删掉可从文件重建）。这是本 ADR 里唯一一处"用可靠性换速度"的
取舍，且被限定在**可重建的缓存**上，不碰用户数据。

> 修订（见文末「后续修订」）：自愈的判定后来收窄成"按 SQLite 错误码只认真损坏"。
> 锁冲突、磁盘满、只读一律原样返回给调用方降级 —— 曾经它们都被当成"库坏了"而删掉健康缓存。

### 6. 索引更新与链接/标签**同源**，不额外读文件

`build_indexes` 在**同一遍扫描**里顺带建 FTS（可取消、`spawn_blocking`）；增量更新挂在既有的
`update_note` / `remove_note` / `rename_note` 上。搜索**不索引非笔记**，`.mimenote/**` 也不进索引。

## 代价与已知限制

| 项 | 实测 / 说明 |
| --- | --- |
| 查询延迟 | 真实查询（命中约 100）**3 ms**；命中 1000 行 **66–79 ms**；命中 29 万行（每行都含查询词）**0.9–1.2 s**。慢的那档是 `bm25()` 给全部命中打分 + JOIN 回行表 + 三键排序，占约 90%；已实测 `CROSS JOIN` / `CTE+LIMIT` / 去 `ORDER BY` / 大页缓存 / `mmap` 五个变体**都在同一量级**，没有便宜的优化空间 |
| 索引体积 | ≈ 被索引文本的 2.7 倍（中文逐字 token） |
| 每次打开 Vault 整库重建 | ✅ 已修（见「后续修订」）：按 `(path, mtime_ms, size)` 复用缓存 —— Vault 没变时**搜索这一路 4.7–5.0 s → 0.17–0.23 s**，整轮「打开 Vault」9.4–9.7 s → 4.7–5.3 s。**链接+标签仍是内存全量重建**（≈ 4.9 s，读全库文件这件事没省） |
| 连接串行化 | `Connection` 非 `Sync`，查询走 `Mutex` → 并发查询排队（每条 ms 级） |
| 构建期 race | 后台构建完成时按"扫描时捕获的 entries"整份替换索引，构建窗口内的保存/改名/删除可能在索引里丢失（链接索引既有行为，未修） |
| 索引不可用时的降级 | Vault 只读/建库失败 → 记 warn、状态置 `Failed(原因)`、**应用照常启动**，`search_query` 返回 `IO` + 中文原因；构建中 → 同样返回 `IO`（前端据此提示"索引构建中"而不是报错） |

## 影响

- 索引层（`mn-index`）独占 SQLite 依赖；宿主只负责"打开/安装/降级"与查询搬运，IPC 契约与前端不受实现影响。
- 前端搜索面板是命令面板的**第三个模式**（`Ctrl+Shift+F`），异步查询 + 竞态丢弃；
  **回车不跳命中行**（编辑器还没有"定位到某行"的入口，要接应由 editor 侧提供 `openAt(relPath, line)`）。

## 后续修订：跨会话增量复用与锁安全（M5「增量索引」的第一块）

第 5 节那套"每次打开先删库 + 自愈"在真实 Vault（3985 篇笔记）上暴露成两个问题：**打开 Vault 要重建
十几秒**，而绝大多数打开时 Vault 一个字节都没变；以及**并发打开时健康缓存被误删**。这一节记录修订。

### 1. 打开 Vault 不再整库重建：按 `(path, mtime_ms, size)` 复用

- 缓存库新增 `notes_meta(path PRIMARY KEY, mtime_ms, size)`：写行的**同一个事务**里记下文件元数据
  （判定键与 ADR-0004 的 mtime 版本令牌同一口径 —— `mtime` 不可得时一律判为"要重读"，绝不当成"没变"）。
- 打开时先对账（`SearchIndex::plan_incremental`）：`changed`（新增 / 改动 / mtime 不可得）重写、
  `removed`（库里还有、这次扫描已经没有了）删掉，其余**原样留用**。
- **全库命中且无删除时，索引表一个字节都不动**：不开事务、不 `begin_rebuild`、不 `rebuild`、不 `optimize`
  （有测试用 SQLite 的 `data_version` 钉住这一点）。只有"一篇都留不住"（首次构建、schema 升级后、
  库与文件对不上）才走整库重建；增量写入走 `begin_incremental` + 逐篇 `add_note_with_meta` + `COMMIT`，
  FTS 由 external content 的既有约定按行维护（删除发 `'delete'`）—— 刻意不 `optimize`：它要为整个
  索引合并段，几百 MB 的库上本身就是秒级成本，正是这一轮要省掉的东西。
- `SCHEMA_VERSION` 1 → 2，老库直接重建（既有行为）。**索引口径的任何变化（分词、哪些行进索引、
  大小上限）也必须 +1**：增量复用会信任库里已有的行。
- 实测（1 万笔记 / 30.1 万行 / 缓存库 115 MB，两次运行）：搜索这一路 **4.7–5.0 s → 0.17–0.23 s**，
  整轮「打开 Vault」**9.4–9.7 s → 4.7–5.3 s**（剩下的全是链接/标签的内存索引 ≈ 4.9 s）；
  改 1 篇时只重写那 1 篇（搜索这一路 ≈ 0.19 s）。
- **漏检边界**：判定键只有毫秒 mtime 与字节数，**同一毫秒内、字节数又完全相同**的内容改动会被判成
  "没变"。与 ADR-0004 的冲突检测是同一个取舍，内容级校验要引入哈希（M5 再做）。
- **仍然全量重建的部分**：链接索引与标签索引是内存索引（不落盘），每轮打开都要读全库文件
  （1 万笔记 ≈ 4.9 s）。要让它们也受益，得把链接/标签也落盘（`lines` 表里其实已经存了每行原文，
  可以当数据源），那是独立的一块，没在本轮做。
- 对账本身的成本：每轮打开要顺着 `lines_by_path` 扫一遍路径集合（1 万笔记 ≈ 0.15 s，换"删除检测
  精确"这一点，见 `SELECT_INDEXED_PATHS` 的注释），相对整轮 4.7 s 可忽略。

### 2. 自愈只认"真损坏"，锁冲突不再删库

原实现是"打开失败就删库重建"。dev 下 React StrictMode 会把 `vault_open` 跑两次 → 两个构建并发 →
其中一个的 `PRAGMA journal_mode = WAL`（要取写锁）撞上另一个持有的锁 → `SQLITE_BUSY`
（`database is locked`）被当成"库坏了" → **一个完全健康的缓存被删掉，用户白等一次十几秒的重建**。

修订后：

- 连接建立后**立刻**设 `busy_timeout = 2000ms`，任何会取写锁的 PRAGMA（`journal_mode = WAL`）都在其后：
  瞬时锁冲突先等，而不是立刻变成"库不可用"；
- 自愈**按 SQLite 错误码分类**：只有 `SQLITE_CORRUPT` / `SQLITE_NOTADB`（以及 `SQLITE_IOERR`
  且文件头不是 `SQLite format 3\0`）才删库重建；`SQLITE_BUSY`/`SQLITE_LOCKED`、`SQLITE_FULL`、
  `SQLITE_READONLY`/`SQLITE_CANTOPEN` 一律**原样返回**给调用方降级（warn + `search_query` 返回 `IO`）。
  自愈日志记下**原来的错误**与**删了哪些文件**；
- 宿主（`indexer::spawn_build` + `AppState` 的构建互斥量）**串行化构建**：后到的构建等前一轮退出
  （前一轮已被取消，最多再读一个文件），两个构建因此不会同时写同一个缓存库。
  `index_status` 的语义（`idle`/`building`/`ready`/`cancelled`/`failed`）不变。

### 3. 实测：真实 Vault 的缓存库体积与"它躺在同步盘里"这件事

拿一个**真实的重度 Vault** 量过（作者本人的笔记库：4267 篇 `.md`、**501606 行**，位于坚果云同步目录内，
只用只读连接 `mode=ro` 体检，未改动数据）：

| 项 | 实测 |
| --- | --- |
| `search.db` 文件大小 | **207.4 MB**（页 4096B × 53086 页，其中空闲页 1108 ≈ 4.5 MB） |
| `lines` 行数 | **501 606**（与"行"一一对应，正文文本合计仅 **22.1 MB**） |
| FTS5 结构 | `lines_fts` 是 **external content**（`content='lines'`）—— 文本**没有**被存两份 |
| FTS5 内部表 | `lines_fts_data` 7326 块、`lines_fts_idx` 2669 段、`lines_fts_docsize` **501 606 行** |

也就是说：体积主要来自"**把索引建在行上**"（50 万个文档）与 FTS5 默认的 `detail=full` 位置表，
而不是文本本身。这符合决策 2 的取舍（行是唯一能"排名之后还能拿到行号"的单位），
但它带来两个**运维层面**的后果，值得写下来：

1. **缓存库在 Vault 内**（`.mimenote/cache/`）：如果 Vault 在同步盘里，同步客户端会把它当成
   一份 200 MB 级的文件反复上传（坚果云确实会同步 `.obsidian/` 这类隐藏目录，本项目实测库里
   出现过它的 `*.sync-conflict-*.json`）。**建议在同步客户端里排除 `.mimenote/`** ——
   它是**可丢弃的派生数据**（删掉下次打开自动重建），把排除掉它的代价说清楚比让用户猜要诚实。
   应用侧不受影响：扫描器与文件监听都跳过 `.mimenote/`（ADR-0016 决策 4）。
2. **进一步缩小的方向**（本轮**未做**，留给 M5 的收尾）：`detail=none`/`column` 可以砍掉位置表，
   代价是**短语查询与 NEAR 失效**（`space_cjk` 逐字分词下，短语查询是"精确短语"的唯一手段，
   不是可有可无的装饰）；或者把索引单位从"行"改成"篇 + 行内定位表"，但那会动"排名后取行号"
   这条既有的实现主线，属于独立设计题。

### 4. 实测：段合并（`optimize`）买的是**查询速度**，不是磁盘

上面那条体检里有个**被证伪的猜测**值得写下来，因为它太容易复发：真实库 207 MB、`lines_fts_idx`
有 2669 行，我一开始读成"2669 个段，段膨胀撑大了库"。只读复查后：`SELECT count(DISTINCT segid)`
= **1** —— 2669 是"段 × 词"的条目数，而全量重建（`finish_rebuild`）本来就带一次 `optimize`。
**库大是因为索引建在行上（50 万个文档），不是因为有墓碑。**

但顺着这个疑问量了增量路径（`bench_optimize_after_incremental`，1 万篇 / 30 万行 / release）：

| 阶段 | 段数 | 查询平均 |
| --- | --- | --- |
| 全量重建后 | 1 | 62.2 ms |
| 5 轮增量（每轮 200 篇）后 | 16 | 63.5 ms |
| 10 轮 | 11 | 74.5 ms |
| 15 轮 | 18 | 75.0 ms |
| 20 轮 | 11 | 75.6 ms |
| `optimize` 之后 | **1** | **45.8 ms** |

两条结论：

1. **段数不会无限增长**（automerge 把它稳定在 11–18 附近），但它稳定在一个**查询更慢**的布局上 ——
   合并成 1 个段后查询快 **1.68×**（另一批次 82.8 → 37.3 ms，即 2.2×），代价是一次 876–937 ms
   的全库重写；
2. **文件大小一个字节都没变**（118.5 MB → 118.5 MB）：SQLite 把释放的页留在 freelist，
   文件不缩。所以"合并能省磁盘"是错的，"合并能让搜索更快"是对的。

因此把 [`SearchIndex::finish_incremental`] 从"刻意不做 optimize"改成"**按段数触发**"：
段数 ≥ `OPTIMIZE_SEGMENT_THRESHOLD`（8）就合并一次，否则一个字节都不动；合并失败只记 warn
（它是加速器，不是正确性的前提）。判据用段数而不是时间/写入次数 —— 段数是 FTS5 自己合并策略的
结果，同样的写入量在不同写入模式下攒出的段数差别很大。这一条**不改**决策 2 的判断
（索引仍建在行上），只是把那句"optimize 是秒级成本所以永远不做"修成"不该每次做，但也不该永不做"。
