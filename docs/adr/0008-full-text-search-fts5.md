# ADR-0008：全文搜索用 SQLite FTS5，中文逐字分词、external content 换行号

- 状态：已采纳
- 日期：M2

## 背景

M2 要给 1 万笔记量级的 Vault 加全文搜索。要求：**离线**（运行时无出站请求）、**不要求用户额外安装东西**、
索引是**可重建的派生数据**（ADR-0002）、中文必须能搜（这是主要使用场景）。

自然语言全文检索要同时解决分词、倒排索引、相关性排序、增量更新四件事 —— 自己写等于把半个数据库塞进应用。

## 决策

### 1. SQLite FTS5，静态编进二进制（`rusqlite` + `bundled`）

理由与许可证见 `docs/dependencies.md`：`bundled` 把 SQLite 源码编进可执行文件，因此**不依赖系统 `sqlite3.dll`**、
也保证 FTS5 一定可用（系统库是否编译了 FTS5 不可控）。

### 2. 行表 + FTS5 external content：为了"排名之后还能拿到行号"

```sql
lines(id, rel_path, line, text, indexed_text)                     -- 行表（含原文与"分词后"文本）
lines_fts USING fts5(indexed_text, content='lines', content_rowid='id', tokenize='unicode61 remove_diacritics 2')
```

`content='lines'` 让 FTS 表不重复存原文，而 `bm25()` 排完序可以 `JOIN lines` 拿回 **`rel_path` 与 `line`**——
这正是 IPC 契约里 `SearchHit { relPath, line, snippet, score }` 需要的。若只用 FTS5 自带的 `snippet()`，
拿到的是带标记的片段而不是"第几行"，前端就没法展示行号。

### 3. 中文**逐字**分词（`space_cjk`），索引与查询两侧同口径

FTS5 的 `unicode61` 把一整串汉字当作**一个 token**：那样"今天天气很好"里永远搜不到"天气"。
因此入库与查询两侧都用同一个函数把 CJK 逐字切开（`今天天气` → `今 天 天 气`），中文查询于是变成
**相邻字短语匹配**（`天气` → `"天 气"`），语义上等价于子串检索，`今好` 不会命中。

- 代价：token 数与索引体积成正比（实测中文库索引约为被索引文本的 **2.7 倍**，1 万笔记 / 29.1 万行 ≈ 114.7 MB）；
- 如果将来 vault 的中文正文到几百 MB，索引会到 GB 量级，届时需要考虑词典分词或双字词粒度 ——
  这属于 M5 的规模问题，README/architecture 已记为已知限制。

### 4. 用户输入按**自然文本**处理，绝不让它变成 FTS 语法

每个词包进双引号（内部 `"` → `""`）、词尾加前缀 `*`，按空白切词、丢掉不含字母数字的词，最多 16 词 / 每词 64 字符。
`a"b(c)`、`-x`、`OR`、`NEAR`、`*`、`(`、`)`、`^`、`:`、`""`、500 字长串都有测试，**一律不报错**（`OR` 当普通词）。
前端另有 150ms 防抖 + 请求序号竞态丢弃、空查询不发 IPC。

### 5. 构建期间放宽持久化，用**自愈**兜底

批量写几十万行时，默认的 `journal_mode=DELETE` + `synchronous=FULL` 要多花好几秒。
构建期间用 `journal_mode=MEMORY` + `synchronous=OFF` + 32MB 页缓存，构建末尾 `optimize` 合并段。

**代价**：构建中途断电可能留下**坏库**。处理方式是 `SearchIndex::open` **自愈** —— 打不开就删掉重建
（ADR-0002：索引是派生数据，删掉可从文件重建）。这是本 ADR 里唯一一处"用可靠性换速度"的取舍，且被限定在
**可重建的缓存**上，不碰用户数据。

### 6. 索引更新与链接/标签**同源**，不额外读文件

`build_indexes` 在**同一遍扫描**里顺带建 FTS（可取消、`spawn_blocking`）；增量更新挂在既有的
`update_note` / `remove_note` / `rename_note` 上。搜索**不索引非笔记**，`.mimenote/**` 也不进索引。

## 代价与已知限制

| 项 | 实测 / 说明 |
| --- | --- |
| 查询延迟 | 真实查询（命中约 100）**3 ms**；命中 1000 行 **66–79 ms**；命中 29 万行（每行都含查询词）**0.9–1.2 s**。慢的那档是 `bm25()` 给全部命中打分 + JOIN 回行表 + 三键排序，占约 90%；已实测 `CROSS JOIN` / `CTE+LIMIT` / 去 `ORDER BY` / 大页缓存 / `mmap` 五个变体**都在同一量级**，没有便宜的优化空间 |
| 索引体积 | ≈ 被索引文本的 2.7 倍（中文逐字 token） |
| 每次打开 Vault 整库重建 | 链接+标签 5.5 s、含 FTS 10.3 s（后台、可取消、不阻塞 UI）。跨会话复用与按 mtime 增量更新属于 **M5「增量索引」** |
| 连接串行化 | `Connection` 非 `Sync`，查询走 `Mutex` → 并发查询排队（每条 ms 级） |
| 构建期 race | 后台构建完成时按"扫描时捕获的 entries"整份替换索引，构建窗口内的保存/改名/删除可能在索引里丢失（链接索引既有行为，未修） |
| 索引不可用时的降级 | Vault 只读/建库失败 → 记 warn、状态置 `Failed(原因)`、**应用照常启动**，`search_query` 返回 `IO` + 中文原因；构建中 → 同样返回 `IO`（前端据此提示"索引构建中"而不是报错） |

## 影响

- 索引层（`mn-index`）独占 SQLite 依赖；宿主只负责"打开/安装/降级"与查询搬运，IPC 契约与前端不受实现影响。
- 前端搜索面板是命令面板的**第三个模式**（`Ctrl+Shift+F`），异步查询 + 竞态丢弃；
  **回车不跳命中行**（编辑器还没有"定位到某行"的入口，要接应由 editor 侧提供 `openAt(relPath, line)`）。
