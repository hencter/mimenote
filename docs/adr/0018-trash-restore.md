# ADR-0018：回收站恢复（删掉的东西怎么拿回来）

- 状态：已采纳
- 日期：M3 之后

## 背景

删除从 M1 起就是"移到 Vault 内 `.mimenote/trash` + 写台账"（`mn_core::trash`），
**从不 `unlink`** —— 这是"误删是笔记软件最不可接受的事故"这条判断的直接落地。
但**恢复**一直没有做：`list_trash` 从写出来那天起就没有任何调用方，README 的已知限制里写着
"恢复界面在 M2"，一直挂到这一轮；用户想找回删掉的东西，只能去文件管理器里翻
`.mimenote/trash/`，而那里的文件名前面还带着时间戳前缀（`{id}__原名`）。

要回答四个问题：

1. 恢复到哪？原位置被占用怎么办？
2. 台账（`index.jsonl`）是磁盘上的普通文件，被人改过怎么办？
3. 恢复之后条目表与索引怎么跟上（可能是一整棵目录）？
4. 界面上怎么做，才能不让"点一下"变成不可预期的事？

## 决策

### 1. 默认恢复到**原位置**；原位置被占用时**拒绝**，出路是「恢复为…」

`restore_from_trash(root, id)` 放回 `original_rel_path`；`restore_as(root, id, target)` 放到指定
位置（界面上的「恢复为…」）。

**绝不覆盖**：目标位置已经有东西就返回 `ALREADY_EXISTS`，记录与文件都原样留在回收站里。
理由是"静默覆盖"比"删错文件"更糟 —— 用户可能已经把一篇新笔记写到了那个名字上，
而覆盖掉的是**他没打算删的东西**。界面的出路是换个名字恢复（输入框预填原路径，改一下即可），
而不是放宽这条判定。

### 2. 台账**不可信**，所以"恢复"必须逐条校验来源

台账是磁盘上的普通 JSONL，手改一行就能让它指向 Vault 里**任何**文件。若直接按它搬，
`restore` 就是一个"任意文件移动"原语（把 `重要.md` 搬到回收站、再"恢复"到别处）。

因此 `stored_rel_path` 必须是**真的在 `.mimenote/trash` 之下**的一段
（`path_guard` 会拒掉绝对路径、`..`、符号链接与越界），否则 `PATH_INVALID`/`PATH_ESCAPE`。
目标路径同样过 `path_guard`，且不允许指回 `.mimenote/`。
有一条测试专门拿**篡改过的台账**（四种指向）去撞它，并断言文件没被搬动。

### 3. 先搬文件、后改台账

反过来（先删台账）一旦搬失败，文件还在回收站里却再也没人知道它原本叫什么；
而"先搬后改"的最坏情况是"文件回去了、台账里还留着一条" —— 再点一次恢复会得到 `NOT_FOUND`，
**可自愈**。台账删除用 `write_atomic` **重写**整个文件（JSONL 是追加写入的，删行只能重写）：
就地截断中途断电会留下半截台账，而台账是"还能不能找回删掉的东西"的唯一依据。

### 4. 恢复之后：单篇就地补索引，**前端一律刷新一次**

宿主的 `note_restore`：

* **单篇**：读回文件 → `VaultCtx::upsert` 补条目 → `indexer::update_note` 同步标签/搜索/图谱，
  与 `note_create` 是同一条收尾；
* **整目录**：**不做**逐条猜。一个目录可能带几百个文件，逐个构造 `EntryMeta` 等于把扫描器的口径
  （扩展名、忽略规则、大小统计）抄第二遍，任何一处漂移都是"恢复之后树里少几篇"。
  出参带 `needs_rescan = true`，由前端调一次静默重扫。

**前端无论哪种情况都要刷新条目表**（`vault-store.syncAfterRestore`）：宿主更新的是它自己那份
条目表，而前端那份是打开 Vault 时拍的快照 —— 不刷新就会出现"文件回到磁盘了、树里却没有那一行"。
这一步在真实应用 E2E 里被逮到过一次（第一版只对目录刷新），所以现在是**无条件**的，
单篇也走同一条路，免得两套收尾各自漂移。

### 5. 界面：三条硬要求

* **孤儿记录要说清**：台账里有、`.mimenote/trash` 里已经没有的那些（用户手工清过回收站）
  在列表里标成"文件已不在回收站"并**禁用**恢复按钮，而不是让用户点下去才吃到 `NOT_FOUND`；
* **结果如实汇报**：成功要说清"恢复到哪"与"顺手建了哪些目录"（`createdDirs`，自浅到深）——
  删过整个目录再恢复时，用户需要知道凭空多出来的目录是这次恢复建的；
* **删除不再是单向动作**：删除确认框里直接写明"可在「回收站」里恢复"。

入口是命令注册表里的一条命令（`vault.trash`「打开回收站…」，`when: hasVault`），
因此**菜单、命令面板**同时都有它 —— 与其它命令共用同一份真相（architecture §2.2）。

## 后续修订：永久删除与清空回收站（本轮）

上面那张表里的两条"没做"在本轮补上了。回收站此前只有**入口**（东西进得去）没有**出口**：
`.mimenote/trash` 只涨不落，用户唯一能真删东西的地方是文件管理器 —— 而那样清完之后，台账里
留下指向不存在文件的记录（界面只好把它们标成"文件已不在回收站"，一条条躺着，谁也清不掉）。
换句话说：**"永不 unlink"这个决定缺了一半的执行力** —— 一个只会变大的目录迟早会逼用户绕开应用。

本轮补的就是那两个出口，并且刻意**让它们与恢复共用同一套纪律**。

### 1. 两条命令、一个出参

| 命令 | 语义 |
| --- | --- |
| `trash_delete(id, confirm)` | 永久删除**一条**（真删文件/整棵目录树 + 去掉那条台账记录） |
| `trash_empty(confirm)` | 对**当前台账里的所有条目**执行同一套逐条逻辑 |

两者都 `confirm` **必填**（与 `note_delete` 同一条思路：把"用户按下的那一下"变成契约上的
一等公民，而不是指望每一处调用方都记得先弹确认框），都返回同一个 `PurgeSummary`：

```
removed: string[]                    真从磁盘上删掉的条目 ID
missing: string[]                    台账里有、回收站里没有的（只清了台账记录，不释放空间）
failed:  { id, originalRelPath, reason, message }[]   没执行的条目 + 稳定原因 + 原话
bytesFreed: number                   本次实际释放的字节数（只累计 removed 里那些）
```

`removed` 与 `missing` **分开**是这份出参里唯一一个"多此一举"的选择，而它是刻意的：
对用户来说"我删掉了 3.4 MB 的东西"和"我清掉了 1 条早已没有文件的记录"是**两件事**，
合成一个 `count` 之后，界面就再也说不出"释放了 0 字节"这个事实。

### 2. 逐条校验：台账**不可信**这条纪律对"删"比"搬"更要紧

第 2 条纪律（见上）本来是给恢复写的：台账是磁盘上的普通 JSONL，手改一行就能让它指向 Vault 里
任何文件。**同样的篡改放在永久删除上就是一条任意文件删除原语，而且不可逆** ——
恢复至少还能再删一次/再搬回去，`unlink` 之后什么都没有了。

因此这一轮的实现里，形状判定被提成 [`stored_path_under_trash`] 一处，恢复与永久删除**共用**：
`stored_rel_path` 必须真的是 `.mimenote/trash/某一段`（恰好三段的相对路径），随后照旧交给
`root.resolve_existing` 去问 `path_guard`（绝对路径、`..`、盘符、保留名、**逐级符号链接检查**）。
两条命令都不"尽力而为"：**任何一条校验不过就拒绝执行那一条**，进 `failed` 并如实报出理由，
台账记录**原样留着** —— 它是用户唯一还能看见"这里有一条我没能清掉"的地方。
（代价：被篡改的那条会永远卡在列表里。这是刻意的取舍：永久删除这个动作宁可"卡住"，不可"猜"。）

### 3. 顺序与恢复相反：先删文件、后台账

恢复是"先搬文件、后改台账"（第 3 条纪律），永久删除是**同一方向的镜像**：先删文件，后改台账。

为什么不能反过来（先删台账）：
* 台账一删，那条记录就再也**没有入口**能清掉了（列表里已经没有它）。此时文件还在
  `.mimenote/trash` 里占着空间，而用户刚刚在界面里看到的是"已永久删除" —— 这是一句谎话，
  且它的后果是**不可修复**的（只能回文件管理器手删，正是本轮要消灭的那件事）；
* 先删文件后改台账的最坏结果是"文件删了、台账留了一条**孤儿记录**"。这一条界面上本来就会
  标成"文件已不在回收站"，用户再点一次「清掉记录」即可 —— **可自愈**。

所以"最坏情况落在可自愈的一侧"这条判据，在两个方向上是同一个答案：先动文件。

### 4. 界面：两条路都要二次确认，且**不隐藏宿主的拒绝**

* 每行一颗「永久删除」（孤儿记录那颗写「**清掉记录**」—— 那一步不删文件，按钮名与确认文案
  都必须跟着变，否则就是在骗用户）；
* 对话框顶部一颗「清空回收站」（列表为空时禁用）；
* 两条路都走 `confirm-store` 的 `ask`，`danger: true`，文案明确写"**不能恢复**"、
  "真的从磁盘上删掉"；"删除到回收站"那种"可以随时恢复"的话在这里一个字都不能出现；
* 结果如实汇报：`永久删除了 N 项，释放 X`（+`另清掉 M 条「文件已不在回收站」的记录`），
  有 `failed` 时**逐条**列出理由（`path-invalid` / `path-escape` / `io` + 宿主原话），
  并且**列表里那一行必须留着** —— 界面若把它一起抹掉，用户就再也看不到"这条为什么没清掉"。

`missing` 那一类**不**调用条目表刷新：删的只是 `.mimenote/trash` 里的东西，它本来就不在扫描
范围里（`.mimenote/` 被扫描器忽略），文件树与索引一个字节都没变（这与恢复**恰好相反**，
恢复必须无条件刷新）。

### 5. Mock 适配器：`present` 的语义被摆正了

Mock 里原来有两条并行的"东西还在不在"的说法（一个从不被写入的 `goneFromTrash` 集合，
和真正存正文的 `removedTexts`）。本轮把 `present` 收到 `removedTexts` 一处，并加了
`simulateTrashFileGone(id)`：它只把"回收站里的文件"拿走、台账记录留着 —— 这正是孤儿记录的
定义。没有这个钩子，孤儿记录那一路（`present: false`、`missing`、"清掉记录"）在 Mock 底座上
根本造不出来，界面那条分支就只能靠临时桩适配器覆盖。

Mock 的 `trash_delete` / `trash_empty` 与宿主**逐条对齐**（包括 `confirm` 必填、孤儿记录进
`missing` 不释放空间），但刻意**永远不产生 `failed`**：内存 Vault 里不存在"台账指向回收站之外"
或"文件被占用"这两种处境，编一个假的跳过项只会让浏览器预览里的汇报看起来更完整、实际更不可信
—— 那条路径由宿主单测（`purge_delete_rejects_a_tampered_ledger_entry`）与 UI 层用桩适配器写的
用例覆盖。
