# ADR-0021：知识图谱改为"自我中心子图 + canvas 卡片"

- 状态：已采纳
- 日期：M3 之后

## 背景

用户对既有图谱的反馈是两句：

> 知识图谱的视图不对，有点乱，我希望进入后只有先关联的图谱，然后图谱深度是可以调节的，
> 并且每个节点是完整的 markdown 预览，采用 canvas 进行处理。

对照 ADR-0010 的实现，这两句各自指向一个**结构性的**问题，不是调参能解决的：

1. **"有点乱"**：全库视图里所有卡片都铺在同一个平面上（文件夹装箱 + 均匀网格），
   画布上**没有"距离"这个维度**。读者只能靠连线的形状去推理"谁离谁近"，
   而一两千张卡片时连线本身就是一团噪声。
2. **"每个节点是完整的 markdown 预览"**：每张卡片是一个 DOM 元素（`GraphCard`），
   正面只有标题/路径/标签/度数这些**摘要**。想做完整预览，就得给每张卡片塞进一整篇正文的
   富文本 —— 300 张卡片就是几万个 DOM 节点，浏览器每帧的排版代价会让平移直接掉帧。
   摘要不是偷懒，而是 DOM 方案下的唯一选择。

## 决策

### 1. 默认视图改成"关系图"（自我中心子图），整个 Vault 退成可切换的另一种视图

两种视图回答两个不同的问题，因此**都保留**：

| 视图 | 回答的问题 | 卡片内容 | 入口 |
| --- | --- | --- | --- |
| 关系图（默认） | "这篇笔记周围连着谁" | **完整 Markdown 预览** | 进入图谱即是 |
| 整个 Vault | "这个库的整体结构长什么样" | 紧凑卡片（标题/目录/度数/标签） | HUD 上的"整个 Vault" |

默认进入 1 跳（直接相关的那一圈），深度可调 1..5，**双向**（出链与反链都算一跳 ——
用户说的"先关联"就是双向的）。默认给 1 而不是 2/3：默认给 2 会在几十个邻居的笔记上立刻
变成一屏乱线，而那正是这次要修掉的东西。

折叠（文件夹容器）只属于全库视图：关系图里的"容器"就是半径，没有可折叠的层级。

### 2. 跳数 = 半径（同心环），坐标是数据的纯函数

环半径由"这一环装得下多少卡片"的**弧长和**算出来（不是写死的间隔），环内按 `relPath`
字典序、从正上方（-π/2）顺时针开始摆。于是同一篇笔记 + 同一个深度**每次打开位置完全一样** ——
"空间记忆"是图谱最有用的地方，力导向布局给不了它（每次打开都换一个样子，读者永远记不住谁在哪）。

**被否掉的替代**：力导向 / 弹簧布局。它能让"连接紧密的聚在一起"，但代价是每次重排都不一样、
且拖一下某个节点整幅图会重新抖动 —— 对一个"用来找东西"的界面来说，稳定性比聚类更重要。

### 3. BFS 在宿主里做，不在前端从 `graph_data` 里筛

`graph_data` 在大 Vault 上按度数截断（上限 8000 节点）。从**被截断过的**数据里做 BFS，
得到的邻居集合是**错**的："这篇只连着 3 篇"可能是真相，也可能是另外 7 篇被截掉了。
邻接只有索引知道，所以 BFS 在宿主（`mn-index`）里做，纯内存、零文件 IO。

- `LinkIndex::ego_graph(root, depth, max_nodes)`：双向 BFS，起点恒在；
- 截断按"距离升序 → 同层度数降序 → 路径字典序"，因此**截断后子图必然连通**；
- 悬空边只在中心那一侧；
- 归一化在索引层一处完成：`depth.clamp(1, 5)`、`max_nodes.clamp(1, 300)`（缺省 1 / 80）；
- 返回的 `GraphData` 与 `graph_data` 形状逐字一致（前端不需要第二套类型）。

反过来说，这也是这一轮里最贵的一次调用：**≈50–60 ms / 1 万笔记**（`graph_data` ≈75 ms）。
贵的部分是"入度必须按全库口径算"，因此每次调用都要解析一遍全库链接（≈20 ms）——
与 `graph_data` 同源的口径换来的是"度数在两种视图里一致"，这个一致性比省 20 ms 值钱。
初版"全量组装再筛子集"是 ≈130 ms，改成"第一趟只扫度数+邻接表、选点后第二趟只为子集造节点/边"
之后降到 50–60 ms。全程纯内存。

**被否掉的替代**：把每个节点的度数缓存进索引。它会让"增量更新时哪些度数失效"变成一个
必须维护的失效图（改一篇笔记要重算所有指向它的节点的入度），而收益只有 20 ms。

### 4. 卡片画在 canvas 上（读数与取舍）

这是本轮最大的改动，也是最容易被误读的一处，所以把量出来的数字放在这里。
本机实测（`node` + jsdom，80 篇结构相似的中文笔记，都是"标题 + 6 段 + 列表 + 提示框 + 代码块"）：

| 做法 | 代价 |
| --- | --- |
| 阅读视图那条渲染管线（markdown-it + DOMPurify）跑一遍这 80 篇 | **102.8 ms**（**不含** DOM 落地与浏览器排版 —— 那才是大头，见 ADR-0020 的 1 MiB 实测） |
| 焦点视图：把这 80 篇**排版成卡片**（解析 + 换行，一次性且有缓存） | **27.2 ms**（0.34 ms/篇） |
| 焦点视图：画一帧（10 张在屏幕里，70 张被裁剪） | **0.3 ms**（400 次绘制调用） |
| 焦点视图：画一帧（80 张全在屏幕里，即缩到最小时的最坏情况） | **1.1 ms**（3200 次绘制调用） |

也就是说：**画**这件事便宜到可以忽略，而 DOM 方案的代价恰恰在"把富文本变成节点、再让浏览器排版"
那一侧（ADR-0020 里 1 MiB 文档的 `innerHTML` 落地 ≈3177 ms / `DOMPurify` ≈3469 ms）。
canvas 把这块代价换成了"我们自己按 `fillText` 画" —— 一处**可控且可测**的线性成本。

代价与补偿（这部分必须写在明处，否则后面的人会以为 canvas 是白拿的）：

| 失去的东西 | 补偿方式 |
| --- | --- |
| 卡片不再是 DOM ⇒ 点击命中要自己算 | 世界坐标矩形命中（`rectHit` + 4px 屏幕宽容度）；缩放/平移不影响判据 |
| 卡片不能再 Tab 聚焦 | 宿主 `tabIndex=0` + 方向键在"同一方向上最近的卡片"之间移动选中项，`role="application"` 给出整体说明 |
| 卡片文字不能被浏览器选中/查找 | 关系图是"看结构 + 决定打开哪一篇"的界面，真要读/搜索有编辑器、阅读视图与全文搜索三条路；预览面板（`GraphPreview`）仍是 DOM，可以选中正文 |
| 缩放时文字会被放大成模糊 | 反而是收益：每一帧按当前缩放**重新排版**（字号跟着变），文字始终清晰 |
| 一张卡片的一个像素变了就要整帧重画 | 一帧 1.1 ms（见上表），且只画视口内的卡片 |

三层各画什么（坐标只有一套：`屏幕 = 世界 × scale + offset`，`viewport.ts`）：

1. **canvas** —— 卡片本体与卡片里的正文（`canvas/paint.ts`）；
2. **SVG** —— 连线（`GraphEdges`）。刻意**不**用 canvas 重画：正交折线、箭头、
   悬空链接的虚影与目标名都已经实现且更细腻，用 canvas 画直线是退步（所以画笔收到的 `edges` 是空数组）；
3. **DOM** —— 全库视图里可点、可折叠的文件夹头（几百个节点不是负担）。

### 5. 卡片内容 = 那篇笔记的完整 Markdown 预览，且与阅读视图同一套语法口径

`canvas/blocks.ts`（Markdown → 绘制块清单）刻意**复用**阅读视图的判据：
`domain/callouts.ts` 的 `parseCallout`、`domain/links.ts` 的 `splitWikilink`、
markdown-it 的令牌流。于是"画布上看到的"与"阅读视图渲染出来的"不会漂移 ——
新增一种语法时，两边同时得到它（提示框就是这么接进来的）。

排版（换行、块高、表格列宽、图片占位）全部在 `canvas/text-layout.ts` 里，
字号/行高/缩进来自一份 `LayoutMetrics`；画笔只消费结果，**不自己再算一次换行**。
缓存键是 `(relPath, 标题, 正文, 宽度, 上下限)`：平移/缩放每帧都会问同一批卡片的排版，
没有缓存的话每帧都要重跑一遍解析与换行（27 ms 级的代价，见上表）。

**正文一次性随子图读回来**（`notes_read_batch`，40 篇一批），不做增量：环半径取决于卡片高度，
"先画再补正文"会让环半径反复变、卡片跳来跳去。读不到正文的节点退成紧凑卡片（标题/目录/度数），
于是"某篇读失败"不会让整幅图缺一块。

### 6. 深度与视图持久化；手工拖动只在全库视图成立

- `{mode, depth}` 存在 `localStorage` 的 `mimenote.graph.prefs.v1`，**不按 Vault 分**：
  它是"我怎么看图"的偏好，换一个 Vault 还要重选一遍只会让人以为开关坏了。
  手工位置仍按 Vault 分（`mimenote.graph.positions.v1`）——那才是"这个 Vault 长什么样"。
- 关系图里**不能拖动卡片**：卡片的位置就是"离中心几跳"，拖一下就把这个唯一的信息变成了谎话。
  在那个视图里按住卡片拖动 = 平移画布。
- "换圆心"不需要单独的按钮：双击一张卡片 = 打开它，而圆心跟着当前打开的笔记走。

### 7. 截断如实说出来，不给"还有多少没显示"的假精度

`ego_graph` 只返回 `truncated: true`（DTO 与 `graph_data` 逐字一致）。HUD 上的角标说的是
"相关的笔记太多，只显示了离中心最近的一部分（调小深度可以看得更清）"，
而不是"还有 N 篇没显示" —— 后者要加字段，而"离中心最近的一部分"这句话本身就是准确且有用的。

## 后果

- **正面**：进入图谱第一眼就能看到"与当前笔记直接相关的内容"，且卡片上就是正文；
  深度是可调的、坐标是稳定的；80 张卡片的最坏一帧 1.1 ms；
  跳数与颜色的口径在两处只有一份（宿主 BFS、`LayoutMetrics`/主题令牌）。
- **负面 / 已知限制**：
  1. `ego_graph` 每次 ≈50–60 ms（1 万笔记），且**每次调深度都会重跑一次**（含全库入度）。
     连续调节深度时会感到一次可接受的延迟（HUD 上的"刷新中"会亮）；
  2. 关系图里卡片不能被 Tab 聚焦、文字不能被选中（补偿见决策 4）；
  3. canvas 上的提示框强调色要靠"探针元素"读 `--mn-callout-accent`（`canvas/probe.ts`）——
     app.css 把 13 种颜色写在 `var()` 的**兜底位置**上，`getComputedStyle` 读不到那个名字；
  4. 卡片标题不折行也不补省略号（超出由卡片裁剪），这是刻意简化：折行会让标题行高随内容变、
     同一屏卡片高低不齐；
  5. 图片在卡片里只画占位框（`canvas` 里解码 `asset://` 是异步的，会把"一帧"变成"一串帧"）；
  6. **预览面板打开时方向键仍然是"换选中项"**：面板自己没有实现键盘滚动，排除掉就等于
     "预览开着时方向键是死键"，而画布是一块可键盘操作的整体（要滚正文用滚轮，或先 `Esc` 关掉预览）。
     这条是被端到端用例钉住的（`test:e2e:ui` 的"方向键仍能在画布上换选中"）。

## 相关的替代方案（都被否掉）

| 方案 | 为什么否掉 |
| --- | --- |
| 保留 DOM 卡片，只做"虚拟化 + 完整预览" | 虚拟化解决的是"节点多"，解决不了"每个节点都很重"：一屏 10 张完整预览就是 10 篇正文的富文本排版 |
| 力导向布局 | 每次打开位置都变，空间记忆失效（见决策 2） |
| 前端从 `graph_data` 里筛子图 | 截断过的数据会给出错误的邻居集合（见决策 3） |
| 用 canvas 顺带重画连线 | 正交折线、箭头、悬空虚影与目标名在 SVG 层已经实现且可访问（`<title>`），重画是退步 |
| 关系图里也允许拖动卡片 | 位置本身就是信息，拖动会把它变成谎话（见决策 6） |
