# ADR-0006：标签与 Frontmatter 的解析归属、判同键与编辑路径

- 状态：已采纳
- 日期：M2

## 背景

M2 要为笔记补上两类"结构化信息"：

1. **Frontmatter**（开头的 `---` 区块）——用户已经在写 `tags`、`title`、`date` 这类字段；
2. **行内标签**（`#标签`、`#父/子`）——不需要 frontmatter 就能用。

它们都要同时出现在三个地方：**索引**（反向链接式的"哪些笔记用了这个标签"）、**界面**（标签面板与属性表）、**未来的编辑**（在面板里改标签）。

三个问题必须先定，否则后面每一处实现都会各定一套：

- 解析放哪一层？
- 两个写法（`#Rust` 与 `#rust`、`#父/子/` 与 `父/子`）算不算同一个标签？
- 从 UI 改标签怎么落盘（要不要新开一条写路径）？

## 决策

### 1. 解析在 `mn-core`，索引在 `mn-index`，宿主只搬运

| 层 | 职责 | 落点 |
| --- | --- | --- |
| `mn-core` | 从**一段文本**里抽取 frontmatter 与标签；纯函数、不碰文件系统 | `mn-core::frontmatter`、`mn-core::tags` |
| `mn-index` | 在既有 `upsert(rel_path, text)` 里顺手建立"笔记 ↔ 标签"双向索引（与链接索引同源同生命周期） | `mn-index` |
| `src-tauri` | 三个只读命令：`note_tags` / `tags_list` / `tag_notes` | `commands.rs` |
| 前端 | 只展示与跳转，不自己解析 Markdown | `features/tags`、`state/tags-store` |

理由：与链接抽取（`mn-core::links`）保持同一种形状 —— 抽取器可以被独立测试（`mn-core` 有 60+ 个相关单测），索引可以整轮重建（ADR-0002），宿主保持"零业务逻辑"。

**不做 Markdown AST 解析**：不引 `pulldown-cmark` 之类依赖，自己写"够用的扫描器"。代价是少数语法（缩进代码块、复杂 YAML）口径保守，收益是依赖最小、行为可测试可预期。

### 2. `normalize_tag` 是唯一的判同键

判同规则（`mn_core::tags::normalize_tag`）：去首尾空白 → 去掉开头的 `#` → 连续空白折叠 → **转小写** → 折叠连续 `/` 并去掉首尾 `/`。

- 因此 `#Rust` / `rust` / `#RUST` 是同一个标签；`#父/子/` 与 `父/子` 也是同一个。
- **索引、去重、查询入口都必须走这个函数**，任何一处自己写一套"看起来差不多"的规则，都会让面板与索引对不上（这类 bug 只在用户同时用大小写两种写法时才暴露，代价极高）。
- 展示用的写法是**首次出现的原文**（`TagRef::tag`），保留大小写与层级；`#` 前缀由 UI 决定加不加。
- 小写化的理由：Windows/macOS 文件系统与既有链接匹配（`normalize_target`）都是大小写不敏感口径，标签保持一致。

### 3. 改标签**不开新写路径**

在 UI 上编辑标签（未来的"点标签改标签"）必须走：

```
note_read（拿原文与 mtime）
  → mn_core::frontmatter::set_tags（只改 tags 那几行，返回新文本）
  → note_write（带 baseMtimeMs）
```

绝不新增"直接写文件"的命令。理由：ADR-0004 的冲突保护（mtime 版本令牌）与原子写是**用户数据安全**的底线，任何绕开它的写路径都会让"编辑器里有未保存内容"与"磁盘被外部改过"这两种情况失去保护。

`set_tags` 因此被设计成**最小 diff**：只替换 tags 相关的行/段，BOM、CRLF、注释、未知键、字段顺序全部保真；没有 frontmatter 时返回 `None`（**不擅自给文件补 frontmatter** —— 那是产品决策，交给宿主层）。

## 代价与已知偏差

| 代价 / 偏差 | 说明与缓解 |
| --- | --- |
| 缩进代码块（4 空格）里的 `#标签` 会被抽出 | 与 `links.rs` 对 `[[链接]]` 的口径一致（只认围栏与行内代码）；在模块文档里声明 |
| `#标题`（行首单个 `#` 直接跟标签字符）判为标签，`##标题`/`# 标题` 判为标题 | 这是最容易踩的边界，已用 `heading_rules_are_pinned` 测试钉死；改判定只需动 `heading_line()` 一处 |
| 极简 YAML 子集：嵌套映射、折叠标量、锚点、`...` 结束标记不支持 | 笔记场景罕见；不支持的整行忽略（不报错），并在文档里声明 |
| **frontmatter 区块计入正文统计**（字数/行数/阅读时长） | 现状如此（Rust 与 TS 两侧都算全文）。要改必须**两侧同时改**（`frontmatter::body` + TS 对应实现），否则"编辑器即时统计"与"磁盘统计"会互相打架 —— 它们当前互为校验 |
| 标签面板目前只读 | 本 ADR 第 3 条已经定了改标签的路径，接线时按它做即可 |

## 影响

- `mn-core` 新增两个模块（含 66 个测试），`mn-index` 的 `upsert`/`remove` 成为"文本派生数据"的唯一入口：**将来任何从文本派生的索引（标签、搜索、图谱）都应挂在这里，不要再读一遍文件**。
- 前端不得自行解析标签：判同规则只有一份（Rust），否则 `#Rust` 与 `#rust` 会在两侧分叉。

## 后续修订：标签面板可以加/删标签了（本轮）

M2 时面板只做展示与跳转，改标签要手动编辑 frontmatter。本轮把"加/删标签"接上了，**只做增删**（重命名/合并、按标签过滤文件树仍然另开）。

### 1. 写路径：宿主命令 `note_set_tags`，但没开第二套写纪律

上面第 3 条定的是"`note_read → set_tags → note_write`，绝不新增直接写文件的命令"。落地时发现：**这三步必须由宿主执行**，因为"改哪一行、写成什么形态（标量 / 行内数组 / 块数组 / 补区块 / 引号规则）"全在 `mn_core::frontmatter`；让前端用 TypeScript 再实现一遍最小 diff，等于把判同与保真纪律复制成两份 —— 正是本 ADR 第 2 条最反对的事。

于是新增命令 `note_set_tags`，它**不是**新的写路径，而是把那三步搬进宿主，并且与 `note_write` 共用**同一把写锁、同一次 mtime 令牌校验、同一个 `write_atomic`、同一处 `indexer::update_note` 增量同步**：

```
note_set_tags(relPath, add[], remove[], baseMtimeMs)
  写锁内：
    stat 磁盘 mtime ≠ baseMtimeMs → CONFLICT（附 currentMtimeMs），一个字节都不写
    读磁盘上的最新文本
    可编辑列表 = mn_core::frontmatter::editable_tags(text)
    结果列表  = mn_core::tags::apply_tag_edits(可编辑列表, add, remove)
    新文本    = mn_core::frontmatter::set_tags_or_create(text, 结果列表)
    新文本 == 旧文本 → 直接返回 changed=false（不写盘、不动 mtime、不重建索引）
    否则 atomic 写 → indexer::update_note（标签/搜索/图谱同一处增量更新）
```

前端在调它之前**先落盘**（复用既有的 `saveNow` 流水线，与重命名同一条纪律）：宿主以磁盘文本为基准改写，内存里的未保存内容若不先落盘，随后那次自动保存会把刚写下的标签覆盖掉。冲突走**同一条冲突横幅**（`note-store` 的 `conflict` 态），不另发明提示。

### 2. 入参是"增与删"，不是"新的完整列表"

面板上的列表可能比磁盘旧一拍（索引/面板刷新有延迟）。传"想要什么"会在那种情况下**静默丢掉别的标签**；传"加什么、删什么"则由宿主基于**它刚读到的文本**算结果，旧一拍的最坏后果只是"重复加了一个已存在的"（幂等，不写盘）。

### 3. 三个新函数与一条硬性纪律（都在 `mn-core`，都可独立测试）

- `frontmatter::set_tags_or_create(text, tags) -> String`：`set_tags` 的另一个入口。**产品决策落在它身上** —— 用户点的是"给这篇加标签"，那就必须有地方放它，于是没有 frontmatter 时补一个区块（BOM 保留、插入行沿用文件自己的换行风格、**正文一个字节不动**）；要写入的标签为空时原样返回，不给干净正文戴一顶空区块的帽子。`set_tags` 的既有契约（没有 frontmatter → `None`）一字未改。
- `tags::apply_tag_edits(existing, add, remove) -> Vec<String>`：增删的纯函数。删按 `normalize_tag` 判同（传 `#Rust` 也能删掉 `rust`），**既有标签的写法与顺序原样保留**；加会先清理（去 `#`、把连续空白折叠成一个空格 —— 单行输入框进不来换行，IPC 与未来的插件能，而带换行的标签会写出一个跨行的引号标量、把区块切成两半），已存在的不重复加入。
- `frontmatter::editable_tags(text)`：**改写的基准列表**（`set_tags` 真正会写的那个字段：优先 `tags`，其次 `tag`）。与 `Frontmatter::tags`（面板显示的、两字段**合并**去重）刻意分开：拿合并列表去改写会让 `tag:` 字段里的标签被复制进 `tags:`（于是"什么都没改"的请求也改文件），而它自己又永远删不掉。**显示用合并，改写用 `editable_tags`**。
- 幂等是硬要求：结果与磁盘一致时命令返回 `changed=false`，**不写盘、不动版本令牌、不重建索引**（"加一个已经存在的标签"必须没有任何副作用，包括不制造无意义的 diff）。

### 4. 几个必须先定死的产品问题（本轮的决定）

| 问题 | 决定 | 理由 |
| --- | --- | --- |
| 完全没有 frontmatter 时加标签 | **补一个区块**（`---` / `tags: [...]` / `---`），正文一字不动、首行绝不被吞 | 用户点的是"给这篇加标签"，没有落点就只能拒绝这个动作；ADR 正文里说"这是产品决策，交给宿主层"，本轮把它落在 `set_tags_or_create` 一个函数上 |
| 删掉最后一个标签 | **保留字段、写成空列表**（块数组删掉项行留下 `tags:`，行内数组变成 `tags: []`），**不删 key** | 删 key 会让用户手写的顺序/位置信息凭空消失，且"空 `tags:`"与"没有 tags 字段"在语义上等价（都是零标签）；保留字段也是最容易解释的行为 |
| 一次输入多个标签 | **只用逗号分隔**（`,` 与 `，`），空格不拆；开头的 `#` 与首尾空白由清理规则吃掉 | `normalize_tag` 明确允许标签里有空格（`中文 标签` 是一个合法标签），按空格切会把用户一个合法标签拆成两个；而逗号本来就是 frontmatter 里 `tags: 甲, 乙` 的既有口径 |
| 正文行内 `#标签` | **只读**，但面板必须标出来源（「正文」角标）并给一句可读提示（"请到正文里删"） | 行内标签删掉就等于改正文，那是编辑器的活；把 `×` 做成禁用态只会让用户以为面板坏了 |
| 面板显示 vs 写入目标 | 显示合并（`tags` + `tag`），写入只写 `tags`（没有 `tags` 时才写 `tag`） | 见上面第 3 条；两者同时存在时 `tag:` 里的标签点 `×` 删不掉，面板会如实说"没有改动，它来自 `tag:` 字段"，而不是假装删了 |

### 5. 其余保真与边界（都有测试钉住）

- **最小 diff**：除 `tags` 那几行外逐字节不变（BOM / CRLF / 注释 / 未知键 / 字段顺序），加一个标签就是把 `[甲]` 换成 `[甲, 乙]`。
- 标签里有空格 / 斜杠 / 中文：写出去必须能原样读回来（`'带 空格'` 这种引号规则沿用既有实现）。
- `tags` 是标量（`tags: 甲`）：沿用原写法 —— 1 个标签仍是标量，0 或 ≥2 个变成行内数组。
- **只读 Vault / 写失败**：报 `IO`（不静默降级为直写），磁盘内容与索引都不变；前端不改变界面状态。只读文件的用例只在 Windows 上跑：`write_atomic` 的收尾是 `MoveFileEx(REPLACE_EXISTING)`，目标只读时必然失败，而 POSIX 的 `rename` 只看目录权限。
- 正在编辑的笔记改完标签：**内存文本必须对齐磁盘**（否则下一次自动保存会把标签覆盖掉）。这里复用既有的 `revision` 自增（整篇替换）通道 —— 编辑器刻意不订阅 `text`（否则每次按键都会让 React 重渲染），`revision` 是唯一能把外部文本送进 CM 文档模型的既有机制。代价是光标位置按旧偏移保留（标签改在文件开头，正文里的光标会差一个标签长度），收益是**撤销历史保留**（整篇替换是一次普通事务），而且"刚改的标签可以被 Ctrl+Z 撤销"本身是好行为。

## 后续修订：标签的重命名与合并（本轮）

上面一节只做了 frontmatter 的**增删**，并且把"标签重命名/合并"与"按标签过滤文件树"一起留在外面。
本轮补上**重命名 / 合并**（全库改写），并因此第一次打开了一条此前刻意关着的边界：
**正文里的行内 `#标签` 也要改**。

### 1. 为什么这一次必须改正文（以及 `note_set_tags` 为什么仍然不改）

`note_set_tags` 只改 frontmatter，理由是"删掉正文里的 `#标签` 等于改用户的正文，那是编辑器的活"。
这个理由在**删除**上成立（用户想删的是标签，不是那句话），但在**重命名**上会立刻变成一句谎话：

```
改名前：tags: [旧]      正文 …… #旧 ……
只改 frontmatter 之后：tags: [新]   正文 …… #旧 ……
```

标签索引按"键 → 笔记"倒排，`#旧` 仍然被抽出来 —— 于是改名之后的笔记**同时挂着 `新` 与 `旧`**，
面板、图谱、概览三处一起说谎，而用户以为自己只是换了个名字。所以：

* **重命名/合并改正文**（行内 `#标签` 一起换）；
* **删除仍然不改正文**（`note_set_tags` 的契约一字未动）；
* 打开这条边界的代价是**跳过判据必须与抽取器完全一致**：围栏代码块、行内代码、HTML 注释、
  frontmatter 区块、Markdown 标题行里的 `#甲` 一个都不动。实现上这不是"再写一遍规则"，而是
  **复用同一个 `BodyScanner`** —— 抽取器改成返回"标签 + 行内字符区间"，改写路径直接用那些区间。

### 2. 语义（写死在 `mn_core::tags::TagRename` 上，逐条都有测试）

判同仍然只有 `normalize_tag` 一份。设源键 `K = normalize_tag(甲)`、新写法 `乙`（已清理：去 `#`、折叠空白）：

| 情形 | 结果 | 说明 |
| --- | --- | --- |
| 标签的键 `== K` | 换成 `乙` | 大小写/层级写法都会被统一成 `乙`（`#RUST` 与 `#rust` 是同一个标签，改名之后不该一个变一个不变） |
| 标签的键以 `K + "/"` 开头，且开关打开 | 换掉**前缀那一段**，后缀逐字保留 | `父` → `母` 时 `父/子` → `母/子`、`父/子/孙` → `母/子/孙`；后缀的大小写是用户写的，我们只动被改名的那一段 |
| 标签的键只是"看起来像"（`父老`、`父辈`） | 不动 | 按 `/` 切段比较前 `depth` 段，不做字符串前缀匹配 |
| 键等于 `K` 但开关关闭 | 不动 | 面板上的开关，缺省打开 |
| "改整条"（源写成 `父/子`） | 同上，`父/子` → `新`，`父/子/孙` → `新/孙` | 层级只在**段边界**上生效，`父` 不是 `父/子` 的后代 |
| 新写法的键与源键相同（`rust` → `Rust`） | 只统一写法，**不去重、不删任何一处提及** | 见下面第 3 条 |

frontmatter 的落点是**两个字段都改**（`tags` 与 `tag`）：只改一个会让旧写法留在磁盘上，
用户看到的就是"改了但没改干净"。每个字段**各自**去重（合并时"目标已经在同一个字段里"就是
这种情况），两个字段之间刻意不合并成一个（那是用户在磁盘上自己写下的结构，属另一件事）。

### 3. 合并：一篇里两个标签都有时不留重复项

把 `甲` 合并进 `乙`，一篇笔记里可能两个都有（`tags: [甲, 乙]`、正文 `#甲 #乙`）。
逐处替换的结果是 `tags: [乙, 乙]` 与 `#乙 #乙` —— 索引按笔记去重看不见，但用户在磁盘上看得见。
因此判据是：

* **目标键在原文里已经出现过**（frontmatter 或正文都算）→ 这一处正文提及是**重复的**，
  连同它旁边的一段空白一起去掉（行尾那一处改吃它前面的空白）；frontmatter 里重复的那条直接不写；
* **目标键原本不在这一篇里**（纯改名）→ 一处不动地逐处改写，`#甲 #甲` 仍然是 `#乙 #乙`
  —— 改名不该顺手删用户的提及；
* 判据只看"**原文**里有没有目标标签"，与处理顺序无关，因此同一篇文本的结果是确定的；
* 例外：新写法与旧标签是**同一个键**时（`rust` → `Rust`），"目标已经在原文里出现过"永远成立
  （就是它自己），按合并口径去重会把每一处提及都删掉。所以这种"统一写法"只改写、不去重。

顺带钉住的另一个细节：`#甲` 独占一行、而目标标签在别处出现时，那一行会变成**空行**（行本身保留）。
删掉整行会更"好看"，但那是在合并一个标签时顺手删用户的一行结构，代价大于收益。

### 4. 写路径：一个新命令 `tag_rename`，纪律与既有写路径完全一致

```
tag_rename(from, to, includeChildren?, dryRun?)
  候选集：标签索引里所有键落在改名范围内（== K 或 K/sub…）的笔记（并集，字典序）——**不重扫全库**
  逐篇（每篇一个短临界区，不是整批一把锁）：
    写锁 → 对账（条目表里的 (mtime,size) vs 磁盘）→ 读盘 → tags::rename_tags
        → 与原文逐字节相同 → 计入 unchanged，不写盘、不动 mtime
        → atomic 写（write_atomic）→ indexer::update_note（标签/搜索/图谱同一处增量同步）
  收尾：条目表按写入后的真实 (size,mtime) 增量更新
```

与前两轮一致的三条纪律一条不少：**同一个 `write_atomic`**、**同一份 `(mtime,size)` 判定**、
**最小 diff 改写 frontmatter**（BOM/CRLF/行尾注释/未知键逐字保真），
`mn_core::frontmatter` 的改写能力一行都没有重写 —— 新增的只是"把每条标签交给一个映射函数"
（`rename_tag_fields`），落点逻辑与 `set_tags` **共用同一个 `field_replacement`**。

几个必须解释的选择：

* **候选集来自索引，而不是扫全库**：1 万笔记里改一个标签，真正要读的是"用到它的那几十篇"。
  代价是索引里没有的笔记（超大被跳过、非 UTF-8）不会被改到 —— 这与标签面板显示的集合**同源**，
  因此不会出现"面板里有、改名却漏了"的落差。索引**没就绪**时明确报 `IO`（"正在构建"），
  而不是回答"改了 0 篇"：后者是一句假答案。
* **没有 `baseMtimeMs` 入参**：这次动的不是"用户正在编辑的这一篇"，而是全库。逐篇的版本令牌
  来自**条目表里的 `(mtime,size)`**（正是 ADR-0016 判定"磁盘上有没有新闻"用的那份对账口径）：
  对不上 → 该篇跳过并如实报告"磁盘被外部改动，请重试"，而不是拿一份可能已经过时的正文去覆盖。
  条目表里没有这一篇、或 mtime 不可得时**放行**（拿不到证据就不拦）。
* **一篇一汇报，绝不"部分成功却报告成功"**：出参把 `edited` 与 `skipped` 分开，跳过原因分成
  三个**稳定串**（`external-change` / `unreadable` / `write-failed`）—— 刻意**不是错误码**：
  一次操作里每个文件的处境都不同，用错误码表达等于把"部分成功"折叠成"失败"。
  单篇写失败只记一条跳过、继续下一篇，用户可以重试。
* **重试幂等**：写入成功后那一篇的旧写法就不存在了，候选集（索引已增量同步）自然缩小；
  就算索引比磁盘旧一拍，判定也是"与原文逐字节相同 → 不改"，连 mtime 都不动。
* **`dryRun`**：走**完全一样**的候选集与判定、只是不落盘 —— 对话框那句"这会改 N 篇笔记"
  因此与真跑的篇数同源，不是估的（这是"先查询再确认"能站得住的前提）。
* **索引同步复用既有增量路径**：每篇写入后就是 `indexer::update_note`（文本派生数据的唯一入口），
  没有新开一条往索引里写东西的路。

### 5. 界面：入口、两段确认与如实汇报

* 入口：标签面板里每个标签旁的 `✎`（本篇标签与全库概览都有），不是"双击即静默改写"；
* 对话框三段：输入新名字（+「连同子标签一起改」）→ **预览**（"这会改 12 篇笔记" + 明细 +
  "会写进磁盘、代码块里的不动"）→ **确认**（真跑）→ 结果（改了 N 篇 / 跳过 M 篇 +
  逐组说明原因与下一步）；`Esc` 取消（写盘途中不响应，否则用户会以为取消了），
  输入框里 `Enter` 走当前阶段的主按钮；
* 有跳过时给的是**警示**提示（"改了 12 篇，3 篇没改（磁盘被外部改动）—— 磁盘被外部改动，请重试"），
  而不是成功提示：这一块最该避免的就是"只报成功"；
* 当前正在编辑的那一篇若在改写范围里 → 重读磁盘对齐内存；**它有未保存内容时不重读**
  （宁可让下一次保存走既有的冲突横幅，也不替用户丢掉刚敲的字）；
* 面板与全库概览在改动后重读一次（索引已在宿主侧增量同步），展开中的那个标签换成新键。

### 6. 本轮仍然没做

* **按标签过滤文件树**仍未做（与本轮无关，属另一块）；
* 缩进代码块（4 空格）里的 `#标签` 与 `[[链接]]` 一样，**仍被当成标签**（既有口径，未改）；
* 全库改写**没有进度与取消**：一次改上百篇时界面只在写盘期间显示"正在改写…"，
  中途无法中断（实测代价见 `docs/architecture.md` 的性能预算一节）；
* frontmatter 的 `tags`/`tag` 两个字段并存时，本轮的改法是**两个都改**，但**不合并成一个字段**。
