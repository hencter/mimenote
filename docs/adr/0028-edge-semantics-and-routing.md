# ADR-0028：连线的语义分层与环向走线

- 状态：已采纳
- 日期：M3 之后（ADR-0025 / 0026 / 0027 的同一轮）

## 背景

用户看过 ADR-0025 之后的图谱，提了一句开放式的意见：

> front meta 不需要在知识图谱当中展现。我们看看能不能够用更优雅的线去关联这些知识图谱的关系，
> 这个我希望你跟我讨论一下，或者说你有没有什么更好的想法。

（frontmatter 那半句已经在 ADR-0025 的同一轮里修掉：卡片正文在进入排版前过
`domain/frontmatter.ts` 的 `frontmatterBody`，判据仍是那一份。）

讨论之后用户选了两条：**B 语义分层**（出链暖 / 入链冷 + 跳数编码粗细与透明度）与
**A 环向布线**（沿环走弧，不再直穿圆心），并要求直接落进代码 + 单测 + ADR。

诊断（改之前的状态）：每条边都是**两点一条三次贝塞尔**（`tensionPath`），于是最拥挤的地方
恰好是圆心周围 —— 同一环上相邻卡片之间的线全都从中间横穿过去。视觉通道只有"虚实 + 明暗"
两档，读不出权重、方向与距离；同一对笔记之间有多条链接时只画一条，信息藏进 tooltip。

## 决策

### 1. 语义色相：以**当前笔记为参照**才有"出/入"可言

| 边 | 判定 | 色相 |
| --- | --- | --- |
| 圆心 → 别人 | `from === root` | `out`（暖） |
| 别人 → 圆心 | `to === root` | `in`（冷） |
| 环与环之间 | 两端都不是圆心 | `context`（中性） |

为什么以圆心为参照：整幅图就是围着它组织的（"离它几跳"是唯一的结构维度），
而环与环之间**两端都算一跳**（BFS 是双向的），在别处根本没有稳定的"出/入"。

颜色令牌是新引入的**可选**令牌 `--mn-edge-out` / `--mn-edge-in`，没定义时落到既有的
`--mn-warning`（暖）与 `--mn-link`（冷）。**不往 `REQUIRED_TOKENS` 里加**：
那会让所有用户自定义主题在启动时报"缺令牌"，而这里的降级链本来就是完整的。

### 2. 跳数编码粗细与不透明度，而且**淡化/强调是乘性调制**

基准权重按"这条边最远牵到第几跳"（两端跳数的较大者）：

| 跳数 | 线宽 | 不透明度 |
| --- | --- | --- |
| 1 | 2 | 0.95 |
| 2 | 1.5 | 0.72 |
| 3 | 1.25 | 0.55 |
| ≥4 | 1 | 0.4 |

"与圆心/选中/悬停相关"（强调）与"都无关"（淡化）**在基准上调制**，而不是替换它：

- 强调：`width = max(base, 2.2)`、`opacity = min(1, base + 0.22)`；
- 淡化：`width = max(1, base × 0.7)`、`opacity = base × 0.3`。

为什么必须乘性：改成"覆盖"之后跳数权重就**永远看不见**了 —— 与圆心相关的边全是强调档、
环与环之间的边全是淡化档，两档正好覆盖所有边，"越远越细越淡"成了图上没人能看出来的空话。
（这是实现过程中真实踩到的坑：第一版写成覆盖，测试立刻发现"二跳的边宽度是 1，
既不是 1.5 也不是我以为的强调值"。）

⚠️ 这条同时**改了淡化档的观感**：过去是钉死的 1px / 0.16，现在随跳数浮动
（一跳淡化 ≈ 1.4 / 0.285，二跳 ≈ 1.05 / 0.216）—— 上下文线比从前略明显一点，
换来的是"几跳"在任何状态下都读得出来。

### 3. 环向走线：三种形状，判据只有一条

```
      同一环（跳数相同且 ≥1）                跳数不同                   涉及圆心
    ┌──────────────────────────┐      ┌────┐          ┌────┐    ┌────┐
    │      ↗ 环外的弧 ↖         │      │ A  │⌒⌒⌒⌒⌒⌒⌒⌒→│ B  │    │ 中心├───→│ X  │
    │   ┌────┐        ┌────┐    │      └────┘          └────┘    └────┘
    │   │ A  │        │ B  │    │      径向切线：两端朝外鼓     保持 ADR-0023 的原样
    │   └────┘        └────┘    │
    └──────────────────────────┘
```

- **同环**：径向出到环外的弧 → 沿弧走 → 径向进入目标。弧半径取"两张卡片**最远的角**"之外
  再加 26px 余量（**不是**"中心距离 + 余量"：100×60 的卡片在半径 300 处，最远的角已经在 351 上，
  按中心算会让弧从卡片身上穿过去 —— 第一版就踩了这个坑）；
- **跳数不同**：径向切线的三次贝塞尔 —— 两个控制点沿各自的"朝外"方向偏移
  `tension × 弦长 / 3`，两端都朝外 ⇒ 曲线走外侧、不横穿圆心；`tension = 0` 时退化成直线
  （张力旋钮的语义没变）；
- **涉及圆心**：**返回 `null`**，调用方继续用它手里那条 `tensionPath`。为什么不在这一层重画：
  圆心那些边本来就在径向上，而径向切线在径向边上会退化成一条直线（朝外方向 = 弦方向）——
  张力旋钮在**最常见的那些边**上就会看起来失灵。形状的决定权留在 `link-edge` 那一份实现里。

换形状时**锚点也要换**（`outerExit`：从卡片中心朝外打射线，取外缘那一点）。为什么：
环外的弧与"朝目标"的内侧锚点之间那段连接会被卡片挡住（卡片是不透明底、线段在它下面），
看起来就是"线在卡片里断了"。换了锚点，卡内那段虚线引线也**必须重画到同一个点上** ——
分界处严丝合缝那条纪律（ADR-0023）不能因为换了形状就破；引线的虚线相位由 `GraphEdges`
按两端点重算，所以它自动跟上。

环半径用**当前**位置算，而不是理论上的 `ringRadii[hop]`：漂浮与拖拽之后卡片并不精确落在环上
（力场会把环收紧三分之一左右），用理论值会让弧穿过卡片。

### 4. 可关

HUD 上有一个「沿环走线」开关（`ringRouting`，缺省开，按"我怎么看图"的偏好落盘）：
关掉就退回"两点一条曲线"的老画法。保留它是因为这是纯观感的选择，
也因为"能不能当场对比"决定了以后讨论这类问题时有没有共同语言。

## 代价与已知边界

1. 弧是**按当前极角**实时算的，漂浮时线会跟着微微变形（这是刻意的：形状必须跟着卡片走，
   否则线会从卡片上穿过去）；也因此它不含任何随机量，同一份输入每次都是同一条弧；
2. 同环的弧不随张力变直（它是结构性走线）—— 张力说的是"线有多绷"，不是"走不走环"；
3. 跨环的径向切线是"朝外鼓"的近似，不做真正的避障（那需要 A*/可见性图，代价与收益不成比例）；
4. 同一对笔记之间的多条链接仍然只画一条（`count > 1` 在 tooltip 里）—— 平行束留给下一轮；
5. 连线仍然是 **React 渲染的 SVG**，漂浮仍是 20fps；把连线搬进 canvas（讨论里的 E 方案）
   是 taper / 发光 / 流动这些"更优雅"效果的前置，本轮没有做。
