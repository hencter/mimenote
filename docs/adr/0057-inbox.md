# ADR-0057：收件箱（独立目录 + 快速捕获）

- 状态：已采纳（本次交付）
- 日期：2026-10-12（用户诉求："收件箱"：独立目录、一行式快速捕获、一个能打开/归档的视图）
- 相关：ADR-0002（Markdown 单一真相）、ADR-0004（原子写与冲突令牌）、ADR-0012（移动改写相对链接）、
  ADR-0018（回收站）、ADR-0030（显示名不带 `.md`）、ADR-0044（frontmatter 时间挂钩）、
  ADR-0048（三格式 frontmatter）、设计 01（`[inbox]` 配置项）、设计 02（模板默认落点）、
  设计 03（`docs/design/03-inbox.md`，本决定的完整规格）

## 背景

"记下来再整理"这条路径在 MimeNote 里一直是断的：`note.new` 建在**当前选中的目录**
（`targetDirectoryForNewNote`），于是"随手记一条"要么落进某个已有项目目录（还没决定放哪，
却已经放进去了），要么先想清楚放哪（这正是当时想做不下去的事）。结果是用户要么开着别的
应用记，要么在 Vault 根堆一片 `未命名笔记 1/2/3`。

三件事让它现在能做成：

1. 捕获需要的写入能力**已经齐了**：`note_create`（唯一命名）+ `note_write`（带 mtime 版本
   令牌 + 原子写，ADR-0004）+ `note_move`（跨目录搬 + 全库链接改写，ADR-0012）；
2. 条目表是"打开 Vault 时扫一次"的现成快照（`vault-store.entries`），派生一份"收件箱列表"
   不需要任何新 IPC；
3. 「移动到…」对话框（`features/vault/MoveDialog.tsx`）+ `requestMove` 事件已经是**唯一的**
   移动入口——"归档"就是它的一个调用方，不必发明第二个目标选择对话框。

设计 01 已经定下配置 schema（`[inbox] dir = "Inbox"`、`dailyNote = false`），本 ADR 只回答
"判定、语义、粒度"这几个必须由一处说了算的问题。

## 决策

### 1. 收件箱 = Vault 内一个独立目录，"未整理"就是位置本身

条目判据只有一份（`domain/inbox.ts`）：**路径落在收件箱目录之内（含子目录）+ 是 Markdown**。
不引入第二套标记（frontmatter 字段 / `#未整理` 标签 / `.mimenote` 状态表）。

理由：标记与位置一旦并存就会互相打架——用户手工把文件拖出 `Inbox/`，标记不会跟着变，
界面随即开始说假话。位置作为判据的另一面是**它的代价被限制在一处**：只要"整理 = 移出目录"
这条规则不变，任何把笔记搬出 `Inbox/` 的既有路径（拖拽、命令面板的「移动到…」、
文件管理器里手拖）都自动等于"整理好了"，不需要为它们各写一遍状态同步。

非 md 附件**不是**条目：视图的动作全是笔记语义，附件混进计数会让"还剩 N 条"永远清不掉。

### 2. 默认捕获语义 = 新建一篇带时间戳的笔记；当日模式（`inbox.dailyNote`）作为开关

- 默认（`dailyNote = false`）：`Inbox/<YYYY-MM-DD HHmm> <首行摘要>.md` 一篇新笔记；
- 可选（`dailyNote = true`）：追加到 `Inbox/<YYYY-MM-DD>.md`。

理由（详见设计 03 §2.1）：收件箱唯一要做的事是**整理**，而"一条 = 一篇文件"让整理、打开、
计数都落在文件级动作上（复用 `openNote` / `note_move`）；当日模式把整理变成"从共享文件里
剪一段文本"，那件事没有原子性、也拿不到自己的 frontmatter 时间。

**为什么两种都实现**：设计 01 已经把 `inbox.dailyNote` 写进了配置 schema（默认 `false`），
留一个"文档里有、代码里没有"的开关比不做更糟；而"追加"这件事的原子性与 diff 表现必须
在实现里被真实验证过（否则它只是一段听起来成立的文字）。

### 3. 时间戳只到分钟，标题里带首行摘要

`YYYY-MM-DD HHmm`（本地时间，文件名里不能有 `:`）+ 首行摘要（压空白、截 24 字符、
经 `sanitizeAttachmentStem` 与宿主 `sanitize_file_stem` 同口径）。重名由宿主唯一命名兜底
（`我的第一篇 1.md` 那种纪律）。

理由：收件箱列表要"一眼看出这条是什么"，否则它就是一串时间戳；而"读每篇首行"要 N 次
`note_read`（1 千条就是 1 千次往返）。**代价**是文件名与正文重复了首行、改正文不会同步改
文件名——这条代价被接受，是因为收件箱里的笔记本来就活得很短（整理后就该改名/归档）。

### 4. 捕获正文 = 用户输入，**不加 H1、不加项目符号**（单篇模式）

宿主 `note_create` 写的是 `# 标题` 占位（我们自己填的标题），落盘时用 `note_write` 换成
用户的那句话 + 一个换行；frontmatter 时间挂钩写下的块**保留**（`mergeCapturedBody`）。

理由：加任何前缀都是在改用户输入，而"文件即真相"要求磁盘上的文件就是写下的东西。
当日模式是例外：那是**共享容器**，必须有一个"这是我们捕获的"的标记，所以追加写成
`- HH:mm 正文`（多行时续行缩进两格），这条差异在设计 03 §2.3 有明确说明。

### 5. 追加的三条纪律：基准令牌、保留字节风格、不自动重试

- `note_write` 带上读到的 `mtimeMs`：中间被改过就 `CONFLICT`、**一个字节都不写**；
- 写回经过 `domain/eol.ts` 的 `toEditorText` / `fromEditorText`：BOM 与 CRLF **原样保留**
  （否则一次捕获会让整个文件在 Git 里"全部改动"）；
- 冲突**不自动重试**：重试会掩盖"这中间有人改过"——而"绝不覆盖"是 ADR-0004 的纪律。
  用户看到错误、输入框内容还在，再按一次回车即可。

当日笔记**正被编辑且有未保存内容/处于冲突态时拒绝捕获**（编辑器内存与磁盘是两条写入路径，
同时成立必然有一方看不见另一方）；干净地开着是允许的，追加成功后编辑器会静默重载。

### 6. 归档 = 移出收件箱，走 `moveEntry` 那条链路，目标当场输入

收件箱视图的「归档…」在行内展开一个目标目录输入（`<datalist>` 给出现有目录、输入新目录由
宿主创建），提交后调 `app/actions.moveEntry`（宿主搬文件 + 改写全库链接 + 条目表换路径 +
标签页对账，ADR-0012）。**不设固定的"归档目录"**：那只会造出第二个收件箱。

**为什么不是 `requestMove` → `features/vault/MoveDialog`**：那个对话框由 `FileTree` 挂载，
而侧栏隐藏（`Mod+Shift+B`）时整格收缩、组件不在树上 —— 事件会**静默无效**。
"归档"是收件箱里的主动作，不能有"看情况失效"的入口。
目标若仍落在收件箱里（`isInboxPath` 判）则按钮置灰并说明"归档是移出这个目录"。

### 7. 搜索里不特殊对待收件箱条目

现状是 `ORDER BY -bm25(lines_fts) DESC, rel_path ASC, line ASC`（`mn-index/src/search.rs`），
没有目录/时间加权；`note_create` 与 `note_write` 都会 `indexer::update_note`，所以捕获的笔记
**立刻可搜**。决定不加权：
"收件箱里的更相关"是错的（收件箱意味着"还没决定放哪"，不是"更重要"），而且排序在 Rust 侧，
前端重排会让 `total` 与展示顺序不再同源。要加也得是宿主侧一个显式参数 + 可解释的权重。

### 8. 树侧只给钩子，不写树

`FileTree.tsx` 由 `filetree-columns` 持有。本决定只提供三个接口：
`isInboxPath(relPath, dir)`（唯一判据，禁止在树里比较 `'Inbox'` 字面量）、
`withInboxFirst(baseComparator, dir)`（包一层置顶，其余排序语义不动）、
`useInboxDir()` / `useInboxCount()`。置顶是**排序偏好**，不是扫描规则。

## 替代方案

| 方案 | 否决理由 |
| --- | --- |
| 用 frontmatter 字段 `inbox: true` 标记条目 | 与位置打架：拖出去之后标记还在，界面开始说假话；而且每篇要读 frontmatter（N 次 IPC）才能算计数 |
| 只算 `Inbox/` **顶层**、子目录当"已整理" | 同一件事出现两套判据（文件树在 Inbox 里看得见、收件箱视图看不见），漏算的观感是"东西丢了" |
| 只用当日笔记、把条目当行级对象 | 打开/归档/计数都要做文本手术，且没有原子性；一条笔记的删改不再是一个文件操作（与 ADR-0002 的姿态相悖） |
| 设一个固定的 `归档/` 目录、一键归档 | 造出第二个收件箱：用户还得从 `归档/` 再搬一次；而"去哪"本来就是用户此刻要决定的事 |
| 捕获框里支持模板展开（`@today` 等） | 展开需要交互（`@cursor` / `@prompt`），与"零交互入袋"冲突；依赖方向也不该让纯函数的捕获域依赖演进中的模板域 |
| 收件箱视图做成可停靠模块（ADR-0026 那套） | 本轮的授权面不含布局树；对话框已经能覆盖"看列表 + 打开/归档"，先交付语义、再谈停靠 |
| 捕获时顺便打开新笔记 | 打断正在做的事，而捕获的全部价值是"记完就走"；要立刻看，列表里点一下即可 |

## 影响

**新增**：`domain/inbox.ts`、`state/inbox-store.ts`、`features/inbox/**`、
`docs/design/03-inbox.md`、本 ADR、`tests/features/inbox/inbox.test.ts`。

**Lead 接线**：`App.tsx` 挂 `<InboxHost />`；`app/builtin-commands.ts` 登记
`inbox.capture`（`Mod+Shift+I`）与 `inbox.open`（`Mod+Alt+I`）并给 `when`。
`inbox.dir` **不用接线**：收件箱目录读 `settings-store.inboxDir`（已落地），store 不缓存第二份；
`inbox.dailyNote` 若要提供，接进 `inbox-store.setCaptureMode`。

**未新增**：任何宿主命令（`crates/**` / `src-tauri/**` 一个字节都没动）、任何运行时依赖。

**已知边界**：归档不搬附件（沿用 ADR-0012 的现状，Inbox 里会留下那几张图，但它们不算条目）；
捕获**不可撤销**（IPC 写入不进编辑器撤销栈），出路是删到回收站或改用单篇模式；
当日模式的"一条"在磁盘上是一段文本，没有单条粒度。
