# ADR-0014：链接 / 标签索引与全文搜索共用同一份判定键，跨会话落盘复用

- 状态：已采纳
- 日期：M5

## 背景

ADR-0008「后续修订」把**全文搜索**的跨会话复用做完了：打开 Vault 时按 `(path, mtime_ms, size)`
与缓存库对账，命中的笔记一行都不重写（1 万笔记：搜索这一路 4.7–5.0 s → 0.17–0.23 s）。
但那一轮**没有**解决剩下的大头：链接索引与标签索引是**内存索引**，不落盘，于是每轮打开
仍要读全库文件重建 —— 1 万笔记 ≈ 4.9 s，用户真实 Vault（3985 篇）每次打开都要等这几秒。

结论很清楚：要让"打开 Vault"降到对账的量级，**链接与标签也必须跨会话复用**。
要回答的问题有三个：

1. 落盘成什么形状（一行一段 blob，还是按路径/链接拆成表）？
2. 判定"没变"用什么键 —— 再造一套，还是复用已有的？
3. 复用之后，**所有改变索引的写入口**怎么保证落盘的那一份也跟着变？
   （这一条错了不会让当前会话出问题，而是让**下一次打开**拿到过期链接 —— 最难发现的一类错误）

## 决策

### 1. 落盘成三张表：凭证表 + 出链表 + 标签表

```sql
link_notes(path PRIMARY KEY, title)                       -- 每篇一行；title 是 frontmatter 的 title
link_refs (id, path, ord, kind, raw_target, alias, anchor, line)   -- 出链，ord 保留文档内顺序
tag_refs  (id, path, ord, tag, source, line)                       -- 标签，ord 保留抽取顺序
```

`link_notes` 同时充当**"这篇的落盘数据完整"的唯一凭证**：零链接零标签的笔记在另外两张表里
一行都没有，没有这张表就分不出"这篇什么都没有"与"这篇的数据丢了"。装载时**只有**在它里出现过的
路径才算有数据 —— 少了凭证就让这一篇退回"读文件"，于是库里少一份数据只会慢一点，不会错。

需要装的只有三样东西：出链、标签、frontmatter 标题。反向链接（`LinkIndex::backlinks`）是出链的
**纯投影**、`by_path`/`by_stem`（解析消歧用的索引）由路径直接算出来 —— 都不落盘：
它们不是"另一份真相"，存下来只会多一份可能过期的副本。

**为什么不落成一整段 blob**（`LinkIndex` 序列化成一行）：

| 维度 | 三张表（选定） | 整库一段 blob | 每篇一段 blob |
| --- | --- | --- | --- |
| 打开时的装载 | **37–50 ms**（1 万篇 / 2 万条链接，实测） | 反序列化整份索引，且要一次读出全部字节 | 同一量级（1 万个小 JSON 的解析） |
| 单篇保存的更新成本 | **+0.68 ms/篇**（实测：只删写这篇的几行） | 每存一篇要把**整份索引**重新序列化 + 写回（1 万篇的链接数据 ≈ 2–3 MB），是 ms→百 ms 级的退化 | 重写这一篇的那一行，成本与表方案相当 |
| 冷启动写放大 | 链接侧 4.9–5.1 s → 5.4–5.5 s（+5%，多写约 3 万行） | 一次性序列化，冷启动更快 | 比表方案再省约 2 万次插入（约 0.1–0.15 s） |
| 空 payload vs 丢数据 | 由 `link_notes` 凭证区分 | 由那一行是否存在区分 | 同左 |
| 依赖 | 无新增（SQL 原生类型） | 需要 `serde_json`（`mn-index` 目前没有这条依赖） | 同左 |
| 可诊断性 | 可以直接 SQL 查某一篇的落盘内容 | 要写解码脚本 | 半可读 |

决定性的是第二行：**单篇保存是最高频的写路径**（每次 Ctrl+S、每次自动保存），整库 blob 把它从
微秒级变成"重新序列化整个索引"；而表方案在保存上只碰这篇的几行。表方案多花的钱在冷启动
（一次性多写 3 万行 ≈ +0.26 s，占整库重建的 5%），那是**每次都要忍受**与**只付一次**的差别。

### 2. 判定键复用 `notes_meta`，不造第二套

链接/标签的落盘数据与 `lines`、`notes_meta` **共用同一张判定表**（`path` + `mtime_ms` + `size`，
口径与 ADR-0004 的 mtime 版本令牌一致）。理由不是省一张表，而是**避免"两套键"必然带来的中间态**：
两份键各自为政时，必然出现"文件变了一半"的状态（行是新的、判定键是旧的），而那种状态
没有任何安全的解释方式 —— 要么白重建，要么复用出过期数据。

推论：链接/标签的数据与搜索的行 **要么一起提交、要么一起回滚**。实现上靠两件事：

* 写透句柄（`IndexStore`）与 `SearchIndex` **共用同一个连接**（`Arc<Mutex<Connection>>`）。
  两个连接就是两套事务，一个成功一个失败时库里会留下"行是新的、判定键是旧的"；
  同一个连接 + `in_transaction` 的 `is_autocommit` 判断，让写穿透自动参与构建那个大事务；
* 任何改写落盘数据的路径**都在同一个事务里删掉这篇的判定键**（`replace_note` 的最后一步）：
  写盘时手上没有文件 mtime/size，"不知道"只能表达成"下一篇必须重读"。

### 3. 三条不变量（写代码时不许打破）

1. **落盘数据与判定键同一个事务**：判定键一旦对上，索引就必须真的可复用；
2. **任何改写落盘数据的路径都作废判定键**：宁可让下一篇多读一次文件，也不留下一个被信任的旧快照；
3. **装回内存与解析写内存走同一段记账代码**（`LinkIndex::insert_parsed`）：复用回来的索引与
   从零重建的索引逐条相同，是**代码结构保证的**，不是"两处实现碰巧一致"。
   为此 `upsert` 被拆成"解析（`parse_note`）→ 落盘 → 记账（`insert_parsed`）"三段，
   复用路径只替换第一段的来源（从库里读 `NoteIndexData`）；标签同理（`TagIndex::replace`）。

违反其中任何一条的后果都不是"慢了"，而是**复用出过期链接**。

### 4. 写穿透挂在 `LinkIndex` 上，而不是加在宿主

所有改变链接索引的入口最终都落到 `LinkIndex::upsert` / `remove` 上（保存、新建、删除、
改名、跨目录移动 —— 后两者在 `rename.rs` 里）。把镜像写在**这两个方法内部**，意味着：

* 不需要在宿主里维护一张"哪些操作要同步索引"的清单（那种清单一定会漏掉一条）；
* `rename.rs` 一行都不用改（它本来就在改自己的链接改写逻辑）；
* 新增写入口的人只要用 `upsert`/`remove`，落盘就自动跟上。

`clear()` 顺手解绑句柄：清空之后这个索引不再属于任何 Vault，继续用它写盘等于把上一个 Vault 的
解析结果写进当前缓存库（切换 Vault 的顺序是 `reset → clear → spawn_build`，新一轮会挂上新句柄）。

### 5. 写穿透是**加速器**，不是正确性的前提

缓存库不可用（只读、磁盘满、锁冲突、Vault 只读）时：拿不到 `IndexStore`，索引照常建在内存里，
只是回到"每次打开重建"的老路。构建被取消 / 对账失败时**立刻解绑**（`detach_store`）——
库里的内容已经回滚，内存索引与它不再是同一份快照，继续写盘才会把半截数据混进去。

失败模式因此收敛成一句话：**写盘失败 / 没写盘，最多让下一篇多读一次文件**（判定键也跟着被作废），
绝不会让一个对得上的判定键对应一份旧数据。

## 代价与已知限制

| 项 | 实测 / 说明 |
| --- | --- |
| 打开 Vault（1 万笔记，Vault 没变） | **9.7–9.9 s → 0.25–0.34 s**（约 30×）。其中对账 0.17–0.23 s（扫 `notes_meta ∪ lines` 的路径集合，ADR-0008 已记录的成本）、装载 0.04–0.05 s（10k 篇 / 20k 链接 / 6.7k 标签） |
| 打开 Vault（改了 1 篇） | **0.26–0.31 s**（只重读那一篇） |
| 冷启动整库重建的写放大 | 链接侧 4.9–5.1 s → 5.4–5.5 s（**+5%**，多写约 3 万行）。这一轮只发生在"第一次打开 / schema 升级 / 库损坏"之后 |
| 单篇保存的增量成本 | **+0.68 ms/篇**（0.015 → 0.693 ms，含一次事务提交；每次 Ctrl+S 都付这笔钱，量级可忽略） |
| 漏检边界（**不变**） | 判定键只有毫秒 mtime 与字节数：**同一毫秒内、字节数又完全相同**的内容改动会被判成"没变"。与 ADR-0004 的冲突检测同一取舍，内容级校验要引入哈希（本 ADR 没做） |
| 复用后仍要重读的场合 | 缓存库打不开（降级）、构建被取消、`schema` 升级后的第一次、`link_notes` 少一份凭证（自愈：那一篇退回读文件） |
| 库里的数据看不懂时 | 装载返回错误 → 整轮退回读文件重建（不用看不懂的数据凑索引），并记 warn。**没有**顺手清库：那次打开会白读一遍，但不会用错数据 |
| 目录删除 | 落盘数据的子树清理用转义后的 `LIKE 'prefix/%'`（`_`/`%`/`\` 都转义），与 `lines` 的既有做法一致 |
| 别名的落盘点 | 表结构跟 `LinkRef` 字段一一对应；**新增字段时 `SCHEMA_VERSION` 必须 +1**（口径变了就不能沿用旧口径的行） |

## 影响

- `docs/architecture.md` §6 与 §8 里"链接/标签索引每轮打开都要读全库文件 ≈ 4.9 s"这条限制
  已不成立，待统一更新（本 ADR 只记录设计与实测）。
- 缓存库的 schema 升到 **v3**：老库（v2）第一次打开整库重建（既有行为）。
- 宿主（`indexer.rs`）新增一条对前端可见字段 `IndexStatus.reusedNotes`（见下），
  其余 IPC 契约不变；日志里多报"复用 N 篇、对账 M ms"。
- `crates/mn-index/src/tags.rs` 新增一个**只在复用路径上用到**的方法 `TagIndex::replace`
  （用已经抽取好的 `TagRef` 重算一篇的标签），`upsert` 改为调用它 —— 目的是让两条路的
  归一化/过滤/反向索引记账**同一份代码**，而不是在 lib.rs 里照着重写一遍。
