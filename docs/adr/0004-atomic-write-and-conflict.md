# ADR-0004：原子写 + mtime 版本令牌 + 显式冲突解决

- 状态：已采纳
- 日期：M1

## 背景

Markdown 文件可能同时被外部程序修改：用户在 VSCode/IDE 里改、OneDrive/Dropbox 同步、Git checkout 覆盖。天真的"直接写"会产生两类事故：

1. **半写文件**：写到一半崩溃/断电，笔记变成半截内容（不可恢复）。
2. **静默覆盖**：用户在别处改了文件，应用内存里是旧内容，保存时把对方的改动吞掉。

两者都是**数据丢失级别**的问题，必须在 M1 就解决。

## 决策

### 1. 原子替换

写入统一经 `mn_core::atomic::write_atomic`：

```
同目录创建临时文件 .mimenote-<rand>.tmp
  → write_all → flush → sync_all（fsync 数据落盘）
  → rename 覆盖目标（Windows 用 MoveFileEx REPLACE_EXISTING 语义，由 tempfile::persist 保证）
```

同目录是必须的：跨卷 rename 不具备原子性。临时文件前缀固定，便于崩溃后人工识别与清理。

### 2. mtime 作为版本令牌

- 读文件时返回 `mtimeMs`，前端保存时原样回传 `baseMtimeMs`。
- 写前在**同一把写锁内**重新 `stat`，与 `baseMtimeMs` 比较，不等则拒绝写入，返回 `CONFLICT` + `currentMtimeMs`。
- 写入成功后返回新的 `mtimeMs`，前端更新基线。

### 3. 冲突必须由人决定

UI 收到 `CONFLICT` 后进入冲突态，横幅给出两个选项：

- **覆盖保存**：以内存内容为准（`force=true`），用户明确知情。
- **重新加载**：丢弃内存改动，从磁盘重读。

**任何情况下都不静默覆盖，也不自动丢弃用户输入。**

## 理由

- 原子替换把"半写文件"从可能变为不可能（最坏情况是留下一个 `.tmp`）。
- mtime 校验成本近零（一次 `stat`），却能挡住绝大多数外部改写。
- 冲突是可解释的状态而非异常：用户看得懂"文件被外部修改了"，看不懂"保存失败"。

## 代价与限制

| 限制 | 说明 / 缓解 |
| --- | --- |
| 同毫秒内两次独立修改可能漏检 | 概率极低；M2 增加内容哈希作为二级令牌（写入后校验读回哈希） |
| 某些同步盘（OneDrive）rename 语义异常 | 写失败时保留临时文件并报 `IO` 错误，不静默降级为直写；M2 增加"直接写 + 备份"回退路径 |
| 无合并能力 | 不做三方合并（超出笔记工具预期）。M2 可提供"另存为冲突副本"（`xxx.conflict-<ts>.md`）作为第三选项 |
| fsync 影响保存耗时 | 单文件 fsync 在 SSD 上通常 <10ms，预算 50ms 内可接受；状态栏可见实测耗时 |

## 影响

- 所有写路径（含未来的插件写入 API）必须复用 `write_atomic`，禁止 `fs::write`。
- 删除同理走"移动到回收站"而非 unlink（见 `mn-core/trash.rs`）。
