# ADR-0050：行内 `#标签` 高亮（一份判据，两处消费）

- 状态：已采纳（已交付）
- 日期：v0.3.0 之后（UI 走查轮）
- 相关：ADR-0006（标签抽取）、ADR-0027（标签过滤）、ADR-0009（所见即所得）

## 背景

标签一直是"数据里有、正文里看不出来"：`#项目/子项` 在编辑器里与普通文字完全同色，
阅读视图也一样。用户要在正文里认出它们是标签。

难点不在染色，而在**"什么算标签"必须与宿主索引一致**：索引（`mn-core::tags`）认的
写法与界面上染色的写法只要差一点，就会出现"索引里有、界面上不亮"或者反向的
两个真相。

## 决策

### 1. 判据只有 `domain/inline-tags.ts` 一份，而且只做"行内"

`inlineTagSpans(text)` 输入**一行文本**，输出标签的**区间**（不是文本）：

- `#` 前必须是行首或空白，后面必须是 Unicode 字母/数字/`_`/`-`/`/`；
- 纯数字不算（`#123` 是 Issue 号）；行首 `# 标题` / `## 标题` 不算（那是 ATX 标题）；
- 尾部的 `/` 归分隔符（`#项目/` 的区间到 `项目` 为止）。

返回区间而不是文本，是因为两个消费方都需要**位置**（编辑器加装饰、阅读视图插
`<span>`）；只给文本会逼调用方自己 `indexOf`，同一行里重复出现的标签必然定位错。

### 2. 两处消费同一个区间函数

| 消费方 | 落点 | 产物 |
| --- | --- | --- |
| 所见即所得 | `cm/live-preview/build.ts` 在**可见行**上加 `Decoration.mark` | `<span class="mn-inline-tag">` |
| 阅读视图 / 导出件 | `domain/markdown-core.ts` 的 markdown-it 规则（`mn_inline_tags`） | 同一个类名 |

样式只有一份（`app.css` 的 `.mn-inline-tag`）⇒ 编辑器与阅读视图的观感天然一致。

### 3. "哪些行不该扫"归块级信息管，不归扫描器

代码块、行内代码、frontmatter、链接目标里都不该染色 —— 但那需要块级/文档级信息
（围栏状态、已占用的装饰区间），行内扫描器看不到，也不该假装看到：

- 编辑器路径：跳过 `codeRanges` 与已被 `Link`/`Image` 装饰占用的区间
  （`collection.isClaimed`），frontmatter 区域整体跳过；
- 阅读视图路径：markdown-it 的 `core` 规则只处理**正文 `text` token**，
  并在 `heading_open..heading_close` 之间与链接内部跳过 —— 代码块/行内代码在
  更早的 token 化里就已经是 `code_inline` / `fence`，天然不是 `text`。

两处都有各自的"该跳过什么"用例（`tests/inline-tag-style.test.ts`）。

## 代价与已知边界

1. 编辑器里每个可见行都要跑一次正则（`buildLivePreviewDecorations` 只算视口，
   见 ADR-0009/0020）：行内扫描是纯字符串运算，量级远小于它旁边的 wikilink 遍历；
2. **不做**"点标签就按标签过滤"这类交互（标签面板已经有一份完整入口）：
   正文里的标签是**显示**，不是控件；
3. 与索引判据的一致性是靠**同一份口径写法**保证的，不是共享代码（一个在 Rust、
   一个在 TS）。两边都有用例钉住同一批边界（纯数字、层级、尾部斜杠、行首标题）——
   改一边必须同时改另一边，这条纪律写在 `inline-tags.ts` 的文件头。
