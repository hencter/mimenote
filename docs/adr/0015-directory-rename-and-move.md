# ADR-0015：目录重命名与目录移动（连同整棵子树的链接改写）

- 状态：已采纳
- 日期：M5

## 背景

M2/M3 交付了**单篇**笔记的重命名与跨目录移动（`note_rename` / `note_move`），共用一条链路
（`crates/mn-index/src/rename.rs` 的 `relocate_note`）：换位置 → 全库指向它的链接按字符 span
精确改写 → 索引增量同步。ADR-0012 又把"被移动笔记**自身正文**里的相对链接"补齐了。

`docs/architecture.md` §8 第 2 条与 `README.md` 的「已知限制」里一直写着同一条边界：
**目录重命名与目录移动仍未做**（"要连同整棵子树改写链接"）。本轮把它做掉。

要回答的问题有三个：

1. "搬一棵子树 + 改全库链接"要不要另写一套？（直觉上形状不同：一个旧目标 → 一棵新前缀）
2. 顺序与原子性怎么排？磁盘上搬 1000 个文件不是原子的。
3. 一棵 1000 篇的子树搬完要多久，值不值得做进度与取消？

## 决策

### 1. **不另写一套**：目录搬迁 = "每篇按新前缀 relocate"，复用 `rename.rs` 的机制

新增 `crates/mn-index/src/dir_move.rs`，只补**目录特有**的那两件事，其余全部复用：

| 复用了什么 | 出处 |
| --- | --- |
| 候选集机制（"谁指向它"由索引回答，**绝不**全库读文件） | `LinkIndex::resolve` / `paths_under` / 新增的 `paths()` |
| 一条链接的新目标文本（相对路径换算、裸名保持、Markdown 扩展名写法） | `rename.rs` 的 `new_target_for` + `TargetStyle`（特意抽成共用） |
| 字符 span 精确替换 + 回读校验（含空格自动补 `<>`） | `rename.rs` 的 `replace_verified` 同一套写法 |
| BOM / CRLF 保真、跳过代码块与行内代码 | `extract_links_with_spans` + `split_inclusive('\n')` |
| 索引增量同步（不整库重建） | `LinkIndex::upsert` / `remove`（写穿透见 ADR-0014） |
| 落盘错误语义（`ALREADY_EXISTS` 原样透给 UI、绝不覆盖） | 同 `relocate_error` |

**为什么坚持复用**：另写一套的代价不是"多写 300 行"，而是两边的 Markdown 形态支持度会漂移 ——
表现是"单篇移动改对了、目录移动没改"，而这种缺陷只有用户撞上才会发现。共用 `new_target_for`
以后，"目录搬迁与单篇搬迁的写法规则"在结构上不可能分家。

### 2. 链接改写 = **前缀映射**，而不是"按路径算术重算一切"

对候选集里的每一篇、每一条链接：

1. **这条链接原本指向谁**（`LinkIndex::resolve`，与反链面板/索引完全同一套规则）；
   指向的东西在子树里 → 把它的路径按「旧前缀 → 新前缀」映射；
   指向子树**之外** → 看下一步；
2. 索引解析不到（悬空链接、图片、PDF）→ 若文本本身就是**按 Vault 根口径写的前缀路径**
   （`[[项目/乙]]`），做同一套前缀映射（搬迁前悬空、搬迁后依然悬空，但"指向新目录下那一篇"
   的意思被保住了）；否则按"相对本文件旧目录"做路径算术，再映射；
3. 用与单篇移动**同一个** `new_target_for`，按本文件**改写后**的目录表达；
4. 结果与原文一字不差 → **不写盘**。

这个组合自然给出两种直觉上不同的行为，都不需要特例：

| 源文件在哪 | 表现 |
| --- | --- |
| **在子树里**（跟着一起搬） | 源与目标的相对位置不变 ⇒ 换算结果与原文一字不差 ⇒ **一个字符都不动**（子树内部保持最小 diff、mtime 也不跳） |
| **在子树外**（原地不动） | 换算结果必然变化 ⇒ 链接改成指向新位置 |

**反例（明确否掉的做法）**：不要用"把链接文本里的旧目录名替换成新的"这种纯文本做法 ——
源文件跟着搬时那个文本是**相对路径**（`[[../子/甲]]`），替换只会写出悬空链接。
本 ADR 的第 2 步之所以是"先解析出真实目标，再映射"，就是为了避开它。

### 3. 裸名 wikilink：只处理"原本指向子树里那篇"的，且显式判"同不同层"

单篇移动刻意不碰裸名（`[[乙]]`）：它按文件名主干解析，改写成路径反而更长。
目录搬迁**必须**碰那些原本指向子树里的裸名 —— 子树一换名字，同一条 `[[乙]]` 就可能落到
全库**另一篇**同名笔记上（静默的错误指向，比"链接变长"严重得多）。

规则是"加不加目录前缀"而不是"一律改成相对路径"：源与目标一起搬、还在同一层时，写出来仍是
裸名（`[[乙]]` 在 `项目/` 与 `归档/` 里含义相同 ⇒ 最小 diff），只有真的需要区分时才带上目录段。

### 4. 顺序：**先算全部计划 → 搬整棵目录 → 写回调改 → 同步索引**

1. **先算计划**：此时索引里还是旧路径，才能用同一套解析规则找出"谁指向它"，以及每条链接的落点；
2. **搬整棵目录**：同卷一次 `fs::rename`（`mn_core::atomic::move_dir`）—— 与子树大小无关，
   而且**整体成败**；跨卷（Vault 里有联接目录指向另一个卷）退回递归复制 + 删源；
3. **写回被改写的文件**（`write_atomic`）；
4. **同步索引与全文搜索**：旧路径消失、新路径立刻可查（不等重扫）。

**为什么搬整棵目录而不是逐篇 `move_note`**：逐篇搬要 N 次系统调用，中途失败还会留下
"半棵子树"；整棵 `rename` 把这两个问题一起消掉。文件夹拖到文件夹上如果是"已存在的同名目录"，
`fs::rename` 在 Windows 上会失败、在别的平台上语义不同 —— 因此**搬迁前显式拦一次**
（`occupied`），绝不合并两棵子树。

### 5. 失败语义：搬迁失败 → 什么都没动；改写失败 → 记日志、不回滚

| 失败点 | 用户看到什么 |
| --- | --- |
| 搬家本身失败（目标被占用、权限、跨卷回退也失败） | 返回错误码（`ALREADY_EXISTS` / `IO`），**磁盘上一个字节都没动过** |
| 某一个被改写文件写失败 | 搬迁**照常成功**；那一篇被排除出 `updatedLinks` 并记 warn。它的链接暂留旧目标 —— 用户会看到**悬空链接**（可见、可再拖一次修好），而不是一个"报成功但目录其实没搬"的假象 |
| 索引同步某一步失败 | 只记 warn：索引是可重建的缓存，下一次重扫自愈（与 ADR-0014 同一口径） |

**为什么不回滚搬迁**：目录已经在新位置了，回滚只会制造更大的不一致（而且回滚本身也可能失败）。
这与单篇搬迁的既有取舍一致（`relocate_note` 的"部分失败不回滚"）。

### 6. 索引同步：先整批删、再整批写；外部引用者也要重新入库

`sync_indexes` 三步：

1. `LinkIndex::remove` + `SearchIndex::remove_note` 逐篇清掉旧路径（**先整批删完再整批写**：
   `paths_under` 读的是内存记账，边改边读会漏掉后半截）；
2. 子树里每一篇按新前缀 `upsert`（被改写过的直接用计划里的文本，与磁盘逐字相同；其余现读一次）；
3. 子树**之外**被改写的引用者也 `upsert` —— 它们的路径没变、正文变了。漏掉这一步的表现是
   "反链面板还指着旧路径、链接面板显示悬空"，而磁盘上其实已经改好了。

全文搜索那一路刻意**逐篇删除**（`remove_note`）而不是删目录：`drop_dir` 的连带删除只覆盖
`lines` 表，判定键（`notes_meta`）若留在库里，下一次打开就会拿一个对得上的键去复用一个已经
不存在的路径 —— 属于 ADR-0014 点名的"看不见的过期数据"。

### 7. 顺带修掉一个既有缺陷：索引的解析不折叠相对路径里的 `..`

搬迁会把链接改写成 `../目标` 形态（`别的/引用.md` 里的 `[[../工程/乙]]`），而
`LinkIndex::resolve_target` 原来把带 `/` 的目标按"相对当前目录 / 相对 Vault 根"拼出来之后
**不折叠 `.` 与 `..`**，`by_path` 的键又是规范路径 —— 于是"搬迁之后链接全部悬空"。

修法：拼接候选后过一遍 `fold_dots`（`别的/../工程/乙` → `工程/乙`），语义与
`mn_core::links::join_relative` 一致。这条修复对**单篇**移动同样必要（它写出的
`[[../归档/乙]]` 在旧实现里解析不到）。

### 8. 契约：复用 `RenameOutcome`，不新增错误码

- 命令：`dir_rename`（`relPath, newTitle, updateLinks?`）与 `dir_move`
  （`relPath, targetParentRel, newTitle?, updateLinks?`），出参**复用 `RenameOutcome`** ——
  一次目录搬迁要交代的仍然是"旧路径 / 新路径 / 被改写的文件与条数"，前端因此能复用同一套
  状态收尾。唯一的字段语义差别是 `newMtimeMs`：目录不是版本令牌的载体（ADR-0004 的令牌是
  **文件** mtime），因此如实报 `0`，而不是塞一个会被误用的数字；
- **不新增错误码**："把目录搬进它自己/它的后代"用 `PATH_INVALID` + 一句能读懂的原因
  （`不能把目录搬到它自己或它的子目录里（项目）`）。它是路径问题、不是新的一类失败，
  而新增一个错误码要在 Rust 与 TS 两侧同步维护（见 `error.rs` / `ipc/types.ts` 的白名单口径）；
- 前端：`domain/drag.ts` 的落点判定新增**文件夹**类型（`DragPayload.kind`）与
  "拖进自己/后代 = 无效落点 + 原因"；F2 / F6 对文件夹同样可用（`renameEntry` / `moveEntry`
  按条目类型分派到对应的宿主命令）。

### 9. 状态收尾：标签页必须在**条目表变化之前**换前缀

条目表一变，`tabs-store` 的 `pruneMissing` 就会把旧路径的标签剪掉，而 `syncFromNote` 只会把
"当前文档"补回列表**末尾** —— 顺序反了标签顺序就被打乱（原来在第 1 个的标签跑到最后一个）。
因此目录搬迁的收尾顺序固定为：**先换标签 → 再换整棵子树的条目 → 再收敛正在编辑的文档**。

## 代价与已知限制

| 项 | 说明 |
| --- | --- |
| "移动到它自己" = 无操作 | 与单篇移动同一口径（"移到自己所在目录 = 无操作"）。真正的错误（搬进自己的**后代**）仍然拒绝 |
| 跨卷退回"复制 + 删源" | 与 `move_file` 同一取舍：只在 `rename` 必然失败时走，那条路**没有原子性**（中途崩溃会留下源和目标各半份），会记 warn |
| 部分改写失败不回滚 | 见决策 5：用户会看到悬空链接（可见、可再操作），而不是假的"全部成功" |
| 依赖索引已建好 | 与单篇改名同一前提：索引构建中搬迁会漏掉尚未收录的引用者（`docs/architecture.md` §8 第 10 条已记同类边界） |
| 被搬走的笔记里**靠后缀解析**的路径链接会被改写成相对写法 | `[[子/丙]]` 写在 `项目/甲.md` 里靠"路径后缀 ∩ 全库唯一"命中；子树换名字后不再唯一，因此必须改成相对写法（`工程/子/丙`）。判断依据是"新写法在索引前两条规则下是否命中"，不查全库 |
| 裸名链接的漂移仍不修（ADR-0012 的既有边界） | 子树**之外**的裸名链接指向子树里的某篇时也会被改成路径形式；子树**内部**的裸名按"同层保持裸名"处理，跨层时才带目录段 |
| 引用式定义行、反斜杠目标、越出 Vault 根的目标 | 与 ADR-0012 的代价表完全一致（本次没有扩大范围） |
| 不提供进度与取消 | 实测见下文：搬迁本体与**被引用的篇数**成正比（1000 篇、50 篇被引用：**2.0 s**），而不是与子树大小成正比。因为会到秒级，最终实现给了一次 toast（复用对话框 busy 态 + "耗时 N ms"文案）与**分段的日志**，**没有**做一个半成品的取消机制 —— 真要做得先回答"取消到一半的搬迁怎么交代"（那是一个独立的设计问题） |
| `.mimenote` 内部目录不参与搬迁 | 回收站/缓存库/用户片段都在里面，搬它只会让缓存库自相矛盾；实测拒绝并给出原因 |

### 实测（本机 SSD，`#[ignore]` 基准，见 `mn-index/src/dir_move.rs`）

`cargo test -p mn-index --release -- --ignored --nocapture`

| 场景 | 结果 |
| --- | --- |
| 1000 篇目录 + **50 篇**被引用（贴近典型 Vault） | **2.0 s**（改写 50 个文件 / 50 条链接） |
| 1000 篇目录 + 500 篇内部链接 + 200 篇外部引用（压力档） | **8.3–10.4 s**（改写 700 个文件 / 700 条链接） |
| 四段分解（1000 篇 / 50 篇被引用） | 计划 **742 ms** / 搬树 **2 ms** / 写回 **405 ms**（50 个文件）/ 索引同步 **720 ms** |

瓶颈归因（按重要性）：

1. **每个被改写文件的 `write_atomic`（约 8 ms）** —— `700 × 8 ms ≈ 5.5 s`。主因是它按 ADR-0004 的纪律**逐文件 `fsync`**
   （单独测 700 次 `write_atomic` = **5.5 s**，与搬迁里的写回段完全对得上）。换句话说：
   **搬迁成本与"被引用的篇数"成正比，与子树大小无关** —— 搬树本身是常数级的（**2 ms**）；
2. **索引同步每篇读一次文件**（1000 次读 ≈ 0.7 s）：被改写过的用计划里的文本，其余按会话内缓存重读；
3. **计划一趟遍历全库出链 + 折叠相对路径**（0.7 s）：不做存在性检查、不读全库文件，但每条链接都要解析一次。

**结论**：1000 篇的目录搬迁是**秒级**（2–10 s，取决于有多少篇被引用），因此值得在界面上给一次明确反馈，
但不值得为它引入一个半成品的取消机制。

## 影响

- `docs/architecture.md` §3.1 新增两条命令；§8 第 2 条与 `README.md` 的「已知限制」里
  "目录重命名与目录移动仍未做"这条已经不成立，待统一更新；
- `crates/mn-index/src/lib.rs` 新增三个**只读**工具：`paths_under` 改为段感知
  （原来的 `starts_with` 会把 `归档2/甲.md` 当成 `归档` 的后代）、`paths()`（目录搬迁算候选集
  用的一趟线性遍历）、`remap_prefix`（前缀映射，宿主与搬迁共用），以及 `fold_dots`
  （决策 7 的修复）；
- `crates/mn-index/src/rename.rs` 的 `TargetStyle` / `new_target_for` / `replace_verified`
  的写法被抽成"目录搬迁也能用"，目录改名与目录移动的入参校验
  （`dir_rename_targets` / `dir_move_targets`）也落在同一处；
- 宿主（`commands.rs`）新增 `dir_rename` / `dir_move` 与整棵子树级别的条目表替换
  （`apply_renamed_dir`），前端新增 `renameDirectory` / `moveDirectory` / `renameEntry` /
  `moveEntry`，Mock 适配器同步实现同一套行为（否则 UI E2E 会给出假绿）。
