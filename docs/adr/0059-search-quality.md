# ADR-0059：搜索质量 —— 每篇命中上限、按词高亮、按需计数（不动索引 schema）

- 状态：已采纳
- 日期：2026-10-12
- 前置：ADR-0008（全文搜索用 FTS5、中文逐字分词）、ADR-0014（落盘索引）、设计 05（`docs/design/05-search.md` 的实测缺陷清单）

## 背景

设计 05 用同一套语料（1 万篇 / 301 100 行 / 缓存库 114.7–116.5 MB，SQLite **3.50.2**）量了当前搜索的六件事。
其中三条是**实测出来的缺陷**，两条是"用户能看见但实现里根本没有"的缺口：

1. **一篇笔记能吃掉整个结果列表**：61 篇共 120 行命中时，`limit=50` 返回的 50 条**全部来自同一篇**
   （`probe_note_flood`）。而前端的 Mock 从契约诞生起就有每篇 5 条的上限（`MOCK_HITS_PER_NOTE = 5`），
   并有一条用例钉着"每篇最多 5 条、`total` 是全部命中数" —— 也就是说 **Mock 比真机好**；
2. **多词查询一个高亮都没有**：前端拿**整串**查询去片段里找连续子串，而宿主是"逐词 AND"；
3. **高亮用的是输入框里的当前串，不是产生这批结果的那次查询**：在途期间会把新词标到旧结果上；
4. `COUNT(*)` 白花一半：`total` 只在"可能超过 `hits` 条数"时才需要，现在每次都跑（实测 12–56 ms，
   命中 29 万行时还要多扫一遍）；
5. 多词零命中时面板只说"没有匹配的正文内容"，不告诉用户"多个词必须在同一行"（行级索引的固有限制）。

中文子串检索本身**没有缺陷**：逐字切开 + 相邻短语的 1/2/3+ 字查询实测全部命中，单字也命中；
`trigram` 虽然可用，但 3 字以下不命中，会把中文最常见的查询打回零结果（设计 05 §1.3）。

## 决策

### 1. 每篇最多 5 条命中：SQL 多取一批行，在 Rust 里按篇截断

`SearchIndex::search` 先用 `QUERY_MATCH`（不改排序、不改 SQL 结构）取回
`budget = clamp(limit × 8, limit, 1024)` 行，再在内存里按 `rel_path` 计数、
每篇只保留前 `HITS_PER_NOTE = 5` 条，截到 `limit` 条。

- **为什么是 5**：前端 Mock 的 `MOCK_HITS_PER_NOTE = 5` 与 `apps/desktop/tests/search.test.tsx`
  的用例已经把"每篇 5 条"写进了前端可见行为。这不是新造的排序口径，而是**修 Mock/真机不一致** ——
  真机现在比 Mock 差（一篇吃掉 50 条），修完之后两边一致。
- **为什么多取而不是在 SQL 里做**：实测搬运行数不要钱 —— `LIMIT 50 / 250 / 1000` 分别是
  27/28/28 ms（`关键词`）与 666/599/605 ms（`全文搜索`）：成本全在 `bm25()` 打分与排序，
  它们本来就要遍历全部命中。预算 8× 是为了给"同一篇在窗口里出现很多次"留余量
  （窗口内每篇最多出现 25 次时仍能凑满 `limit` 条）。
- **排序口径不变**：`hits` 仍是"`score` 降序 → `relPath` 升序 → `line` 升序"这个**全序的子序列**
  （在已排序的行上原地筛选，不重排），IPC 契约、前端行为都不变。
- **`total` 语义不变**：仍是全部命中**行**数（含被每篇上限砍掉的那些），
  面板"还有 N 条未显示"照旧。
- **取不满就少给**：极端情况下（取数窗口里只有极少数笔记、且都被截断）返回条数可能少于 `limit`。
  选择"少给几条"而不是"多给同一篇"，这是本决策的取向。

### 2. `total` 按需计数

先取 `hits`；若这次**没有取满预算**（说明命中集已穷尽）→ `total = 取回的行数`，**不跑 `COUNT`**；
只有取满预算时才跑 `COUNT_MATCH`。

- 实测省下的是 `关键词` 10–12 ms、`全文搜索` 54–56 ms 的一次全量扫描；
- 语义严格不变：没取满 ⇒ 命中总数就是取回行数；取满 ⇒ 仍有可能是"恰好等于预算"，必须计数。

### 3. 高亮：按词展开，且用 `settledQuery`

`match.ts` 新增 `searchHighlightTerms(query)` 与 `substringMatchIndicesForQuery(text, query)`：
按空白切词（与宿主 `query_terms` 同口径：丢掉不含字母数字的词、最多 16 词）、逐词找**所有**出现位置、
合并去重后升序返回；单扩展 Unicode 导致小写化长度不一致时退回大小写敏感匹配（沿用既有纪律：
宁可不命中，不把 `<mark>` 标在错的位置）。

`CommandPalette.tsx` 改用 `search.settledQuery`（产生这批结果的那次查询）驱动高亮，而不是
输入框里的当前串 —— 在途期间旧结果不会被新词错标。

### 4. 空态如实说明"多个词必须出现在同一行"

查询含 ≥2 个词且零命中时，空态文案补一句说明。这是对第 5 条限制的**如实告知**，
不是把它藏起来（本轮不修跨行 AND，见「替代方案」）。

### 5. 不动索引 schema，不 bump `SCHEMA_VERSION`

本轮所有改动都在"查询构造 / 结果装配 / 展示"层：`space_cjk`、哪些行进索引、大小上限、
FTS 表结构与 `tokenize` 全部不变，落盘的行与 FTS 内容**一个字节都没变**。
所以旧缓存库继续可用、打开 Vault 不需要重建 —— `SCHEMA_VERSION` 保持 4。
（对照：任何**索引口径**的变化都必须 +1，见 `search.rs` 里 `SCHEMA_VERSION` 的文档。）

### 6. 不改分词路线与查询语法

继续 `space_cjk` + `unicode61 remove_diacritics 2`（理由见「替代方案」）；
不加 OR/短语/排除词语法 —— ADR-0008 §4 的既有决策是"用户输入是自然文本，`OR` 是普通词、
任何输入都不报错"，动语法等于推翻那条决策，不在本轮。

## 理由（实测支撑，全部来自设计 05）

| 决策 | 关键实测 |
| --- | --- |
| 多取 + Rust 截断 | `LIMIT 50/250/1000` = 27/28/28 ms（`关键词`）、666/599/605 ms（`全文搜索`）→ over-fetch 免费 |
| 必须修每篇淹没 | 61 篇 / 120 行命中 → `limit=50` 的 50 条全来自 1 篇；Mock 却是每篇 5 条 |
| `total` 按需 | `COUNT` 占现状 `关键词` 37–46 ms 里的 10–12 ms、`全文搜索` 436–566 ms 里的 54–56 ms |
| 按词高亮 | 宿主是逐词 AND，前端是整串子串 → 多词查询零高亮 |

## 代价与缓解

| 代价 | 缓解 / 说明 |
| --- | --- |
| 同一篇的第 6 条命中不再出现在列表里 | `total` 与"还有 N 条未显示"仍如实报数；换来列表里能看到更多**不同**笔记 |
| 多取最多 1024 行的行文本进内存 | 实测免费；瞬时内存百 KB–MB 级 |
| 极端情形下可能返回少于 `limit` 条 | 明确取舍：宁可少给，不多给同一篇；已在 `search()` 的文档里写明 |
| 高亮仍可能缺（`cafe`↔`café`、被 120 字符裁掉的那个词） | 宿主只回片段、不回偏移；要精确高亮得扩 IPC 契约（加 offsets），属独立题 |
| 跨行多词仍不命中 | 本轮不修（见下）；空态文案如实提示 |

改动后复测（同一台机器、同一份语料）。**绝对耗时在这台机器上不可比**：测量期间有别的构建在跑，
同一份 SQL 在两条连接上能差 5 倍、`bench_*` 的建库时间在 2.4–6.3 s 之间摆。所以对照一律是
**同一条连接上"改动前的查询路径"与"改动后的路径"紧挨着交替跑 7 轮、取每轮比值的中位数**：

| 项 | 改动前 | 改动后（比值中位数） |
| --- | --- | --- |
| 命中 100 的查询（`独角鲸`） | 0.1 ms | 0.1 ms（**0.65×**：命中不足预算 → 跳过 `COUNT`） |
| 命中 10 000 的查询（`关键词`） | 267.6 ms | 281.1 ms（**1.00×**） |
| 命中 290 000 的病态查询（`全文搜索`） | 853.9 ms | 872.6 ms（**0.98×**） |
| 每篇上限的效果（61 篇 / 120 行命中，`limit=50`） | 50 条来自 **1** 篇 | 50 条来自 **46** 篇 |
| `bench_reopen_10k_notes` · Vault 没变（搜索这一路） | 0 ms（全轮 236 ms） | 0 ms（全轮 381 ms，负载更高） |
| `bench_reopen_10k_notes` · 改了 1 篇（搜索这一路） | 4 ms（全轮 289 ms） | 4 ms（全轮 422 ms，负载更高） |

打开 Vault 那条路径本轮一个字节都没改（没有 schema 变更、没有重建），上表里它的数字变化
只反映并发构建造成的负载差；查询路径的代价则在噪音以内（多取 8 倍行不要钱，见设计 05 §4.2/§4.5）。

## 替代方案（否决，附实测/代价）

1. **换 `trigram` 分词器**：3.50.2 支持，英文会变成真正的子串检索，但实测 1 字/2 字查询**零命中**
   （`天气` 0 行、`天` 0 行、`今天天` 1 行）—— 中文用户最常打的正好是 1–2 个字。否决。
2. **SQL 窗口函数 `ROW_NUMBER() OVER (PARTITION BY rel_path …)` 做每篇上限**：
   `bm25()` 不能出现在窗口上下文（要 `WITH matched AS MATERIALIZED` 先落地），而且实测
   `全文搜索` 382 → **1 751 ms**（4.6×）、`的` 592 → **1 707 ms**（2.9×）。否决。
3. **再加一份"按篇"的 FTS 索引**（修跨行多词 AND）：库体积在当前 2.7× 之上再翻一倍
   （真实 Vault 207 MB → 400 MB 级），打开与写入成本同比例上升，收益只是"多词跨行能命中"。
   记入设计 05 的已知限制，另立设计题（真要做得先解决"第二套索引口径"的维护代价）。
4. **多词查询零命中时退化成 OR**：会在用户没要求"任一词"时给出只命中一个词的结果，
   排序口径变得不可解释（哪些结果更相关？），且与既有测试钉住的 AND 语义冲突。否决。
5. **把每篇上限做成契约字段**（宿主入参 `hitsPerNote`）：要给 IPC 加字段、前端要传值、
   Mock 要跟着改，而"每篇 5 条"是展示层的降噪策略，不是调用方的语义需求。否决，
   保持为 `mn-index` 的实现常量（注释里写明它与 Mock 的对应关系）。
6. **前端多取、前端截断**：前端只有宿主返回的这一批（`limit` 条），要自己多取就得改
   `use-search.ts` 的 limit 并与"渲染前 50 条"打架；截断属于"结果装配"，放在索引层更靠近数据。否决。

## 影响

- **IPC 契约不变**：`SearchHit { relPath, line, snippet, score }`、`SearchResult { query, hits, total, elapsedMs }`
  与排序口径都保持原样；前端 `apps/desktop/src/features/palette/*` 只改高亮与空态文案。
- **前端 Mock 与真机不再分家**：两边都是"每篇 5 条 + `total` 全部命中"。
- **不改 schema / 不 bump 版本**：老缓存库直接可用，没有迁移与重建。
- **已知限制清单**（跨行多词、短语/OR/排除词、词中匹配、全角折叠、`cafe`↔`café` 高亮）
  集中留在设计 05 §6，后续要动它们时以本文的替代方案为起点。
