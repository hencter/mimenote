# 设计 03：收件箱（Inbox）

- 状态：**已定稿，进入实现**（Lead 定规格；实现由 `inbox` 队友负责，对应 ADR-0057）
- 日期：2026-10-12
- 前置：ADR-0002（文件即真相）、ADR-0004（原子写与冲突令牌）、ADR-0012（移动改写相对链接）、
  ADR-0030（显示名不带 `.md`）、ADR-0044（frontmatter 时间挂钩）、ADR-0048（三格式 frontmatter）、
  设计 01（配置 schema 里的 `[inbox]`）、设计 02（模板语法，默认落点是收件箱）

## 0. 一句话定义

收件箱 = **Vault 内一个独立目录**（默认 `Inbox/`，配置键 `inbox.dir`）里的笔记。
它的唯一语义是"**我知道要记下来、但还没决定放哪**"；因此"未整理"不是一个需要额外存储的
标记，而是**位置本身**：整理 = 把它移出这个目录。

## 1. 条目判定（唯一判据）

```ts
// domain/inbox.ts —— 只有这一处实现，视图 / 计数 / 命令 / 将来的文件树钩子都调它
isInboxPath(relPath, dir)   // 路径落在收件箱目录之内（含子目录；含目录自身）
isInboxEntry(relPath, dir)  // isInboxPath(...) && isMarkdown(relPath)
```

**结论**：

| 问题 | 判定 | 理由 |
| --- | --- | --- |
| 哪些文件算条目 | 收件箱目录**之内**（任意深度）的 `.md` / `.markdown` | 判据是**位置**："还没归档"= 还在 `Inbox/` 之下。多加一条"只有顶层才算"就等于给这个视图发明一条别处没有的隐性规则 |
| 子目录算不算 | **算**（`Inbox/项目A/x.md` 仍是条目） | 漏算的观感是"我明明在收件箱里，东西却没了"；多算的观感是"它还在收件箱"，与文件树显示一致、可自解释 |
| 非 md 附件算不算 | **不算** | 视图的动作（打开 / 归档）都是笔记语义：附件既打不开也不该被单独归档，混进计数会让"还剩 N 条"永远清不掉 |
| 目录自身算不算条目 | 不算（`isMarkdown` 天然排掉） | 目录没有"整理好没"这回事 |
| 大小写 | **按段比较、大小写不敏感** | Windows / macOS 上 `Inbox` 与 `inbox` 是同一个目录：用户把配置写成小写不该让收件箱变成空的。Linux 上"配置与磁盘仅大小写不同"是配置自己的问题，宽进（两边都算）只多算、不丢东西 |
| 配置为空 / 非法 | `normalizeInboxDir` 回退 `Inbox` | 空串在附件目录那里表示"Vault 根"，在这里等于"整个 Vault 都是收件箱"——没有意义，因此与非法值同等回退（与 `normalizeAttachmentDir` 只差这一条） |

**已知边界（写下来，不假装不存在）**：归档只动笔记本身，**不搬附件**（沿用 ADR-0012 移动笔记的
现状：改路径 + 改写链接，附件留在原地）。因此把一条带图的笔记归档出去之后，`Inbox/` 里会留下
那几张图。它们不是条目（不受计数影响），但要清理得手工搬——这与"移动笔记不动附件"是同一个
既有行为，不在本轮改。

## 2. 捕获语义（`inbox.capture`）：**默认新建一篇带时间戳的笔记**

两种模式都实现，由配置键 `inbox.dailyNote` 决定（设计 01 的 schema 已定：

```toml
[inbox]
dir = "Inbox"
dailyNote = false        # 捕获时是否落到 Inbox/YYYY-MM-DD.md
```

`false`（默认）= **单篇模式**：一次捕获 = `Inbox/<YYYY-MM-DD HHmm> <首行摘要>.md` 一篇新笔记。
`true` = **当日模式**：一次捕获 = 向 `Inbox/<YYYY-MM-DD>.md` 末尾追加一条。

目录的真相是设置层的 `inboxDir`（上游就是这个 `[inbox] dir`）；`dailyNote` 这一轮还没落到
设置层，因此默认语义是"单篇"，切到当日模式需要 Lead 把该配置键接进
`inbox-store.setCaptureMode`（见 §9）。

### 2.1 为什么默认是单篇

| 判据 | 单篇 | 当日追加 |
| --- | --- | --- |
| 打开 / 归档 | 都是**文件级**动作，直接复用 `openNote` / `note_move`（宿主已会改写全库链接） | 归档必须做**文本手术**（从当日文件里剪一段、另存一篇）：没有原子性、不进索引的 `(path, mtime)` 模型，失败会留下半截内容 |
| 计数与"处理掉这一条" | 一条 = 一篇，计数与动作一一对应 | 一条 = 一段文本，没有"处理掉这一条"这个对象；计数退化成"有几天没整理" |
| 冲突面 | 写的是**刚创建、没人打开过**的新文件，冲突面为零 | 每天早上第一条捕获会与"正开着的当日笔记"抢同一个文件 |
| frontmatter（ADR-0044） | 每篇有自己的 `created` / `updated` | 一篇文件只有一份 frontmatter，追加进去的那条拿不到自己的 `created` |
| 代价 | 文件数变多；标题里带时间戳 | 文件少、当天条目聚在一起 |

单篇模式的代价是"文件数变多、标题带时间戳"——而收件箱本来就**要求用户尽快清空**，文件多不是
它的问题；当日模式的代价（归档靠文本手术、没有单条粒度）恰好落在"整理"这条主路径上，
而整理正是收件箱唯一要做的事。

### 2.2 单篇模式怎么落盘

```
1. note_create(dir, "<YYYY-MM-DD HHmm> <首行摘要>", stampTimes)   → 唯一命名由宿主负责
   并立刻 vault-store.registerCreatedNote(...)                    → 树 / 列表当场看得见
2. note_write(relPath, 正文, 第 1 步的 mtimeMs, force=false, stampTimes=false)
   （frontmatter 块刚由 note_create 写好，这一步只填正文，不再挂钩）
```

- **标题 = 时间戳 + 首行摘要**（而不是只有时间戳）：收件箱列表要一眼看出"这条是什么"。
  只有时间戳的话，列表就是一串 `2026-10-12 2054`，而"读每篇首行"意味着 N 次 `note_read`。
  摘要取正文首行、压空白、截到 24 个字符，再经 `sanitizeAttachmentStem`（与宿主
  `sanitize_file_stem` 同一套口径：非法字符换 `-`、保留名与空名交给时间戳兜底）。
  文件名与正文因此**重复**了首行——这是刻意换来的可读性，代价写在 ADR-0057 的"代价"里。
- **正文 = 用户写的那句话**（trim + 末尾补一个换行）。**不加 H1、不加项目符号**：加任何前缀
  都是在改用户输入，而"文件即真相"要求磁盘上的文件就是那个人写下的东西。
- **两类失败都不静默**：`note_create` 失败 → 弹错误、输入框内容留在屏幕上；第 2 步失败 →
  磁盘上留着一篇只有 `# 标题` 的笔记（标题里就有首行，内容没丢），错误照实报。
- **宿主差异必须兜住**：真实宿主的 `note_create` 要求父目录**已存在**（`resolve_existing`
  失败即 `NOT_FOUND`），而 Mock 适配器会自动补父目录。因此"收件箱目录还不存在"这一支
  必须显式处理：先在 Vault 根创建，再 `note_move(relPath, dir, null, false)`（宿主会创建
  目标目录；`updateLinks=false` —— 刚建的文件不可能有反链，跳过全库链接改写是诚实的）。
  **不做**"依赖 Mock 的自动补目录"——那会让 E2E 绿着、真机上是"第一次捕获报错"。

### 2.3 当日模式怎么追加（原子 / 不破坏 / diff）

```
1. 目标存在 → note_read 拿到原文与 mtimeMs；不存在 → note_create(dir, "YYYY-MM-DD", stampTimes)
2. toEditorText(raw)                     → 去 BOM、换行归一化（domain/eol.ts，唯一判据）
3. appendCaptureEntry(text, 正文, at)    → 纯函数：末尾追加
4. fromEditorText(appended, format)      → 还原 BOM 与 CRLF
5. note_write(relPath, appended, mtimeMs, force=false, stampTimes)
```

- **不破坏原有内容**：追加基于"读到的原文 + 纯函数拼接"，并且写回时**原样保留** BOM 与换行风格
  （`domain/eol.ts` 的 `toEditorText` / `fromEditorText`）。一个 CRLF 的当日笔记不会因为捕获
  一条就被 Git 看成"整个文件都改了"。
- **原子**：`note_write` 带 `baseMtimeMs` 版本令牌，磁盘在"读"与"写"之间被改过就返回
  `CONFLICT` 且**一个字节都不写**（ADR-0004）；写本身是宿主里的临时文件 → fsync → rename。
  并发两次捕获：第二次拿到 `CONFLICT` 并**失败退出**，不自动重试——重试会掩盖"这中间有人改过"，
  而"绝不覆盖"是 ADR-0004 的纪律。用户看到错误、输入框内容还在，再按一次回车即可。
- **可读的 diff**：追加**只在文件末尾新增行**——上一条也是列表项就直接接在下一行（当日笔记
  是一串捕获，条目之间不塞空行），否则补一个空行（散文后面紧跟项目符号会被某些渲染器当成
  上一段的延续），已有空行则不补。diff 里除了新增什么都没有。打开时间挂钩时另有两行时间
  字段的更新——那正是挂钩的定义。
- **一次撤销：没有**。这条要老实说：写入走的是 IPC（不是编辑器），所以 Ctrl+Z 的撤销栈里
  没有这一步，捕获**不可撤销**。替代出路是"删除到回收站"（可恢复，ADR-0018）或改用单篇模式
  （删掉那一篇即可）。要做真正的"撤销本次捕获"，得在 store 里记住写入前的原文并提供一条
  `undoCapture()` —— 本轮不做，不做就不假装有。
- **当日笔记正被编辑时不追加**：目标文件在编辑器里且**有未保存内容或处于冲突态**时**拒绝**
  并提示。理由：编辑器内存与磁盘是两条写入路径，同时成立必然有一方看不见另一方（ADR-0004 的
  冲突横幅是给"外部改动"用的，不该被自己的捕获功能天天触发）。干净地开着是允许的：追加成功后
  走一次静默的条目表对齐，编辑器会自己重载到新版本。

### 2.4 空输入 / 空白输入

`trim()` 之后为空 → **不捕获**（不建文件、不追加），不报错（用户按了回车又删了而已），
输入框保持打开。

## 3. 排序、"未整理"与计数

- **排序**：`mtimeMs` **倒序**（新的在前）；`mtimeMs === null` **恒排最后**，不随方向翻转
  （与 `domain/tree.makeEntryComparator` 的规则 1 同一条：null 的含义是"没有这个时间"，
  降序把它顶到最前等于把"未知"显示成"最新"）；主键相同再按 `relPath` 升序兜底，保证结果与
  输入顺序无关。
  - 为什么不用文件名排序：当日模式的 `2026-10-12.md` 会被字典序排到所有"带时间戳的单篇"
    之后，而单篇的文件名前缀只到**分钟**。`mtime` 才是"最后一次动它"这件事的现成答案。
  - 为什么不读 frontmatter 的 `created`：要么 N 次 IPC，要么查索引；而条目表里已经有 mtime。
- **"未整理"的定义**：仍在收件箱目录之内的条目（§1 的判定）。因此
  **未整理数 ≡ 条目数**——这不是同义反复，而是一个决定：**不引入第二套标记**
  （不加 frontmatter 字段、不加 `#未整理` 标签、不加 `.mimenote` 状态表）。
  标记与位置一旦并存就会打架：用户手工把文件拖出 `Inbox/` 时，标记不会跟着变，
  界面于是开始说假话。
- **计数口径**：`inboxCount()` = 收件箱条目数，从 `vault-store` 的**条目表**派生
  （打开 Vault 时那一次扫描的快照），因此计数**不花任何 IPC**、也不会有第二份"收件箱列表"
  与文件树打架。条目表随扫描 / 外部改动事件（ADR-0016）刷新，计数跟着刷新。

## 4. 与索引 / 搜索的关系

**现状**（先看清，再决定）：

1. `search_query` 打在宿主 SQLite FTS5 上，排序是
   `ORDER BY -bm25(lines_fts) DESC, rel_path ASC, line ASC`（`crates/mn-index/src/search.rs`）：
   **只有相关性 + 路径/行号兜底**，没有目录、没有时间、没有"最近打开"任何加权；
2. 中文靠"逐字插空格 + 短语匹配"（`space_cjk`），与本次改动无关；
3. `note_create` 与 `note_write` 都调 `indexer::update_note`
   （`src-tauri/src/commands/notes.rs`），所以**捕获出来的笔记立刻可被搜到**，不存在
   "收件箱是索引之外的地方"。

**决定：搜索里不特殊对待收件箱条目。**

- "收件箱里的更相关"是**错的**：收件箱的含义是"还没决定放哪"，不是"更重要"。按它加权会让
  搜索结果的顺序变成一个用户无法解释的规则（"为什么这条排前面？哦，因为它在 Inbox 里"），
  而这个仓库对搜索排序的既有承诺恰恰是"bm25 能解释"。
- 技术上也不该在这里做：排序在 Rust（`crates/**`，本轮不在写权限内），前端"自己重排结果"
  等于把排序规则抄成两份，且与 `total`（宿主给的命中总数）不再一致。
- 收件箱有自己的入口（`inbox.open` / `Mod+Alt+I`），它承担"按时间看最近捕获"这件事；
  搜索结果里每条都带路径，用户看得见 `Inbox/`。

要加也得是宿主侧一个**显式**参数（例如 `search_query(query, limit, boostPrefix)`），并先有
"真实使用场景 + 可解释的权重"两个证据。本轮明确不做。

## 5. 与文件树的关系（接口，不含实现）

收件箱是**普通目录**：扫描器不忽略它，文件树照常显示、可展开、可拖放，与别的目录没有区别。
本轮**不改** `FileTree.tsx`（由 `filetree-columns` 队友持有）。给他们的接口只有三个：

| 接口 | 用途 |
| --- | --- |
| `isInboxPath(relPath, dir)`（`domain/inbox.ts`） | 判"这一行是不是收件箱目录"的唯一判据。**不许**在树里写 `relPath === 'Inbox'` 这类字面比较——配置可以改目录名，大小写也按同一口径 |
| `withInboxFirst(baseComparator, dir)`（`domain/inbox.ts`） | 把现有比较器包一层"收件箱目录永远排在最前"，其余排序语义原样不动（顶层只有 `Inbox` 这一行落在判据里，子树内部不受影响） |
| `useInboxDir()` / `useInboxCount()`（`features/inbox/use-inbox-entries.ts`） | 树侧要显示"收件箱（N）"这种角标时的现成来源；不要自己数条目（`state/**` 不 import React，所以派生 hook 在 feature 层，与 `features/vault/use-tag-filter-view.ts` 同一写法） |

"收件箱置顶"是一个**排序偏好**，不是扫描规则：不置顶时收件箱按普通目录排，功能一个不少。

## 6. 与 ADR-0044（时间挂钩）、模板语法（设计 02）的关系

### 6.1 ADR-0044

- 单篇捕获调 `note_create(..., stampTimes = 设置里的 frontmatterTimestamps)`；随后那次
  `note_write` 必须**保留刚写下的 frontmatter 块**（`mergeCapturedBody`），只丢宿主写的
  `# 标题` 占位行。这是本设计里最容易写错的一处：丢掉块就会出现"每篇新建的笔记都有
  `created`，唯独收件箱里的没有"，而用户完全不知道为什么。
- 当日模式同样把 `stampTimes` 透传：追加**确实**是一次编辑，`updated` 该跟着走。
  用户已有的当日笔记**没有** frontmatter 块时，宿主**绝不擅自建块**（`notes.rs` 的既有口径），
  追加就只是追加。
- 捕获**不写额外字段**（没有 `inbox: true` 之类）：状态就是位置，见 §3。

### 6.2 模板语法（设计 02）

- 设计 02 §5.1 定下"`template.newFrom` 默认落到收件箱"。因此"收件箱目录是哪个"必须只有一处
  判据：`domain/inbox.ts` 的 `DEFAULT_INBOX_DIR` / `normalizeInboxDir`。模板侧要"默认落到
  收件箱"，读的是同一个来源（Lead 接线后从设置读 `inbox.dir`），不要各写一个 `'Inbox'`。
- **捕获不做模板展开**（v1）：捕获输入框**不是**模板上下文。设计 02 §5 明确只有两个上下文
  （模板文件整篇展开、编辑器内联补全），捕获框是第三个地方，本设计**不把它加进去**。
  逐条理由：
  1. 展开的两个记号都需要交互（`@cursor` 要把光标落点交给编辑器、`@prompt` 要弹对话框），
     而捕获的全部价值是"零交互入袋"；
  2. 两者的失败容忍度相反：模板展开失败可以"原样保留 + 列出未识别记号"再新建；捕获里
     多一步校验就是多一个会打断人的分支；
  3. 依赖方向也不该反过来：`domain/inbox.ts` 是纯函数，拉进展开器会让"捕获"依赖一个
     还在演进中的模块。
  用户在捕获框里写 `@today` 会**字面落盘**——这不矛盾（模板语法只在上面那两个上下文成立），
  但属于要在设置/帮助里说清的一条。将来要支持：在 `capture()` 写入前调**一次**展开器
  （唯一调用点），而不是把展开逻辑复制进 `domain/inbox.ts`。

## 7. 错误与边界（每一条都要有明确的界面表现）

| 情况 | 行为 |
| --- | --- |
| 收件箱目录不存在 | 单篇：先在 Vault 根创建再 `note_move` 进去；当日：同上。成功后照常提示 |
| `note_create` 返回 `NOT_FOUND` 且回退也失败 | 报错（`describeError`），输入框内容留着 |
| `note_write` 冲突（当日模式） | 报错"文件已被外部修改"、**不覆盖**、输入框内容留着，再按一次回车重试 |
| 当日笔记正被编辑且有未保存内容 / 冲突 | 拒绝捕获 + 明确提示（"先保存或关掉那篇，或者改用单篇模式"） |
| 空 / 全空白输入 | 不捕获、不报错 |
| 连续按回车 | `capturing` 标志置忙，第二次直接忽略（不写第二条） |
| 没有打开 Vault | 命令 `when` 为假（置灰）；组件里也要能安全渲染空态 |
| 收件箱为空 | 列表显示空态与"`Mod+Shift+I` 捕获"的提示，不显示空表格 |
| 条目数很大（几千） | 列表直接渲染（与回收站同量级）；不做虚拟列表——收件箱的意义就是尽快清空 |

## 8. 界面与交互（最小面）

两层面板，都挂在 `InboxHost` 一个挂载点上（与 `<TrashDialog />` 同级，见 §9）：

- **捕获框**（`inbox.capture`，`Mod+Shift+I`）：一行输入 + 目标路径预览（`Inbox/2026-10-12 2054 …`）
  + 模式说明。回车捕获、`Esc` 关闭；成功即关，失败留着。
- **收件箱视图**（`inbox.open`，`Mod+Alt+I`）：按 §3 排序的列表，每行 = 名称（`displayName`，
  不带 `.md`）+ 相对路径（`displayPath`）+ 相对时间（`title` 里给绝对时间），动作是
  **打开**（`app/actions.openNote`，先关掉这一层：模态盖着正文等于白点）与
  **归档…**（行内表单输入目标目录 → `app/actions.moveEntry`，与拖拽/「移动到…」同一条链路）。
  头部有未整理计数与「捕获」按钮。
- **归档 = 移出收件箱**，目标由用户当场输入（`<datalist>` 给出现有目录，输入新目录由宿主创建）。
  两个刻意的取舍：
  1. **不设固定的"归档目录"**：那只会造出第二个收件箱，用户还得再搬一次；
  2. **不复用 `features/vault/MoveDialog`**（也就是不派发 `requestMove`）：那个对话框由
     `FileTree` 挂载，侧栏隐藏（`Mod+Shift+B`）时它**不在树上**，事件会静默无效 ——
     收件箱的归档不能有"看情况失效"的入口。因此这里自带目标输入，链路仍是同一条
     （`moveEntry`：宿主搬文件 + 改写全库链接 + 条目表换路径 + 标签页对账）。
  目标还落在收件箱里（`isInboxPath` 判）时「移动」置灰并说明原因："归档是移出这个目录"，
  又一次复用了同一份判据。

## 10. 验收（进入测试阶段的判据）

1. `isInboxEntry` 的边界逐条钉死：子目录算、非 md 不算、目录不算、大小写不敏感、
   `Inbox2/x.md` 与 `Inbox 备份/x.md` **不算**（前缀必须整段相等）。
2. 排序：`mtimeMs` 倒序；`null` 恒在最后；同 mtime 按 `relPath` 升序，结果与输入顺序无关。
3. 单篇捕获：新建在收件箱目录里、标题 = 时间戳 + 首行摘要（压空白、截断、非法字符）；
   正文 = 用户输入 + 一个换行；时间挂钩打开时 `created/updated` 块**保留**。
4. 当日捕获：CRLF 文件保持 CRLF、BOM 保持 BOM；追加只在末尾新增行；原文末尾有无换行、
   已有一个空行、有多个空行三种情况各自的结果可预期。
5. 收件箱目录不存在时，捕获仍然成功（真机路径：先建在根再 move）。
6. 归档走既有的移动链路，移动后条目不再计入未整理数（= 被移出目录）。
7. `pnpm --filter @mimenote/desktop typecheck` 与既有测试全绿。
