# 设计 05：全局搜索的实测缺陷清单（中文命中 / 排序 / 延迟 / UX）

- 状态：**测量已定稿**（本文只记录实测事实与缺口；方案见 ADR-0059，实现范围见文末）
- 日期：2026-10-12
- 前置：ADR-0008（FTS5 全文检索）、ADR-0014（落盘索引）、ADR-0002（索引是可重建的派生数据）
- 测量环境：`rusqlite 0.37` 的 `bundled` SQLite，`SELECT sqlite_version()` = **3.50.2**（FTS5 与 `trigram` 分词器都编在二进制里）
- 测量语料（与既有基准同形）：1 万篇 × 每篇 30 行 = **301 100 行**，release 构建的缓存库 **114.7–116.5 MB**，整库重建 **2.4–2.7 s**
- 测量工具：临时探针（`--ignored` 的一次性测量夹具，定稿后已删除，结论固化进本文与单测）
  + 既有基准 `bench_full_text_search_10k_notes` / `bench_reopen_10k_notes`
  （`cargo test -p mn-index --release -- --ignored --nocapture bench_...`）

> 本文的每一条结论都来自上面这套语料/探针的**实测输出**，不是对 FTS5 文档的转述；
> 凡是没有实测到的（比如"用户实际怎么打字"）本文不写。
>
> **关于绝对耗时的一个告诫**：本轮测量期间机器上同时有别的构建在跑，同一份 SQL
> 在两条连接上测出的耗时能差 **5 倍**（774 ms vs 5465 ms），`bench_*` 的建库时间也在
> 2.4 s 与 6.3 s 之间摆。所以本文给出的绝对数字都注明"安静时测得"，
> 而**改动前后**的对照一律用"同一条连接上交替、取配对比值中位数"的方式量（见 §4.5）。

## 1. 中文：子串能命中，分词是"逐字切开 + 相邻短语"

### 1.1 现状（读代码 + 实测）

`lines_fts` 用 `tokenize='unicode61 remove_diacritics 2'`；入库与查询两侧都先过 `space_cjk` 把 CJK 逐字切开。

不切开会怎样 —— 用 `fts5vocab` 把 `unicode61` 的**分词结果**直接打出来
（`CREATE VIRTUAL TABLE raw USING fts5(t, tokenize='unicode61 remove_diacritics 2');`
`CREATE VIRTUAL TABLE raw_v USING fts5vocab(raw, 'row'); SELECT term FROM raw_v`，
结果是一行行可复现的）：

```
UNICODE61_TOKENS = ["bar","baz","cafe","foo","今天天气很好","研究生命的起源","第2天"]
```

一整串汉字（`今天天气很好`、`研究生命的起源`）与"汉字+数字"混排（`第2天` 里的 `2` 是字母数字，所以整串没被切开）
都只是**一个 token**；同一个语料上直接查 `天气` → **0 行**。这就是 `space_cjk` 存在的原因（ADR-0008 决策 3）。

### 1.2 逐字切开后的命中矩阵（实测）

语料：`甲.md = 今天天气很好，适合写代码。`、`乙.md = 研究生命的起源`

| 查询 | 结果 | 说明 |
| --- | --- | --- |
| `天` | 命中 | **单字**能搜 |
| `天气` / `天气很` | 命中 | 2 字、3 字子串都行 |
| `好` / `气很` | 命中 | 跨"词"边界也照样是子串 |
| `今好` | 不命中 | 两字在原文里不相邻（逐字切开后是短语匹配） |
| `适合写作` | 不命中 | 不是原文的子串（正确） |
| `研究生命` / `命的起` / `起源` | 命中 | 任意位置子串 |
| `气很 好`（带空格） | 命中 | 两个短语，AND 关系，同一行内 |

标点不会破坏相邻性：`今天天气很好，适合写代码` 里 `，` 只是 unicode61 的分隔符，逐字切开后 token 序列仍是
`今 天 天 气 很 好`，所以 `气很` 命中。

**结论：中文（含日文假名、韩文）的 1/2/3+ 字子串检索是成立的**，本轮没有"中文搜不到"这一类缺陷。

### 1.3 trigram 分词器：可用，但**不能**换（实测）

SQLite 3.50.2 支持 `tokenize='trigram'`（建表成功），实测同一批文本：

| 查询长度 | `trigram` MATCH | 结论 |
| --- | --- | --- |
| `天`（1 字） | 0 行 | 3 字以下不命中 |
| `天气`（2 字） | 0 行 | 同上 |
| `今天天`（3 字） | 1 行 | 3 字起才是子串检索 |
| `ello` / `hello` / `defgh` | 命中 | 英文也变成子串检索（含词中） |

也就是说：换 `trigram` 会把**最常见的中文 1–2 字查询打回零结果**，而它唯一的收益（词中匹配）
正好是当前实现刻意不支持的东西。**否决**（记入 ADR-0059 替代方案）。

### 1.4 中文仍有的三个缺口（实测）

| 缺口 | 实测 | 根因 |
| --- | --- | --- |
| **多词必须落在同一行** | 同一篇里第 1 行 `天气`、第 2 行 `代码`：查 `天气 代码` **零命中**（只有当第 3 行同时含两词时才命中）；`天气\n很好` 查 `天气很好` 也零命中 | 索引的最小单位是**行**（ADR-0008 决策 2：行是"排名之后还能拿到行号"的单位），逐字的相邻性只在行内成立 |
| **全角不折叠** | `只有全角 ＡＢＣ 一行` 查 `abc` **不命中**（查 `ＡＢＣ` 命中） | `unicode61` 不做 NFKC：`ＡＢＣ` 与 `abc` 是两个 token；中文用户开全角输入法时偶尔会踩到 |
| 单字 token 的体积代价 | 库 114.7 MB / 正文约 42 MB ≈ **2.7×**（ADR-0008 已记），本轮未变 | 逐字切分 |

## 2. 英文与混合输入：前缀可以、词中不行、短语不可表达

实测语料里放了大小写、连字符、下划线、变音符号、日期与版本号：

| 行为 | 实测 | 说明 |
| --- | --- | --- |
| 大小写 | `hello` = `HELLO` | `unicode61` 折叠大小写 |
| 前缀 | `hel` 命中 `hello`（3 行都命中） | 每个词尾加 `*` |
| **词中** | `ello` **零命中** | 前缀只能从 token 头开始 —— 这是与中文子串最大的不对称 |
| 变音符号 | `cafe` 命中 `café`（`remove_diacritics 2`）；`café` 也命中 | 连字符两侧的字母互为前缀也命中 |
| 多词 | 按空白切成词后是 **AND**：`alpha beta` 命中两词同现的行；`world hello` 与 `hello world` 命中同一批（**不要求顺序**） | 没有 OR、没有 NOT |
| 标点/连字 | `hello-world`、`foo_bar`、`2025-01-01`、`v1.2.3`、`snake_case_name` 都命中 | `-`、`_`、`.` 是分隔符，但整串被引号包成一个短语 → 逐 token 相邻仍等于原样顺序 |
| 短语 | **不可表达**：输入 `"alpha beta"`（带引号）被当成两个词，不会变成短语查询 | 引号内的引号被转义成普通字符（安全，但用户拿不到短语语义） |
| OR / AND 等操作符 | `alpha OR beta` 要求三个词同现 → **零结果**（既有测试 `hostile_queries_never_error` 把这一条钉成"AND 语义"） | 这是能力缺口，不是 bug：ADR-0008 §4 刻意把用户输入当自然文本，保证"任何输入都不报错" |
| 纯标点 / emoji | `😀` 被 `query_terms` 丢掉 → 不查库、空结果、不报错 | 有意为之 |

## 3. 排序与高亮：一条严重缺陷 + 两处高亮错误

### 3.1 bm25 排序本身是全序、稳定（OK）

`ORDER BY score DESC, rel_path ASC, line ASC` 是全序，前端不需要二次排序（既有测试钉住）。
两个要知道的边界：

- **小库里 bm25 会退化**：3 篇小语料的实测里 `关键词` 的 score 全是 `0.000001`（IDF≈0），
  排序实际由 `rel_path` 决定。这不是缺陷，但说明 `score` 只有"同一批结果内的相对含义"；
- 短行/短文档更靠前（实测 `hello`：短行排在长行前）。

### 3.2 缺陷：**一篇笔记能吃掉整个结果列表**

实测：`flood.md` 有 60 行命中，另外 60 篇笔记各命中 1 行，共 **120 行 / 61 篇**
（该行为现已由 `crates/mn-index/src/search.rs` 的 `one_note_cannot_flood_the_result_list`
与宿主 `commands/search.rs` 的 `search_does_not_let_one_note_fill_the_whole_list` 钉住）。
用宿主默认的 `limit=50` 查 `关键词`：

```
total=120，返回 50 条，其中不同笔记 1 篇；返回的前 5 条 = flood.md × 5
```

也就是说**面板里只剩 1 篇笔记**，其余 60 篇一篇都看不到。触发条件很常见：清单式笔记、日志式笔记、
模板页里同一个词反复出现。而前端的 Mock **早就有**每篇上限：

```ts
// apps/desktop/src/ipc/mock-adapter.ts
/** 每篇笔记最多返回多少条命中（真实实现由 FTS5 的 bm25 排序 + 截断决定）。 */
const MOCK_HITS_PER_NOTE = 5
```

`apps/desktop/tests/search.test.tsx` 里还有一条用例专门钉"每篇最多 5 条命中，但 total 是全部命中数"。
所以现状是 **Mock 比真机好**：真机实现从来没有这一层（`QUERY_MATCH` 直接 `LIMIT ?2`）。
这是本轮最该修的一条。

### 3.3 缺陷：多词查询**一个高亮都没有**

`CommandPalette.tsx` 用的是整串查询做子串定位：

```ts
indices={substringMatchIndices(hit.snippet, query.trim())}
```

查询 `天气 代码` 时，片段里几乎不可能出现 `天气 代码` 这个**连续**子串 → 返回空下标 → 没有 `<mark>`。
宿主的语义是"逐词 AND"，高亮却要求"整串连续"，两者不一致。

### 3.4 缺陷：高亮用的是**当前输入框里的串**，而不是产生这批结果的那次查询

防抖 + 竞态丢弃保证"旧结果不会被采纳"，但**已经显示的结果**在新查询在途期间仍留在列表里
（这是有意的，避免闪一下）。此时 `query.trim()` 已经是新词，用它去标旧片段：轻则没有高亮，
重则把新词的偶发出现标在旧结果上。正确口径是 `useSearch` 已经记录好的 `settledQuery`。

### 3.5 snippet：以最靠左的任一词为中心裁 120 字符

多词命中时，另一个词可能被裁掉（于是它也不会被高亮）。这是"一行只给 120 字符"的必然取舍，
本轮不改，但记录在此。

## 4. 大库延迟（release，1 万篇 / 301 100 行 / 114.7 MB）

### 4.1 查询成本结构（探针直接量了 COUNT 与 SELECT 各自多贵）

| 查询 | 命中总数 | `COUNT(*)` | `SELECT … LIMIT 50` | 现状合计（COUNT+SELECT） |
| --- | --- | --- | --- | --- |
| `独角鲸` | 100 | 0 ms | 1 ms | 1 ms |
| `关键词` | 1 000 | 10–12 ms | 27–33 ms | 37–46 ms |
| `全文搜索` | 290 000 | 54–56 ms | 382–513 ms | 436–566 ms |
| `的` | 291 100 | 25–27 ms | 568–603 ms | 595–628 ms |
| `不存在xyz` | 0 | 0 ms | 0 ms | 0 ms |

两个结论：

1. **COUNT 是白花的一半开销**：`total` 只有在"命中数可能超过 `hits` 条数"时才需要。
   先取 `hits`，若这次没取满（命中集已穷尽）就能直接得出 `total`，省掉那 12–56 ms 与一次全量扫描；
2. **慢的那一档（命中 29 万行）与 ADR-0008 记的 0.9–1.2 s 同量级**（本机本次 436–628 ms，
   机器/缓存差异），慢在"给全部命中打分 + 排序"，不在取行数。

### 4.2 **多取行是免费的**（这是"每篇上限"能便宜实现的前提）

同一批语料上换 `LIMIT`：

| 查询 | LIMIT 50 | LIMIT 250 | LIMIT 1000 |
| --- | --- | --- | --- |
| `关键词` | 27 ms | 28 ms | 28 ms |
| `全文搜索` | 666 ms | 599 ms | 605 ms |

成本全在 `bm25()` 打分与排序（它们本来就要遍历全部命中），**搬运多少行几乎不要钱**。
因此"先多取一批、再在 Rust 里按篇截断"不会劣化查询延迟。

### 4.3 用 SQL 窗口函数做"每篇前 N"：**慢 2.5–4×**（否决）

`ROW_NUMBER() OVER (PARTITION BY rel_path …)` 的实测（`bm25()` 不能直接出现在窗口上下文，
必须 `WITH matched AS MATERIALIZED (…)` 先落地）：

| 查询 | 现状（LIMIT 50） | 窗口函数版（每篇 ≤3 条） | 倍数 |
| --- | --- | --- | --- |
| `独角鲸` | 1 ms | 0 ms | — |
| `关键词` | 33 ms | 29 ms | 0.9× |
| `全文搜索` | 382 ms | **1 751 ms** | **4.6×** |
| `的` | 592 ms | **1 707 ms** | **2.9×** |

窗口函数要为整个命中集再加一次排序（外层还要按 score 重排一次）。否决，改用 §4.2 的"多取 + Rust 截断"。

### 4.4 既有基准的改动前数字（同一台机器，release）

`bench_full_text_search_10k_notes`：

```
全文搜索（同一次遍历里顺带建）：2656 ms（库 116.5 MB）
查询 "独角鲸"：3 ms（total=100）   查询 "关键词"：46 ms（total=1000）
查询 "全文搜索"：481 ms（total=290000）  查询 "search"：370 ms（total=290000）
查询 "关键"：7 ms（total=1000）   查询 "关键词" × 20 次平均：36.51 ms
```

`bench_reopen_10k_notes`（打开 Vault 这一路，改动前；库 116.6 MB）：

```
1 万笔记 / 301100 行：
  链接+标签（内存索引，每轮都全量重建）：2820 ms
  旧行为 · 打开 Vault（删库 + 整库重建）：全轮 8627 ms（其中搜索 4161 ms，写 301100 行）
  新行为 · 打开 Vault（Vault 没变）：全轮 236 ms（其中搜索 0 ms，写 0 行，复用 10000 篇）
  新行为 · 打开 Vault（改了 1 篇）：全轮 289 ms（其中搜索 4 ms，写 1 行，复用 9999 篇）
```

也就是说"搜索这一路"在 Vault 没变时是 **0 ms**、改一篇时 **4 ms**，与 ADR-0008 记的
0.17–0.23 s 是同一个量级的同一件事（本轮改动不碰这条路径，只碰查询）。

### 4.5 改动后复测：同连接配对比值（不是绝对值）

改动只动"查询构造 / 结果装配"这一层，所以对照方式必须排除机器负载：
**同一条连接**上让"改动前的路径（`COUNT` → `LIMIT 50`）"与"改动后的路径（`LIMIT 400` → 每篇
5 条 → 截到 50 → 需要时才 `COUNT`）"紧挨着交替跑 7 轮，取**每轮比值的中位数**：

| 查询 | 命中总数 | 老路径最小值 | 新路径最小值 | 每轮比值中位数 |
| --- | --- | --- | --- | --- |
| `独角鲸` | 100 | 0.1 ms | 0.1 ms | **0.65×**（新路径更快：命中不足预算 → 跳过 `COUNT`） |
| `关键词` | 10 000 | 267.6 ms | 281.1 ms | **1.00×** |
| `全文搜索` | 290 000 | 853.9 ms | 872.6 ms | **0.98×** |

也就是说：**多取 8 倍行 + 按篇截断的代价在噪音以内**（同一次运行的 `bench_*` 建库时间是
2.4–6.3 s，负载本身就比这个差异大一个量级），而命中数小于预算的查询反而变快（省掉一次全量计数）。

同一轮里 `LIMIT 50 / 250 / 1000` 的对照（§4.2）也复现了"搬运行数不要钱"：
`关键词` 27/28/28 ms，`全文搜索` 666/599/605 ms。

**每篇上限的效果**（同一批 61 篇 / 120 行命中的语料）：

| 版本 | `limit=50` 返回的 50 条里 |
| --- | --- |
| 改动前 | **1** 篇笔记（`flood.md` 独占 50 条） |
| 改动后 | **46** 篇笔记（`flood.md` 只占 5 条） |

`bench_reopen_10k_notes`（打开 Vault 这一路，与查询无关，用来证明没有连带劣化）：改动后
Vault 没变时**全轮 381 ms、搜索这一路 0 ms**、复用 10 000 篇；改 1 篇时全轮 422 ms、搜索 4 ms
（改动前分别是 236 ms / 289 ms —— 同一次负载波动里 `bench_*` 的建库时间从 2.6 s 涨到 6.3 s，
差值来自负载而不是这次改动）。

## 5. 用户体验缺口

| # | 场景 | 现状 | 结论 |
| --- | --- | --- | --- |
| 1 | 空查询 | 前端不发 IPC，宿主也返回空结果（`search_query_in` 的 trim 判定） | 已是正确行为，不改 |
| 2 | 未打开 Vault | 面板给出"还没有打开 Vault"，宿主返回 `VAULT_NOT_SET` | 已覆盖 |
| 3 | 索引构建中 / 建库失败 | 宿主返回带原因的 `IO` 错误，面板区分"构建中"与"搜索失败" | 已覆盖 |
| 4 | 真的没有命中 | 只写"没有匹配的正文内容" | **缺口**：多词查询零命中时，用户不知道"两个词必须在同一行"（§1.4 的限制），会以为库里没有 |
| 5 | 结果过长 | snippet 裁到 120 字符、以命中为中心、单行 | 已覆盖（多词时可能裁掉另一个词，见 §3.5） |
| 6 | 超过 `MAX_PALETTE_RESULTS`（50） | 面板渲染 50 条并显示"还有 N 条未显示（继续输入以缩小范围）" | 提示正确，但 `total` 是**行**数（29 万级），"还有 N 条"读起来像"还有 N 篇"；且当列表被单篇淹没时（§3.2）"还有"与实际可翻内容不符 |
| 7 | 结果列表的内容分布 | 一篇笔记可以占满 50 条（§3.2） | **缺口**，本轮修 |
| 8 | 语法能力 | 不支持 OR / 短语 / 排除词，也没有语法提示 | 记录为限制（ADR-0059 替代方案里说明为什么本轮不加） |
| 9 | 空态里的"按 X 打开 Vault" | 曾经写死 `Mod+O` | **缺口**：ADR-0055 之后 `vault.open` 的键位由"用户覆盖 → 档案 → 默认表"决定，写死的文案会指向一个不存在的键；改为走 `currentChordsOf('vault.open')` 的解析链（命令不在注册表里才退回默认表的值） |

## 6. 结论：本轮修什么、不修什么

**修**（全部落在"查询构造 / 结果装配 / 展示"层，不动索引 schema）：

1. 每篇最多 5 条命中（与前端 Mock 对齐），实现方式 = 多取一批行 + Rust 按篇截断（实测免费）；
2. `total` 按需计算：没取满就不跑 `COUNT`（省 12–56 ms 与一次全量扫描）；
3. 高亮改成"按词 + 用 `settledQuery`"（多词查询能高亮，且在途期间不会错标）；
4. 空态在"多词零命中"时说明"多个词必须出现在同一行"；
