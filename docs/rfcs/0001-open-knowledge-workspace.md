# RFC-0001：开放知识工作台与发布适配器

- 状态：Draft（提案，尚未采纳）
- 日期：2026-10-21
- 目标仓库：hencter/mimenote
- 相关文档：[README](../../README.md)、[架构文档](../architecture.md)、[ADR-0047](../adr/0047-okf-and-hugo.md)、[ADR-0048](../adr/0048-property-editing.md)
- 本 RFC 的性质：产品原则与架构边界提案；不授权直接开展全部路线图功能，也不替代后续实现级 ADR。

## 1. 摘要

MimeNote 的长期方向是一个开放的个人知识工作台：尊重用户已有的内容与工作流，帮助用户将资料整理成可检索、可关联、可复用的知识，并将其转化为可发布的成果。

本 RFC 提议围绕四项用户需求形成统一架构：

1. 以 Markdown 作为人与人、人与 AI 之间易读、易编辑、易交换的主要协作格式。
2. 尊重 TXT 等普通文本，不强制转换格式；通过非破坏性的阅读增强提升可读性。
3. 将视频、会议录屏、逐字稿、时间线摘要和知识卡片作为有关联的知识资产管理，保留从衍生结论回到原始来源的路径。
4. 使用发布适配器将知识内容转换为 Hugo、公众号工作流及其他目标平台所需的输出，降低重复排版与格式转换成本。

核心架构原则是：**开放文件是内容权威来源；知识模型统一语义而不强迫统一格式；索引与视图可重建；衍生内容有来源；发布过程默认不修改源内容。**

本 RFC 建议先强化现有格式与 Hugo 工作流，再以导入现成逐字稿为起点验证媒体知识工作流。自动转写、自动发布、公共插件市场、云同步和移动端大规模开发不属于首批交付范围。

## 2. 背景与问题

MimeNote 最初来自实际工作流中的摩擦：用户使用 Hugo 构建网站，希望笔记能够尊重 Hugo 的 TOML Frontmatter 和发布语义；同时，希望编辑器扩展能力具有清晰、稳定、开发者友好的接口，而不必让常见能力依赖复杂的第三方插件配置。

这一动机可以扩展为更一般的产品问题：

- 内容格式、笔记软件和下游发布平台之间不应形成不必要的锁定。
- 纯文本文件可以拥有更好的阅读体验，但显示增强不应改变原始字节或迫使用户迁移格式。
- 多媒体资料的价值不应止于存储或观看；摘要、逐字稿和知识卡片应可追溯、可修订、可复用。
- 发布应该是一条可预览、可验证、可重复执行的工作流，而不是把内容复制到另一平台后重新手工整理。

仓库已有的实现基础包括 Markdown 编辑与预览、双链与反链、全文索引、附件处理、属性面板、多种 Frontmatter 围栏、部分 Hugo 元数据规则和站点导出。ADR-0047 与 ADR-0048 记录了其中若干边界和已知限制。本 RFC 应在这些实现上渐进演进，不以重写现有架构为默认选项。

## 3. 产品定位

### 3.1 定位陈述

MimeNote 是一个以开放文件为基础、以知识工作流为核心的个人知识工作台。它让用户保有内容的所有权，并通过检索、关联、媒体理解和发布适配器，帮助用户将已有资料转化为长期可用的知识与成果。

### 3.2 首要用户假设

第一阶段优先验证重视 Markdown、文件自主权和内容输出的开发者、技术作者、独立研究者及知识创作者。该人群是基于现有技术能力与最初使用场景提出的工作假设，尚不代表经过市场规模或留存数据验证的结论。

### 3.3 产品边界

MimeNote 可以提供完整的个人知识工作流，但不以覆盖所有个人生产力场景为目标。邮件、日历、通用项目管理、云协作、完整媒体制作套件等，不因“工作台”定位而自动进入范围。

## 4. 不可妥协的产品原则

### P1. 原始内容归用户所有

- Markdown、TXT、视频和其他附件应保留为用户可访问的普通文件，或由用户明确选择引用的外部文件。
- MimeNote 的索引、缓存、缩略图、解析结果和视图状态不能成为恢复原始内容的唯一来源。
- 用户可以使用其他编辑器、文件管理器和版本控制工具处理其内容。
- 不得把“可导入”描述为“无损往返”；对每种格式的保真边界必须有测试和文档。

### P2. Markdown 优先，但不把所有内容都变成 Markdown

- 新的文本知识资产优先使用 Markdown，因为它易读、易编辑、易于版本控制，也便于人与 AI 协作。
- 标准 Markdown 优先于专有语法；必要的知识管理扩展必须有明确语义、兼容策略和发布转换规则。
- TXT 仍然是有效的一等内容，不因缺少标记语法而被强制转换。
- 视频等二进制媒体保持原始文件形式；其逐字稿、摘要和知识卡片可以作为关联的开放文件保存。

### P3. 增强视图不得暗中改写源内容

- TXT 的着色、时间戳识别、链接识别和排版增强属于视图层，默认不写回文件。
- 属性编辑只能修改明确选择的字段，并应遵循源格式的保真策略。
- 无法安全保留注释、字段顺序或其他格式信息时，优先阻止破坏性改写并解释原因。
- 用户主动执行格式转换时，必须明确显示转换行为及可能的损失。

### P4. 知识衍生物必须可追溯

- 逐字稿、摘要、时间线和知识卡片均应记录来源资产；可行时记录时间范围或片段定位。
- AI 生成内容应当可编辑、可删除、可重新生成；未经用户确认，不应静默覆盖原始内容。
- “生成成功”不等于“事实已验证”。界面应区分待审核、已确认和已修改等状态。
- 当来源无法定位或生成结果缺乏可靠依据时，应明确显示限制，而非制造确定性。

### P5. 发布是一个可检查的转换过程

- 发布适配器读取源内容并生成输出计划，不应为导出而改写源文件。
- 发布前应尽可能提供预览、错误、警告、路径冲突和未支持语法的诊断。
- 输出必须受到目标目录边界约束；路径冲突、越界路径和不支持的转换不能静默处理。
- 适配器应可单独测试，并共享核心解析、链接解析和安全路径能力。

### P6. 复杂性渐进暴露

- 基础知识工作流应尽量内建并可直接使用，不能要求普通用户先安装多个插件才能完成基本任务。
- 高级用户可以通过明确的扩展点和未来稳定的公共 API 扩展工作流。
- 在使用场景尚未验证前，不以插件数量或抽象层数量衡量开放性。

### P7. 本地优先与隐私透明

- 默认工作流不要求上传用户的知识内容。
- 如调用外部 AI 或转写服务，必须清楚说明会发送哪些数据、发送到哪里，并由用户主动授权。
- 本地处理能力可以逐步增加，但不能在未验证成本、性能和质量前承诺所有 AI 功能均可离线完成。

## 5. 核心概念与数据边界

本节定义概念边界，不要求立即创建同名数据库表或 Rust 类型。实现应优先复用现有领域模块，并在后续 ADR 中确定具体类型和接口。

### 5.1 源资产（Source Asset）

用户提供或明确引用的原始内容，例如 Markdown、TXT、视频、音频、图片、PDF 和其他附件。源资产的路径、字节内容及用户维护的元数据应受到保护。

对于较大的媒体文件，默认允许引用其所在路径，不因导入而强制复制；复制、移动和托管方式应由用户明确选择。

### 5.2 知识文档（Knowledge Document）

MimeNote 可以解析、编辑、索引和关联的文本文档。第一阶段以 Markdown 为主，同时允许 TXT 作为普通文本内容被浏览、搜索和管理。

Frontmatter 不是新的封闭数据模型。通用属性访问应保留未知字段；YAML、TOML、JSON 的解析、编辑和序列化必须区分语义读取与源格式保真。

### 5.3 派生资产（Derived Asset）

由源资产或其他知识资产加工得到的内容，例如转写稿、摘要、时间线、知识卡片和发布输出。派生资产应与源资产建立显式关系，并能独立编辑、版本管理和删除。

派生资产不应仅存在于 SQLite 或不可导出的应用内部记录中。默认优先使用 Markdown、WebVTT、SRT 等可访问格式；需要结构化元数据时，选择可文档化的格式，并明确哪些信息无法在纯文本中表达。

### 5.4 知识模型（Knowledge Model）

知识模型是 MimeNote 内部的统一语义层，至少需要表达：

- 资产引用与可定位身份；
- 文本内容与元数据；
- 文档间链接与附件引用；
- 源资产与派生资产的来源关系；
- 可选的时间范围与发布上下文。

知识模型不等于新的唯一存储格式。第一阶段不引入超出需求的块级数据库、复杂对象系统或全库稳定 ID 迁移。路径与现有链接语义继续作为当前基础；若未来需要跨移动、跨版本的稳定身份，应另行提出 ADR 并说明迁移策略。

### 5.5 派生索引与缓存

搜索索引、图谱数据、媒体索引和预览缓存都应视为派生数据。它们应能够从源文件和已保存的派生资产重建；缓存损坏不应导致原始知识丢失。

## 6. Frontmatter、Markdown 与 TXT 策略

### 6.1 Frontmatter

- 支持 YAML（---）、TOML（+++）和 JSON（;;;）的既有约定继续演进。
- 解析器可以把属性暴露为统一语义，但写回应尽量保留注释、字段顺序、正文、BOM 与换行风格。
- 对无法无损编辑的格式，应明确拒绝特定操作或要求用户确认，不得静默吞掉注释或重排内容。
- Hugo 特有的字段语义应由 Hugo 适配层处理，不应将所有 Hugo 假设混入通用属性编辑器。

### 6.2 Markdown 扩展语法

- 标题、列表、引用、表格、代码块、普通链接等优先遵循标准 Markdown/GFM 语义。
- 双链、嵌入和 callout 等 MimeNote 扩展可以保留，但必须明确解析、编辑、导出和不支持场景的行为。
- 发布适配器应将支持的扩展转换为目标平台可理解的输出，或明确要求平台配置；不能假设 Hugo 或其他平台天然理解 MimeNote 语法。
- 任何新扩展语法都应附带往返测试和至少一个发布测试。

### 6.3 TXT 增强视图

TXT 的增强应先做非破坏性呈现，不创造新的 TXT 语法。建议能力包括：

- 字体、行距、自动换行、行号、查找与选择；
- URL、时间戳和常见日志级别的可选识别；
- 用户明确指定语言后的代码高亮；
- 可关闭、可解释的轻量格式识别。

自动识别不应把所有 TXT 强行套用 Markdown 样式。视图增强不写回源文件；若用户要把纯文本转换为 Markdown，应作为明确的另存为/转换操作。

## 7. 媒体知识工作流

### 7.1 首期范围

第一阶段不要求 MimeNote 自研视频解码、语音识别或完整媒体处理管线。先支持：

1. 将视频或录屏作为源资产引用；
2. 导入已有的 WebVTT/SRT 逐字稿；
3. 展示逐字稿时间戳，并在媒体可访问时定位对应片段；
4. 基于逐字稿生成可编辑的摘要、议题时间线和知识卡片；
5. 在派生资产中保留来源文件与时间范围；
6. 将确认后的知识卡片链接到现有 Markdown 笔记。

### 7.2 来源与审核

- 每条时间线条目和知识卡片应尽可能链接到逐字稿片段及原视频时间范围。
- 摘要、事实、决定和待办事项均可能存在模型错误；界面必须支持用户审核与修改。
- 用户删除派生资产时，不应删除源视频或原始逐字稿，除非用户明确选择删除源资产。
- 对外部模型服务，调用前说明数据处理边界并取得明确授权；不支持安全处理的媒体应拒绝或提示替代流程。

### 7.3 暂不纳入

- 自研通用转写引擎；
- 自动录制会议；
- 未经用户确认自动创建任务或修改知识库；
- 将整个媒体文件上传到外部服务作为默认路径；
- 依赖不可导出专有数据库才能访问的转写和摘要。

## 8. 发布适配器架构

### 8.1 适配器职责

发布适配器负责目标平台差异，而不是重新实现整个知识引擎。建议的职责包括：

- 目标平台配置与能力声明；
- 元数据映射和默认值处理；
- 链接、嵌入和扩展语法转换；
- 资源路径与媒体处理；
- 草稿过滤、输出路径规划和冲突检测；
- 发布前校验与诊断；
- 输出计划、预览及结果报告。

### 8.2 建议的发布流水线

1. 扫描所选知识范围；
2. 解析源内容并构建统一语义表示；
3. 计算目标平台的元数据和输出路径；
4. 转换链接、扩展语法和资源引用；
5. 验证路径边界、重复输出、缺失引用与不支持语法；
6. 生成预览和诊断报告；
7. 用户确认后写入输出目标；
8. 返回可复查的结果清单。

该流水线是目标设计，不意味着当前实现已经具备所有步骤。应从现有 Hugo 导出逐步抽取接口，避免一次性重写。

### 8.3 适配器边界

- 通用解析、链接消歧、文件扫描和路径安全应尽可能复用现有权威实现。
- 不允许 CLI 和桌面端各自维护互相竞争的 HTML 渲染真相；遵守 ADR-0047 对渲染管线的边界。
- Hugo 是首个需要完善的适配器。
- 公众号首期以生成适合目标编辑器的富文本/HTML 与资源包、预览和诊断为主；自动发布、账号授权和平台 API 集成暂不承诺。
- 第二个静态站点目标应在 Hugo 适配器验证后引入，用于检验抽象是否确实可复用。

## 9. 扩展能力策略

MimeNote 的扩展能力应分为高层工作流接口和编辑器专业接口，但本 RFC 不要求立即发布公共插件 SDK。

### 9.1 内部扩展点

优先复用现有命令、快捷键、主题和 CodeMirror 扩展机制。新增内部接口应保持生命周期可逆、错误可见、可测试。

### 9.2 未来公共 API 的候选能力

- 命令与快捷键注册；
- 设置项和侧边面板；
- 文件与知识模型事件；
- CodeMirror 6 扩展；
- 导入、导出与发布适配器；
- 明确的能力声明和权限边界。

### 9.3 发布门槛

在真实内部扩展和外部开发者需求尚未验证前，不建立公共插件市场。发布稳定 API 前，需要示例项目、类型定义、调试文档、兼容策略和自动化契约测试。第三方扩展的文件、网络及其他敏感能力应有明确的授权设计。

## 10. 分阶段交付与验收

### Phase 0：内容保真与架构边界

- 梳理 Markdown、TXT、Frontmatter、附件和缓存的权威数据边界。
- 为 TOML 注释、字段顺序、数字原始写法、BOM、CRLF/LF 和正文保真建立回归测试。
- 记录当前 Hugo 导出能力、缺口和测试夹具。
- 定义源资产、派生资产、知识链接和发布诊断的最小接口草案。

验收：
- 已知的保真边界有自动化测试与文档；
- 不安全的写回操作会明确失败，不会静默丢失信息；
- 现有功能没有因为抽象而出现第二条文件写入路径。

### Phase 1：完善现有文本与 Hugo 工作流

- 为 TXT 实现非破坏性增强阅读视图；
- 完善 Hugo 元数据映射、路径计划、资源处理和发布诊断；
- 发布前可检查路径冲突、缺失链接和不支持的扩展语法；
- 保持发布操作不修改源知识库。

验收：
- TXT 视图切换不改变源文件字节；
- 对有 TOML Frontmatter 的真实 Hugo 内容目录进行构建验证；
- 路径越界、冲突和转换失败都有可定位的诊断；
- 重复执行相同发布任务时，在输入与配置未变的情况下生成一致的输出计划。

### Phase 2：媒体知识工作流原型

- 引用视频源资产并导入现成 VTT/SRT；
- 显示时间戳和对应片段；
- 生成带来源定位的摘要、时间线和知识卡片；
- 将确认后的卡片保存为可编辑、可导出的文件。

验收：
- 用户能从卡片返回原视频或逐字稿对应片段；
- 派生内容可独立修改与删除；
- AI 生成失败不会影响源视频和原始逐字稿；
- 生成内容的来源与审核状态可见。

### Phase 3：发布工作台扩展

- 将 Hugo 作为稳定适配器；
- 实现公众号友好的内容转换、预览和资源打包；
- 基于用户反馈决定是否接入官方发布 API；
- 用第二个目标平台验证适配器接口的可复用性。

验收：
- 用户能从现有知识资产生成可检查的发布产物；
- 发布失败能定位原因；
- 源文件保持不变；
- 新增目标平台时，不需要复制整个扫描、解析、链接解析和安全路径实现。

### Phase 4：公共扩展 SDK（暂定）

仅在前述工作流出现重复的扩展需求后再立项。发布前必须有真实示例、稳定契约、权限模型和版本兼容测试。

## 11. 非目标

本 RFC 不批准以下事项进入近期默认开发范围：

- 自建云同步和账号系统；
- 完整移动端产品；
- 全功能项目管理或日历；
- 自研通用语音识别与视频处理平台；
- 未经审核的自动改写和自动发布；
- 立即建立公共插件市场；
- 以新数据库取代用户原始文件作为唯一内容来源；
- 一次性重写现有 Hugo 导出、Frontmatter 或编辑器架构。

## 12. 主要风险与缓解措施

| 风险 | 可能后果 | 缓解方式 |
| --- | --- | --- |
| 知识模型过度抽象 | 开发成本上升，抽象与实际格式脱节 | 先用 Hugo 和一个媒体逐字稿场景验证最小模型 |
| 格式往返保真不足 | 用户注释、顺序或字节级差异丢失 | 区分语义解析与保真写回，建立黄金样本测试 |
| AI 摘要失真 | 错误知识被长期复用或发布 | 保留来源定位、审核状态与用户修订能力 |
| 媒体体积过大 | 导入、备份、索引和 Git 操作成本高 | 默认允许引用外部媒体，区分复制、托管和链接 |
| 发布适配器职责膨胀 | 每个平台都变成独立应用 | 只抽象已被两个真实用例证明稳定的共性 |
| 插件 API 过早稳定 | 兼容负担限制核心重构 | 先使用内部扩展点验证，再发布有版本承诺的 API |
| 范围失控 | 维护者时间被过多功能分散 | 以端到端任务验收，未通过价值验证的模块不进入下一阶段 |

## 13. 决策与衡量

该方向是否成立，不以功能数量或代码规模衡量，而以以下结果衡量：

- 用户能否安全地编辑和迁移已有内容；
- 用户能否从源资料获得可追溯、可修改的知识衍生物；
- 用户能否以更少的手工步骤将知识转化为发布成果；
- 新增发布目标能否复用已有核心能力；
- 用户和外部贡献者是否持续使用、反馈和改进产品。

建议先通过小样本任务测试建立基线，不预设未经验证的市场增长数字。若用户只认可开放格式，却不使用媒体知识和发布流程，应重新评估模块优先级；若核心文本和发布工作流尚不可靠，应暂停扩大媒体与 AI 范围。

## 14. 待讨论问题

在 RFC 被采纳前，需要通过实现调查或用户验证回答：

1. TXT 的第一版增强视图应该只做阅读，还是同时提供纯文本编辑器的语法高亮和语言识别？
2. 视频资产默认应引用外部路径、复制到知识库，还是允许两种模式并明确展示其差异？
3. 第一版 AI 摘要与卡片使用本地模型、用户自带 API，还是先只定义接口并支持导入现有结果？
4. 公众号发布首期的最低可交付成果，是 HTML/资源包、可复制富文本，还是二者都需要？
5. 当前 Hugo 导出中哪些能力可以直接复用，哪些需要先补充测试才能抽取为适配器契约？
